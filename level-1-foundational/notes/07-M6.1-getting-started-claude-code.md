## TL;DR

- Claude Code is an **agent inside your repository**. It reads and edits files, runs shell commands, and
  uses Git. Chat only answers. Claude Code **acts** on your machine. `[code]`
- It beats pasting code into chat for real codebases because it **searches** the repo itself (grep, glob,
  read), works on the **actual file state**, and can **run the tests** to check its own work.
- Install with the **native installer**, which is recommended and auto-updates. Package managers (Homebrew,
  WinGet, apt, dnf, apk) are alternatives. npm is a secondary path.
- Authenticate through the **route your org chose**: a subscription seat, the Console, a cloud provider
  (Bedrock, Google Cloud's Agent Platform, Microsoft Foundry) or an LLM gateway. Never use a personal
  account for client code (M8.1).
- **Permission modes** decide what Claude may do without asking: `default` (Manual), `acceptEdits`,
  `plan`, `auto`, `dontAsk`, `bypassPermissions`. **Shift+Tab** cycles the interactive ones
  (never `dontAsk`).
  `bypassPermissions` belongs **only** in a sandbox or CI, never on a working laptop.
- First session: **branch first, ask questions before asking for changes, read what Claude says it
  will do**, and verify its answers against the code.
- **Git is your safety net.** Commit early and often. Checkpoints (`/rewind`) undo Claude's file edits; Git
  covers file changes checkpoints miss; external side effects (databases, pushes) need their own recovery.

## Concepts

### 1. What Claude Code is

An **agentic coding tool** that runs where your code lives. In one session it can:

| Capability | What it means in practice |
|---|---|
| Read files | Opens any file it needs, not just what you pasted |
| Search | Uses grep- and glob-style tools to find symbols, callers and configs across the repo |
| Edit files | Makes targeted edits (diffs), not whole-file rewrites you copy back |
| Run commands | Tests, linters, builds, package managers, scripts |
| Use Git | Status, diff, branch, commit, and (with permission) push and PRs |
| Connect tools | MCP servers (M4.1) for issue trackers, docs and databases |

**Default model:** Opus 5.5 `[code]` for subscription, Console, Bedrock and Agent Platform users.
Microsoft Foundry defaults to a different model. Check `/model` in your own setup.

**How it differs from pasting code into chat**

| | Pasting into chat | Claude Code |
|---|---|---|
| What Claude sees | Only what you pasted, which may be stale or partial | The live working tree; it fetches what it needs |
| Large codebases | You guess which files matter and blow the context window | **Agentic search** pulls in only the relevant files |
| Verification | You run the tests and paste the results back | It runs the tests and reads the failures itself |
| Applying changes | Copy-paste, with the risk of mismatches | Exact edits as diffs, reviewable with `git diff` |
| Risk | Low: it can only answer | Higher: it can **act**, so permissions matter |

The common failure from M1.1, "doing repository work by pasting code into chat", is slow and lossy. Claude
Code fixes it, but the power to act is exactly why this module puts permissions first.

### 2. Installation

**Native installer (recommended).** It installs a native binary and **auto-updates**, with **stable** and
**latest** release channels.

```bash
# macOS, Linux, WSL
curl -fsSL https://claude.ai/install.sh | bash
```

```powershell
# Windows PowerShell
irm https://claude.ai/install.ps1 | iex
```

```bat
:: Windows CMD
curl -fsSL https://claude.ai/install.cmd -o install.cmd && install.cmd && del install.cmd
```

**Package managers:** Homebrew (`brew install --cask claude-code`, or the `claude-code@latest` cask for the
latest channel), WinGet, apt, dnf and apk. See code.claude.com/docs for the exact repository setup on
each. Package-manager installs update through that package manager, not on their own.

**npm (secondary path):**

```bash
npm install -g @anthropic-ai/claude-code   # Node.js 22+ needed to INSTALL; the installed binary is native
```

Node is needed only to run the installer. Claude Code itself doesn't run on Node.

**System minimums:** macOS 13+, Windows 10 1809+ (or Server 2019+), Ubuntu 20.04+, Debian 10+, Alpine 3.19+;
**4 GB RAM**.

**`/doctor`** (in a session) or **`claude doctor`** (in the shell, without starting a session) runs a health
check of the installation, conflicting installs, updates and settings, with suggested fixes. Use it first when
something is wrong. (`/doctor` now ships as a bundled skill, but you invoke it the same way.)

### 5. Your first session

1. **Start in a repository.** `cd` into the repo root and run `claude`. Claude Code scopes its work to
   that directory.
2. **Ask questions before asking for changes.** "What does this service do? Where is auth handled? How
   are tests run?" This builds Claude's context and **your trust calibration** at zero risk.
3. **Watch it explore.** You'll see tool calls: which files it reads, what it greps. The trail shows
   whether it is looking in the right places.
4. **Read what it says it will do** before you approve. A plan or proposed edit you didn't read is a plan
   you approved blind.

**Permission modes**

| Mode | What it asks you | Risk | Choose it when |
|---|---|---|---|
| `default` (shown as **Manual**) | Reads in the working directory run; **most edits, shell commands and network access ask** | Lowest; you see everything | First sessions, unfamiliar repos, anything sensitive |
| `acceptEdits` | File edits and simple filesystem commands (`mkdir`, `mv`, `cp`…) in the working directory run; **other commands still ask** | Edits land unreviewed until you `git diff` | You trust the direction and will review the diff afterwards |
| `plan` | Claude reads and runs exploratory commands, then proposes a plan. **No edits to your source** | Near zero | Before any non-trivial change: agree the plan first |
| `auto` | A separate **classifier** reviews each action and blocks ones it judges risky (beyond your request, unknown infrastructure, following hostile content) | Medium: "reduces prompts but does not guarantee safety" | Routine work in a repo you know, with Git as backup |
| `dontAsk` | Never prompts. Anything not pre-allowed by rules is **denied** | Low for damage, but tasks may stall | Locked-down CI and scripts. Set only via flag or settings |
| `bypassPermissions` | **No prompts.** Only deny rules, explicit ask rules and a few hard safeguards (e.g. critical-path `rm`) still apply | **Highest**: any command, any file | **Only** inside an isolated container, VM or CI. **Never on a working laptop.** |

All modes `[code]` GA (verified 2026-11-28, code.claude.com/docs/en/permission-modes).

- **Shift+Tab** cycles `default → acceptEdits → plan`; `bypassPermissions` (if allowed) and `auto` (if
  available) join after `plan`. `dontAsk` is never in the cycle. The status bar shows the active mode.
- Starting mode `[code, volatile]`: `auto` has been the default starting mode in the terminal and VS Code
  since 2.1.283. Non-interactive `-p` runs, the Agent SDK and HIPAA orgs start in `default`. If `auto` is
  unavailable, sessions start in Manual (2.1.323). **Look at the mode indicator rather than assuming.**

|---|---|---|

| `/clear` | Starts a fresh context | Switching to an unrelated task |

| `/model` | Switch model | Matching the model to the task (M1.2) |
| `/effort` | Set the effort level | Harder reasoning vs. faster, cheaper turns |
| `/usage` (aliases `/cost`, `/stats`) | Usage and spend | Planning a heavy day; nearing limits |
| `/config` | Settings | Theme, defaults, permissions |
| `/doctor` | Health check | Install, auth or update problems |
| `/resume` | Reopen a previous session | Continuing yesterday's work |
| `/rewind` (aliases `/checkpoint`, `/undo`) | Roll back to a checkpoint: code, conversation or both | Claude went the wrong way |

### 7. Safety basics

**What Claude Code can reach on your machine.** With your permission, the same things *you* can reach
from that shell:

- Files in the working directory **and beyond**, since a shell command can read `~/.ssh` or `../other-repo`.
- **Environment variables**, including any secrets exported in your shell.
- **The network**: package registries, internal hosts and the internet.
- **Your Git credentials**: it could push as you.
- **Any MCP servers** you configured, with their own credentials.

**Git is the safety net**

- **Branch first:** `git switch -c claude/<task>` before the first change.
- **Commit early:** a clean commit before each risky step gives you a known-good point.
- Review with `git diff` before you commit Claude's work.

**Checkpoints (preview).** Every prompt you send creates a checkpoint of the files Claude has edited.
`/rewind` (or `Esc` twice on an empty prompt) restores code, conversation or both to that point.
Checkpoints **don't** undo side effects of shell commands: a file that only a Bash command changed, a dropped
database, a pushed branch. That's why Git and conservative permissions still matter.

**No sandbox by default.** Claude Code's file tools work in your working directory, but an approved shell
command runs with your full user access. Optional sandboxing exists (not on native Windows); until your team
has set it up, the permission prompt and deny rules are the boundary.

**Never start with the widest permission.** Earn trust upwards: plan → Manual → acceptEdits/auto. Don't
start at `bypassPermissions` and hope.

## Under the hood

### The agentic loop

```
  your request
      │
      ▼
 ┌─ gather context ──▶ Grep / Glob / Read (search the repo, open files)
 │        │
 │        ▼
 │      plan ───────▶ (in plan mode: stop here, show you the plan)
 │        │
 │        ▼
 │      act ────────▶ Edit / Write / Bash (each proposal passes the permission check)
 │        │
 │        ▼
 └──── verify ──────▶ Bash: run tests / lint / build → read failures → loop
          │
          ▼
       report back
```

The model never touches your machine directly. It **proposes** a tool call (`Edit file X`, `Bash: npm
test`), and the **Claude Code harness** decides whether to run it:

```
 model proposes tool call
        │
        ▼
 deny rules ──match──▶ blocked   (in every mode, bypassPermissions included)
        │
 ask rules ───match──▶ ask you
        │
 allow rules ──match──▶ run
        │
 permission mode ─────▶ Manual: ask you · acceptEdits: edits run, commands ask
                        auto: classifier judges · plan: nothing runs
                        dontAsk: deny · bypassPermissions: run
```

**Rules vs the auto classifier.** **Rules** are deterministic patterns you write ("always allow `npm run
test`", "never read `.env`"), and they behave the same every time. The **auto-mode classifier** is a
model-based judgement of each action in context. It is flexible, but probabilistic. Use deny rules for
things that must **never** happen, and let auto or Manual handle the grey areas.

```jsonc
// .claude/settings.json (project, committed) — example
{
  "permissions": {
    "allow": ["Bash(npm run test:*)", "Bash(npm run lint)"],
    "deny":  ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)", "Bash(git push:*)"]
  }
}
```

### CLAUDE.md: persistent project memory

Every session starts with an empty conversation. **`CLAUDE.md`** files are loaded automatically at
session start, so they are how the repo "remembers": build and test commands, conventions, no-go areas.
`/init` drafts one by exploring the repo. Edit it, keep it short, and commit it so the whole team shares
it. (M6.8 at Practitioner covers repo artefacts in depth.)

### Context management (ties to M1.2)

Everything Claude reads (files, command output, your messages) fills the context window. Long sessions
degrade: the model has more to attend to, and early details get compacted away.

- `/context` shows what is consuming the window.
- `/compact` summarises older turns. Use it when you're mid-task.
- `/clear` resets. Use it **between unrelated tasks**: stale context from task A misleads task B.
- Agentic search exists so the agent **doesn't** need the whole repo in context. Let it search rather than
  telling it to "read every file".

## In production

**1. Day one on a client project**
*Situation:* New client engagement; you want Claude Code to map the codebase.
*Right move:* Check the client contract for AI-processing permission (M8.1). Log in through the
**org-approved route**. Clone, branch, and start in **plan mode** with questions only.
*Failure mode:* logging in with a personal subscription because "it was already set up".

**2. Understanding an unfamiliar repository**
*Situation:* You've inherited a 300k-line service and have an incident fix due tomorrow.
*Right move:* Ask architecture questions ("trace a request from the router to the DB"). Have it cite
file paths, and **spot-check the citations**. Run `/init` and edit the generated CLAUDE.md.
*Failure mode:* trusting a confident explanation of a file Claude never actually opened. Check the
tool-call trail.

**3. Safe experimentation**
*Situation:* You want to try a risky refactor.
*Right move:* New branch, commit before starting, `plan` mode to agree the approach, then Manual or
`acceptEdits`, then `git diff` and tests before you commit.
*Why:* the commit gives Git a known-good point that covers what checkpoints can't (shell side effects).
*Failure mode:* starting on `main` with uncommitted work, so neither `/rewind` nor Git gives a clean way back.

**4. CI automation**
*Situation:* The team wants Claude to fix lint errors automatically in CI.
*Right move:* Run in an **ephemeral container** with no production credentials, scoped tokens and
restricted network. `bypassPermissions` is acceptable **there**, because the sandbox is the boundary.
Output goes to a PR for human review.
*Why:* an unattended run can't answer prompts, so the boundary moves from approvals to the environment.
*Failure mode:* the job runs with a token that can push to `main` or reach production.

**5. "Just turn on bypassPermissions to stop the prompts"**
*Situation:* A colleague is tired of approvals on their laptop.
*Right move:* Decline. Add **allow rules** for the safe, repetitive commands (`npm test`, `lint`), or use
`acceptEdits`/`auto` for routine work.
*Why:* on a laptop, bypass exposes your SSH keys, cloud credentials, other repos and Git push rights to any
wrong turn or injected instruction.
*Failure mode:* a README in a cloned dependency tells the agent to "clean up" `~/` and nothing stops it.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| Pasting a repo into chat | Partial and stale context, no verification, copy-paste errors | Use Claude Code in the repo |
| Working on `main` | No clean rollback point; risky pushes | `git switch -c` before the first edit |
| Asking for changes first | You can't judge its understanding before it acts | Ask questions first, then plan, then act |
| `bypassPermissions` on a laptop | Unbounded access to your whole environment | Sandbox/CI only; allow rules for routine commands |
| Approving without reading | The approval is the control | Read each edit and command |
| Trusting `/rewind` for everything | It doesn't undo shell side effects | Git + conservative permissions |
| One endless session for many tasks | Context pollution, degraded answers | `/clear` between tasks, `/compact` within one |
| Secrets in the working tree | Claude may read them while exploring | Deny rules for `.env`/secrets; keep secrets out of repos |

## Hands-on exercises

1. **Install, authenticate, run `/doctor`, and open the sandbox repository for your stack.**
   **Done when:** `/doctor` is clean and you can state which auth route you're on.
2. **Ask five questions about the codebase. Verify two answers** by reading the code yourself.
   **Done when:** you've recorded both answers with file:line evidence, plus any discrepancy.
3. **Make one small change in Manual mode, one in `acceptEdits`, and one in plan mode.** Describe what each
   mode asked you and when you'd choose it.
   **Done when:** you have a three-row table of mode → prompts seen → when you'd use it.
4. **Break something on a branch and recover with Git.**
   **Done when:** you've used both `/rewind` and a Git restore, and you can explain which one undoes what.

### First-session runbook (sandbox repo) — exercises 1–3

```bash
# 1. Install and check health
curl -fsSL https://claude.ai/install.sh | bash
claude --version

# 2. Open a sandbox repo (never a client repo on day one)
git clone <your-org-sandbox-repo-url> sandbox && cd sandbox
git switch -c claude/first-session

# 3. Start Claude Code and log in with your org's route
claude
#   /doctor          → install/auth health check
#   /status          → confirm WHICH account/route you're on
#   Shift+Tab        → switch to plan mode
```

Then, inside the session:

```text
> What does this project do, and how are the tests run? Don't change anything.
> Where is input validation done for the /orders endpoint? Show file paths and line numbers.
> /init
> Propose (don't apply) a change that adds a test for an empty order list.
```

Verify two of its answers yourself: open the cited files and line numbers and confirm they say what it
claimed.

### Break something on a branch, recover with Git — exercise 4

```bash
git switch -c claude/break-and-recover      # isolate the experiment
# In Claude Code (Manual mode): "Rename the function calculate_total to calc and update callers."
git status                                   # what changed?
git diff                                     # read every hunk

# Recover options, from smallest to largest:
#   /rewind                                  → undo Claude's edits to a checkpoint (inside Claude Code)
git restore path/to/file.py                  # discard uncommitted changes in one file
git restore .                                # discard all uncommitted changes
git reset --hard HEAD~1                      # drop the last commit AND all uncommitted changes (destructive)
git switch main && git branch -D claude/break-and-recover   # abandon the branch entirely
```

Rule: anything you can't explain from `git diff` doesn't get committed.
