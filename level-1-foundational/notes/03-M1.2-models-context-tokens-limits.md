# M1.2 — Models, context windows, tokens and limits

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| CORE | All clusters | 1 | M1.1 |

**Objective:** choose a model and effort level **on purpose**, and work within context and usage limits
instead of being surprised by them.

> Most "Claude got worse" complaints in engineering teams turn out to be one of four things: the wrong model
> for the task, effort left at a default, a context window stuffed past the point of usefulness, or a
> usage limit hit mid-incident. This module removes all four.

---

## TL;DR

- **Line-up `[app]`:** **Haiku 5.5** handles high-volume, latency-sensitive work. **Sonnet 5.5** balances
  speed and intelligence. **Opus 5.5** handles long-running agentic coding and knowledge work, and is the
  recommended default. **Fable** handles the most demanding reasoning and long-horizon agentic work, is
  billed separately, and is not on Free.
- **Models retire.** Before you standardise a team, script or pipeline on a model, check the
  **deprecation page**.
- **A token is a sub-word chunk.** English prose runs at about **1.3 tokens per word** (≈0.75 words per
  token). Code and non-English text use more. Tokenizers differ between model generations, so **count with
  the model's own `count_tokens`**, never `tiktoken`.
- **The context window** is everything the model can see at once: about **1M tokens** on the current
  generation. **Cost and latency scale with tokens**, and quality degrades when relevant facts are buried
  in a huge context.
- **Effort is the main dial:** Low → Medium → High → Extra high (`xhigh`) → Max. More effort buys deeper
  reasoning at the cost of time and usage. On 5.5-generation and Fable models in the app, **thinking can't
  be switched off**. You set effort instead.
- **Training cut-off ≠ today.** Anything recent, price-like, or version-like needs a **web search**.
  Force one when it matters.
- **Non-deterministic:** the same prompt can give different answers. Test LLM features on a small set of
  examples, scoring the share of correct outputs, never on one run.
- **Usage limits `[app]`:** a **5-hour window** and a **weekly window**, plus **usage credits** on some
  plans. Plan heavy days around them.

## Concepts

### 1. The current model line-up

| Model | Positioning (syllabus) | Typical engineering use |
|---|---|---|
| **Haiku 5.5** | High-volume, latency-sensitive | Classification, extraction, log-line tagging, quick rewrites, sub-agents doing bulk reading |
| **Sonnet 5.5** | Balance of speed and intelligence | Everyday coding help, PR descriptions, ticket triage, most chat work |
| **Opus 5.5** | Long-running agentic coding and knowledge work. **Recommended default** | Claude Code sessions, multi-file refactors, design reviews, long document analysis |
| **Fable** | Demanding reasoning and long-horizon agentic work. Billed via usage credits or a share of the weekly limit. **Not on Free** | Hard debugging, architecture trade-offs, long autonomous tasks where Opus has measurably fallen short |

> **Syllabus says:** Fable **5.1** · **Current (verified 2026-11-14, Anthropic release notes / support
> docs):** **Fable 5.2** launched 9 Nov 2026 and is the current Fable. Fable 5.1 is still served and still
> listed in the app. Expect the exam to say 5.1. In practice, pick 5.2.

**"More models" `[app]`.** Older models (e.g. Opus 5, Sonnet 5, Opus 4.7/4.6, Sonnet 4.6) sit behind
"More models". Reasons an engineer reaches for one:

- **Reproducibility.** Re-run an analysis or eval exactly as it was produced last month.
- **Pinned behaviour.** A prompt or pipeline was tuned on a model, and a switch changes outputs (format,
  verbosity, refusals) before it's been re-validated.
- **Regression comparison.** "Did the new model fix this, or did my prompt change?" Run both models on the
  same inputs.
- **Cost or latency** on the API, where older or smaller models can be cheaper for a narrow task.

Default to the current generation. Pick an older model only for a reason you can state.

### 2. Models retire, so plan for it

| Event | Fact (verified 2026-11-14, deprecation page) |
|---|---|
| Opus 4.1 | **Retired 5 Aug 2026**. Requests to it no longer work |
| Sonnet 4.5 | **Deprecated** since 30 Sep 2026. Tentative **retirement 30 Nov 2026** |

The lifecycle runs **active → deprecated** (still works, with an announced end date) **→ retired**
(requests fail). Third-party platforms such as Bedrock and Google Cloud can set their own schedules.

**Rule:** check the **deprecation page** (platform.claude.com/docs → Model deprecations) **before** you
standardise a team guide, a script, a CI job or a product feature on a model. Record the model ID and its
retirement date wherever the model is pinned, and set a calendar reminder.

### 3. Tokens and context windows

**What a token is.** Models read and write **tokens**, which are sub-word units produced by a tokenizer
(a byte-pair-encoding-style vocabulary). Common words are one token. Rare words, identifiers, numbers and
non-Latin scripts split into several.

| Content | Rough ratio | Why |
|---|---|---|
| English prose | **~1.3 tokens/word** (≈0.75 words/token, ~4 chars/token) | Common words map to single tokens |
| Source code | **More tokens per character** than prose. Roughly **8–12 tokens per line** of typical code | Symbols, indentation, camelCase/snake_case identifiers split |
| Non-English text | Often **1.5–3×** the tokens of the English equivalent | Vocabulary is weighted toward English and Latin scripts |
| JSON / logs | High: punctuation, quotes, IDs, timestamps | Each `"`, `{`, `:` and digit run costs tokens |

**Tokenizers differ by model generation.** The tokenizer introduced with Opus 4.7, and used by later
generations, produces **~1–1.35× as many tokens** for the same text as older models. A budget measured on
an old model is wrong for a new one, so **re-count**. Never estimate Claude tokens with `tiktoken`: that's
OpenAI's tokenizer, and it undercounts Claude.

**Context window.** The context window is the total the model can attend to in one request: system prompt
+ conversation + files + tool results + the response being written.

| Surface | Context window | Max output |
|---|---|---|
| Current generation (Opus/Sonnet/Haiku 5.5, Fable) | **1M tokens** | **128K tokens** `[api]` |
| Haiku 4.5 (older) | 200K tokens | — |

**Cost and time scale with tokens.** On the API you pay per input and output token. In the app, tokens
consume your usage windows. Latency grows with input size, and especially with output size. A 600-page
PDF costs far more than a 2-page summary of it.

### 4. Thinking and effort

**Effort levels** `[app]`: **Low · Medium · High · Extra high · Max**.

> **Syllabus says:** "xhigh" · **Current (app UI):** the label is **"Extra high"**. `xhigh` is the API
> value. Same level, different surface.

**The thinking toggle.** On **5.5-generation and Fable models in the app, thinking can't be disabled**.
The model always thinks adaptively, and **effort** sets how much.

| Surface nuance `[api]` | Behaviour |
|---|---|
| Opus 5.5 | Thinking always on. **Default effort is `medium`**, so set it explicitly for hard tasks |
| Sonnet 5.5 | `disabled` is rejected. A `between_tools` mode turns thinking off between tool calls (at `high` effort or below) |
| Haiku 5.5 | Can disable thinking at `high` effort or below |
| Fable 5.x | Thinking always on. Effort is the only control |

These rows are **surface differences**, not syllabus errors. The syllabus describes the app.

**What more thinking buys and costs.**

| More effort buys | More effort costs |
|---|---|
| Deeper multi-step reasoning, fewer logic slips | Slower responses (sometimes minutes on hard agentic tasks) |
| More thorough tool use and self-checking in agentic work | More tokens, so faster usage-limit burn or higher API cost |
| Better results on genuinely hard problems | **Little or nothing on easy tasks.** Past a point, extra effort stops helping |

Rule of thumb: **Low/Medium** for rewrites, summaries, chat and classification. **High** for real
reasoning and most coding. **Extra high/Max** only when you've seen High fall short on a task that
matters. Exercise 3 makes you find that point empirically.

### 5. Knowledge cut-off and live information

- **Training cut-off:** the model knows the world only up to a date. After it, the model **doesn't know
  that it doesn't know**. It may answer confidently with stale facts.
- **Web search** fetches current pages at answer time, with citations you can check.
- **Signs of a stale answer:** it names "latest" versions, prices, APIs, model names or people in roles
  without citing anything. It describes something you know has changed. It's vague on dates.
- **When to force a search:** library versions and APIs, pricing, security advisories, regulations,
  anything "current" or "latest", anything after the cut-off, and any fact going into client-facing text.
  Say so in the prompt: *"Search the web and cite sources."*
- **Research mode** (multi-step, many-source investigation) is taught at Practitioner in **M3.4**.

### 6. Capabilities and limitations

| Strong | Weak or risky without help |
|---|---|
| Language: drafting, summarising, translation, tone | **Exact arithmetic** on long numbers. Use a tool (code execution, a spreadsheet) |
| Code: reading, writing, explaining, reviewing | **Current facts** without search |
| Analysis: comparing, critiquing, structuring | **Invented references**: citations, URLs, API names, case law that look real |
| Structured transformation: text → JSON/tables | **Consistency over very long chains** of steps without checkpoints |
| Vision: screenshots, diagrams, charts, scanned docs | |

**Non-determinism.** The same prompt can produce different outputs. Sampling picks among likely
continuations, and longer reasoning paths can diverge. What that means for testing:
- Don't judge a prompt or feature on **one run**. Run it several times or across many inputs, and judge
  the **distribution**.
- Build a **small eval set** (20–50 real inputs with expected properties) and score the pass rate. Assert
  **properties** (valid JSON, contains the ticket ID, under 120 words), not exact strings.
- When one bad output appears, ask whether it's a fluke or a pattern before you rewrite the prompt.

**No hidden state.** Each chat starts fresh. Only **memory** and **Projects** (instructions and knowledge)
carry anything across chats. Claude also has **no access to any system unless it is connected** (a
connector, Claude Code on your machine, or a tool). "Check our Jira" without a Jira connector produces a
guess, not a lookup.

**Input limits** (verified 2026-11-14):

| Input | `[app]` claude.ai | `[api]` Messages API |
|---|---|---|
| Images | JPEG, PNG, GIF, WebP up to 8000×8000 px | — |
| Files | Up to 500 MB each, 20 per chat | 32 MB per request |
| PDFs | Up to **1000 pages**. Visual analysis (charts, images) for PDFs of **≤100 pages**. 101–1000 pages are read as text only | Up to **600 pages** (100 on 200K-context models) |

These are different surfaces with different limits, and neither is wrong. Know which surface you're on.

### 7. Usage limits in practice `[app]`

- **5-hour window:** a rolling session budget. Heavy use exhausts it, and it refills as the window rolls.
- **Weekly window:** an overall weekly cap on top of the 5-hour window.
- **Usage credits:** paid top-ups to keep working past limits. Available on Pro, Max, Ultra and Team.
  **Not on Free or Enterprise**, where Enterprise usage is governed by the contract.
- **Fable billing:** uses **usage credits on Pro**. On **Max/Ultra** it has a **separate weekly Fable
  limit**. On Team **Premium seats**, Fable usage counts at **50%** of the weekly limit.

**Planning a heavy day** (release day, incident review, migration):
1. Start the heavy work early in a fresh 5-hour window.
2. Use the cheapest model and effort that do each subtask well: Sonnet/Haiku and Low/Medium for
   rewrites, Opus/High for the hard reasoning.
3. Keep contexts lean: start new chats per topic, and don't re-upload the same 300-page doc into five chats
   (use a Project).
4. Check remaining usage before you start an incident-critical task.

**When you hit a limit:** don't switch to a personal account (M8.1). Switch to a lighter model or lower
effort if the task allows. Buy or use credits if your plan and policy permit. Otherwise queue the work for
the next window. If limits block business-critical work, raise it with your admin, since seat type is an
org decision.

## Under the hood

### Why long context costs more and can work worse

A transformer processes the context by letting every new token **attend** to the tokens before it. Two
consequences:

1. **Cost and latency grow with context length.** Every output token is computed against everything in
   context. A 900K-token prompt is slow and expensive even if the answer is one line.
2. **More context is not free accuracy.** Models can **under-use facts buried in the middle** of a very
   long context (the "lost in the middle" effect) and get distracted by irrelevant material. Put long
   documents **first**, the question **last**, and include only what's relevant. M2.3 (context
   engineering) builds on this.

**Prompt caching** (high level, `[api]`): the model's internal key/value state for a prompt prefix can be
cached. Re-sending an identical prefix, such as a big system prompt or a document, is then billed at
**~0.1× the normal input price** and starts faster. Any byte change in the prefix invalidates the cache.
Claude Code and the apps use caching automatically. You'll design for it at Advanced level.

### Adaptive thinking and the effort dial

Current models use **adaptive thinking**: the model decides per request whether and how much to reason
before answering, and **effort** biases that decision and the overall token spend. That's why "turn
thinking off" was replaced by "set effort". The model can still skip reasoning on trivial requests at any
effort, and Low effort means fewer, more consolidated tool calls and terser output.

### Why outputs vary

At each step the model produces a probability distribution over next tokens, and the system **samples**
from it. Small early differences compound, so two runs can phrase the answer, order a list, or even reach a
conclusion differently. Product-side features such as tools, search results and thinking add further
variation. You can't make it deterministic. Design checks that tolerate the variation (see §6).

### Counting tokens and setting effort on the API

```python
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY or an `ant auth login` profile

# 1) Count tokens with the model's own tokenizer (never tiktoken)
doc = open("design-rfc.md").read()
count = client.messages.count_tokens(
    model="claude-opus-5-5",
    messages=[{"role": "user", "content": doc}],
)
print(count.input_tokens)

# 2) Choose effort deliberately. Opus 5.5 defaults to "medium", so set it explicitly
resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    output_config={"effort": "high"},   # low | medium | high | xhigh | max
    messages=[{"role": "user", "content": f"<rfc>\n{doc}\n</rfc>\n\nList the three riskiest assumptions in this RFC, with evidence."}],
)
for block in resp.content:
    if block.type == "text":
        print(block.text)
print(resp.usage.input_tokens, resp.usage.output_tokens)
```

### Will this codebase fit? A worked estimate

| Step | Value |
|---|---|
| Lines of code (excluding vendored/generated) | 120,000 |
| × tokens per line (typical code) | ~10 |
| = estimated tokens | **~1.2M** |
| Current context window | 1M, which must also hold instructions, conversation and output |
| **Verdict** | **Doesn't fit**, and stuffing even half of it would be slow, costly and less accurate |

**Do instead:** use **Claude Code**, which explores the repository *agentically*. It searches, opens the
relevant files, and keeps only what matters in context. For a small service (say 8K LOC ≈ 80K tokens),
pasting would technically fit, but Claude Code is still the right surface for repository work (M1.1).
Verify the estimate by running `count_tokens` on a few representative files.

### Model-choice guide for engineering work

| Task | Model | Effort | Why |
|---|---|---|---|
| Rewrite a Slack update / fix tone | Sonnet 5.5 or Haiku 5.5 | Low | Language task. Speed matters more than depth |
| Tag 5,000 log lines by category | Haiku 5.5 | Low | High volume, simple per-item judgement |
| PR description from a diff | Sonnet 5.5 | Medium | Moderate understanding, routine |
| Multi-file refactor in Claude Code | Opus 5.5 | High / Extra high | Long-running agentic coding |
| Long contract / RFC risk review | Opus 5.5 | High | Long context + careful reasoning |
| Root-cause a heisenbug across services | Opus 5.5 → Fable if it stalls | High → Extra high | Hard reasoning. Escalate only on evidence |
| Architecture trade-off with many constraints | Fable | High | Demanding reasoning. Worth the extra usage |

## In production

**1. Long contract or RFC review vs a quick rewrite**
*Situation:* In the same afternoon you need a risk review of an 80-page vendor MSA and a friendlier
version of a release announcement.
*Right move:* MSA on **Opus 5.5, High**, with the document first and specific questions last. Announcement
on **Sonnet, Low**.
*Failure mode:* running both on the default. You pay Opus-level usage for the rewrite, or get a shallow
contract review.

**2. "Can I just paste the repo?"**
*Situation:* A teammate wants to zip a 150K-LOC monorepo into a chat.
*Right move:* Estimate it (~1.5M tokens, which doesn't fit) and use **Claude Code** in the repository.
*Why:* agentic search keeps context small and relevant, and Claude Code can run the tests too.

**3. "Why did the output change?"**
*Situation:* Your manager asks why the weekly report summaries suddenly changed style and length.
*Right move:* Check whether the model or effort changed (a new default, a teammate's switch, a retirement).
Explain in plain terms: different models and effort levels behave differently, and outputs are
non-deterministic anyway. Re-validate the prompt on the new model and pin the choice in the team guide.

**4. Nightly batch job pinned to a retiring model**
*Situation:* A nightly ticket-classification job calls a model that the deprecation page shows retiring at
month-end.
*Right move:* Migrate before the date. Run old and new models on the same sample, compare outputs, adjust
the prompt, re-count tokens (the tokenizer may differ), then switch and record the new retirement date.
*Failure mode:* discovering the retirement when the job starts failing at 02:00.

**5. Flaky test in an LLM feature**
*Situation:* A CI test asserts the exact summary text for a fixed input and fails one run in five.
*Right move:* Assert properties (contains the required fields, valid JSON, length bounds), and measure the
pass rate on an eval set instead of a single golden string.
*Why:* the outputs are non-deterministic by design.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| Always using the default model and effort | Over-pays on easy tasks, under-thinks hard ones | Choose per task, using the guide above |
| Max effort "to be safe" | Slower and burns usage with no gain on routine work | Escalate effort only when lower effort falls short |
| Estimating with `tiktoken` or a word count | Undercounts Claude tokens, especially code | `count_tokens` with the target model |
| Stuffing whole repos or folders into context | Cost, latency, lost-in-the-middle | Claude Code agentic search, or relevant excerpts |
| Trusting "latest version is X" from the model | Training cut-off | Force a web search and check citations |
| Asking for exact sums of long figures | Arithmetic slips | Use code execution or a spreadsheet, then verify |
| Pinning a pipeline without checking deprecation | Breaks at retirement | Check the deprecation page and record the date |
| Testing a prompt on one run | Non-determinism hides failure rates | Small eval set, pass rate |
| Switching to a personal account at a limit | Data-governance breach (M8.1) | Lighter model, credits per policy, or wait |

## Hands-on exercises

1. **Same three tasks on Haiku, Sonnet and Opus.** Record quality, time and usage consumed, then decide
   which model you'd use for each and defend it. **Done when:** a 3×3 table with a one-line defence per
   task.
2. **Estimate the token count of five real files, then check** with `count_tokens` (or the app's context
   indicator, or `/context` in Claude Code). **Done when:** every estimate is within ±30%, with notes on
   what you mis-estimated (code? JSON?).
3. **Effort ladder:** run one reasoning task at Low, High and Max. **Done when:** you can name the level
   where extra effort stopped improving the answer, and what it cost in time and usage.
4. **Write a one-page model-choice guide for your own team.** **Done when:** it covers your team's top
   five tasks with model, effort, reason and a "check the deprecation page" line.
