# M3.1 — Communication and writing

| Status | Audience | Hours | Prerequisites |
|---|---|---|---|
| CORE | All clusters | 1.5 | M2.1, M8.1 |

**Objective:** produce clear, audience-fit written communication faster than unaided — and **send nothing
you have not checked**.

> Writing is where most engineers first get value from Claude, and where most visible mistakes happen: a
> wrong date in a client email, an action item nobody agreed to, a confident sentence about a fix that
> hasn't shipped. This module is about speed *and* sending discipline.

---

## TL;DR

- Claude drafts, replies, shortens, re-tones and translates well. **You own every name, number and
  commitment** in what gets sent.
- For long documents: **outline first, then section by section**, then a consistency pass against a glossary.
  One-shot long docs drift.
- Encode voice once, reuse it: **custom Styles** from your own samples `[app]`, and a **team voice guide as
  Project instructions** `[app]`.
- Switch register on purpose: **client** (precise, committed only to what's agreed), **internal** (direct,
  technical), **executive** (decision + impact + ask, first).
- Separate **structural edits** (order, argument, what's missing) from **line edits** (wording, grammar).
  Do structure first.
- Narrative before slides: write the story, then cut it into a deck outline with speaker notes.
- In shared channels (Claude Tag in Slack, BETA), **assume everyone in the channel can see what Claude posts**.
- **Fluent ≠ correct.** Polished text lowers reviewer vigilance. Verify summaries and action items against
  the source; client-facing text carries a verification note (full process: M8.2).

## Concepts

### 1. Email and messages

**Core operations** `[app]` GA — all work in plain chat:

| Operation | Prompt shape that works | Watch for |
|---|---|---|
| Draft | Recipient, purpose, key facts, the one ask, tone, length | Claude filling gaps with plausible-but-invented details |
| Reply | Paste the thread (redacted per M8.1) + your intended position | Agreeing to things you didn't decide |
| Shorten | "Cut to ≤120 words; keep every date, number and ask" | Silently dropped caveats |
| Change tone | "Same content, firmer / warmer / more formal" | Meaning drift (a "maybe" becoming a "yes") |
| Multi-language draft | Write in your strongest language, ask for the target language + a back-translation | Idioms, honorifics, legal/commercial terms |

**Thread summaries.** Paste or connect the thread and ask for: decision, open questions, actions (owner,
due date). Summaries are where errors hide (see *Under the hood*) — always verify actions against the thread.

**Product surfaces for mail**

- **Outlook add-in** `[app]` **BETA** (Claude for Microsoft 365): triage of the inbox, reply drafts that are
  **never sent automatically** (you always press send), and meeting preparation from calendar + mail context.
  Demonstrate, don't rely on it for assessed work.
- **Gmail connector** `[app]` GA (Google Workspace connectors): Claude can search and read mail and create
  drafts via the connector. Write actions on Google Workspace require **approval by default** (M4.1).

> Whatever the surface, the human-send rule holds: Claude drafts, you send.

### 2. Documentation and long-form writing

1. **Outline first.** Ask for a heading-level outline with one line per section stating its purpose and
   reader takeaway. Fix the outline — this is the cheapest point to change the argument.
2. **Section by section.** Generate each section with the approved outline in context. Review each before
   moving on.
3. **Rewrite for a defined reader.** "Rewrite for an on-call SRE who has never seen this service, reading at
   3 a.m." beats "make it clearer".
4. **Consistency pass.** Ask Claude to list every term, product name, number and date that appears more than
   once and flag inconsistencies (e.g. "p95 latency 120 ms" vs "~150 ms").
5. **Enforce a glossary.** Provide the glossary (`<glossary>` tags) and ask for violations as a table:
   location → used term → glossary term. Then fix.

### 3. Tone, voice and Styles

- **Custom Styles** `[app]` GA: built from samples of your own writing; applied per chat to make drafts sound
  like you. Use 3+ samples of the *genre* you want (emails train email voice; RFCs train RFC voice).
- **Team voice guide as Project instructions** `[app]` GA: put the house rules (tone, banned phrases, how we
  name products, sign-off conventions, glossary) in a Project's instructions so every chat in the Project
  starts conditioned on them.
- **Switching register:**

| Register | Lead with | Typical length | Commitments |
|---|---|---|---|
| Client | Status + impact on *them* + next step | Short | Only what's contractually/explicitly agreed |
| Internal (peers) | The technical facts, links, the ask | As needed | Normal |
| Executive | Decision needed / risk / impact in one line, then 3 bullets | Very short | Clear owner and date |

### 4. Editing and review

- **Structural edit:** Is the argument in the right order? What's missing? What should be cut? Ask Claude
  to critique structure **without rewriting** first.
- **Line edit:** sentence-level clarity, grammar, concision. Ask for tracked-style output (original → edit →
  reason) so you can accept selectively.
- **Proofreading in a second language:** ask Claude to correct and *explain* each change; for client
  correspondence, have a fluent human check anything contractual.
- **Suggestions in Claude Docs** `[app]` and the **Word add-in** `[app]` (syllabus: BETA; **GA since verified 2026-11-14**, Pro/Max/Team/Enterprise): review-style suggestions
  in the document rather than a rewritten copy — better for collaborative review because changes stay
  visible and attributable.

### 5. Presentations

- **Narrative before slides.** Write the story as 5–8 sentences (situation → complication → resolution →
  ask). Then ask for a deck outline: one slide per sentence, title as the takeaway, 3 bullets max, speaker
  notes carrying the detail.
- **Slides artifacts** `[app]` and the **PowerPoint add-in** `[app]` **PLAN: Pro and above**: generate or
  edit slides directly. The structure work above is what makes the output good — the tool only renders it.

### 6. Chat-platform communication

- **Claude Tag in Slack** `[app]` **BETA; Team and Enterprise**: summarise a channel, draft a post, follow up
  on a thread. *(Syllabus: replaced "Claude in Slack" in August 2026. Current docs: Claude Tag replaces the earlier app
  in place, and the legacy app stopped answering in paired workspaces on 5 Oct 2026. The docs don't confirm
  the August date. See `reference/fact-status.md`.)*
- **Visibility and etiquette:**
  - Assume **everyone in the channel can see Claude's posts** and the request that triggered them.
  - A summary of a private conversation posted in a public channel is a disclosure (M8.1).
  - Claude's posts carry your authority — review before they're addressed to people.
  - Don't use Claude to answer for someone else ("what did Priya mean?") in their own channel.

### 7. Sending discipline

**Read before you send.** Every time. Check every:
- **Name** — right person, spelled right, right role.
- **Number** — dates, times, time zones, amounts, versions, SLAs, percentages.
- **Commitment** — anything that sounds like a promise ("we will", "by Friday", "fixed").

**Verification note on client-facing text.** Client-facing text produced with Claude carries a verification
note per your org's policy (what was checked, by whom, against what source). The full process is M8.2 at
Practitioner. *Trainer note: insert your org's verification-note format.*

## Under the hood

### Why summaries drop or invent action items

Summarisation is **lossy compression** guided by what the model predicts is important. Three failure modes
matter in engineering threads:

| Failure | Mechanism | Example |
|---|---|---|
| **Dropped item** | Late, short, or casually phrased messages get low salience ("oh and can someone bump the cert?") | Expiring TLS cert never makes the action table |
| **Attribution error** | Pronouns and quoted replies blur who said what | "I'll take it" attributed to the wrong person |
| **Hallucinated owner/date** | An action table *format* has an Owner and Due column; the model fills empty cells with plausible values | "Owner: Ravi, Due: Fri" when nobody committed |

**Defence:** make every claim traceable. Ask for a **citation per action** (message timestamp/author) and an
explicit `UNASSIGNED` / `NO DATE` when none was stated. Then spot-check citations against the thread —
especially any action with an owner who wasn't in the conversation.

### Why Styles and voice guides work

The model conditions on everything in its context window. Writing samples and voice rules placed in context
(via a Style or Project instructions) shift the distribution of likely next words toward your patterns —
**in-context conditioning**, no retraining involved. Persistent instructions win over per-chat reminders
because they're present on every turn and you don't forget to add them.

### Why outline-first beats one-shot long documents

- **Planning:** an outline forces the argument to be decided before prose locks it in.
- **Coherence:** long generations drift — terminology changes, earlier claims get contradicted. Section-level
  generation against a fixed outline + glossary keeps them anchored.
- **Review checkpoints:** reviewing 10 short sections catches more than skimming one 4,000-word draft.

### "Fluent ≠ correct"

Model output is grammatical and confident by default. Humans use fluency as a proxy for competence, so
polished text **lowers reviewer vigilance** exactly when it should be highest. Counter this deliberately:
review numbers and commitments as a separate pass, out of the reading flow.

### Reusable prompt: thread → decision summary with cited actions

```xml
<thread>
[paste the redacted thread, each message prefixed with "[YYYY-MM-DD HH:MM] Author:"]
</thread>

You are summarising this thread for the engineering lead who was not in it.
Output:
1. One paragraph (≤80 words): what was decided, what remains open.
2. A table: Action | Owner | Due | Source (timestamp + author of the message where it was agreed).
Rules:
- Only include actions someone explicitly agreed to or was explicitly assigned.
- If no owner was stated, write UNASSIGNED. If no date was stated, write NO DATE. Never infer either.
- List anything ambiguous under "Needs confirmation" instead of guessing.
```

### Pre-send checklist

- [ ] Every **name**: correct person, spelling, role, and they should be on this thread.
- [ ] Every **number**: dates, time zones, amounts, versions, SLAs — checked against source.
- [ ] Every **commitment**: agreed by someone with authority; nothing promised by implication.
- [ ] **Register** fits the reader (client / internal / executive).
- [ ] **Data**: nothing confidential or restricted for this audience (M8.1).
- [ ] **Actions** verified against the thread, not just the summary.
- [ ] **Verification note** added if client-facing.
- [ ] Re-read once as the recipient.

## In production

**1. SEV-2 stakeholder update**
*Situation:* Checkout errors at 4%. You need a status-page post and an exec update every 30 minutes.
*Right move:* Give Claude the facts you've confirmed (impact, start time with time zone, current mitigation,
next update time). Ask for two registers: customer-facing (no internal names, no root-cause speculation)
and exec (impact, ETA confidence, decision needed).
*Why:* same facts, two readers.
*Failure mode:* letting Claude "fill in" a likely root cause or ETA — public speculation you'll have to retract.

**2. Weekly client status email**
*Situation:* Ten bullet notes from stand-ups; client exec reader.
*Right move:* Draft from notes, then run the pre-send checklist; strip anything not agreed with the client
(e.g. internal estimates); add the verification note.
*Failure mode:* "Feature X will ship next sprint" — an internal hope turned into a client commitment.

**3. RFC for two audiences**
*Situation:* An approved design doc must go to the CTO and to the implementing team.
*Right move:* Structural edit first; then an exec version (decision, cost, risk, timeline in one page) and an
engineering version (interfaces, migration, rollback). Glossary pass on both.

**4. Release notes from a commit list**
*Situation:* 60 commits since last release.
*Right move:* Ask Claude to group by user impact (Features / Fixes / Breaking), rewrite in user language, and
**cite the commit hash for each line**. Verify breaking changes against the diff.
*Failure mode:* a refactor commit described as a user-facing feature.

**5. Multilingual client correspondence**
*Situation:* Japanese client, you write in English.
*Right move:* Draft in English, ask for Japanese with appropriate business register plus a back-translation;
have a fluent colleague check anything with commercial or legal weight.

**6. 40-message thread → paragraph + action table**
*Situation:* A cross-team Slack/email thread about a migration window.
*Right move:* Use the prompt template above; verify every action's source citation against the thread before
posting.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| Sending a draft after a skim | Fluency hides errors in names, numbers, commitments | Separate pass for names/numbers/commitments |
| Trusting a summary's action table | Dropped items, misattribution, invented owners/dates | Require source citations; spot-check them |
| One-shot 10-page doc | Drift, inconsistency, unreviewable | Outline → sections → consistency/glossary pass |
| "Make it more professional" | Vague; meaning drifts | Name the reader, register and length |
| Line-editing before structure is right | Polishing paragraphs you'll delete | Structural edit first |
| Posting a private-thread summary in a public channel | Disclosure | Check audience before posting |
| Machine translation sent unchecked for contracts | Legal/commercial terms mistranslated | Back-translate + fluent human review |

## Hands-on exercises

1. **Rewrite one real email for three audiences** — client executive, peer engineer, vendor — in a single
   chat. **Done when:** facts identical across all three; length and lead sentence differ appropriately.
2. **Build a personal Style** from three samples of your own writing; test on a new draft; have a peer rate the
   match. **Done when:** peer rates ≥4/5 "sounds like you".
3. **Turn a 40-message thread into one paragraph + action table.** Verify every action against the thread.
   **Done when:** every action cites a message, and you've found and fixed at least any dropped/invented item.
4. **Ten-slide outline with speaker notes** from a project report. **Done when:** slide titles alone tell the
   story; notes carry the detail.
