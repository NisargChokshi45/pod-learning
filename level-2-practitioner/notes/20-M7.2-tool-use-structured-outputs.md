# M7.2 — Tool use, structured outputs and server-side tools

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| ELECTIVE | Cluster D | 3 | M7.1 |

**Objective:** build reliable tool-calling loops and typed outputs that fail safely.

> A tool call is Claude asking your program to act. A structured output is Claude promising a shape. Both
> cross a trust boundary in both directions. Claude's arguments are untrusted input to your system. Your
> system's results are untrusted input to Claude. This module is about engineering that boundary: schemas,
> loops, caps, idempotency and errors.

Every claim here is `[api]`. Volatile details carry a status tag and a verification date. The quiz tests the principles.

---

## TL;DR

- **The loop is yours.** Claude returns `tool_use` blocks. You execute them and send back `tool_result` blocks with
  matching IDs, all in **one** user message. Repeat until `stop_reason` isn't `tool_use`.
- **Schema first.** Use `strict: true` with `additionalProperties: false` to guarantee valid tool arguments. Add
  `input_examples` for tricky formats. Write descriptions that say *when* to call the tool.
- **Don't force tool calls on current models.** `tool_choice` `any` or `tool` returns 400 there. Use `auto`, name the tool in
  the prompt, and use `strict`. Use structured outputs when you only wanted JSON.
- **Typed answers come from `output_config.format`** (JSON schema) or the SDK's `messages.parse()`, never from
  regex over prose. The old `output_format` parameter is deprecated.
- **Server tools** (web search, web fetch, code execution) run on Anthropic's side and **bill differently**.
  Client tools (memory, bash, text editor, computer and browser toolsets) run on your side, **with your
  security responsibilities**.
- **Skills work through the API too.** It's the same `SKILL.md` format, attached to a code-execution container.
- **Robust loops:** idempotent tools, errors returned as results (`is_error`), timeouts, an iteration cap,
  and a log line for every call.

## Concepts

### 1. Tool use

**A tool definition** has a name, a description and a JSON-schema `input_schema`. The **description is the
prompt**: it decides when Claude calls the tool. Say what the tool does, when to use it and when not to.

```python
tools = [{
    "name": "get_ticket",
    "description": "Fetch one Jira ticket by key (e.g. OPS-1234). Use when the user names a ticket "
                   "or you need its status, assignee or comments. Do not use to search.",
    "strict": True,                                   # GA: arguments guaranteed to validate
    "input_schema": {
        "type": "object",
        "properties": {"key": {"type": "string", "description": "Jira key, PROJECT-NUMBER"}},
        "required": ["key"],
        "additionalProperties": False,                # required for strict
    },
    "input_examples": [{"key": "OPS-1234"}],         # GA: each example must validate
}]
```

- **The `tool_use` / `tool_result` loop.** The response stops with `stop_reason: "tool_use"` and contains one or more
  `tool_use` blocks (`id`, `name`, `input`). You append the assistant turn unchanged, run the tools, and
  append one user turn holding a `tool_result` for **each** `tool_use_id`. The full loop is in "Under the hood".
- **`input_examples`** `GA` show the model concrete argument shapes. They help most with formats that are easy to get
  subtly wrong, such as IDs, date ranges and filter syntax. Each costs a few hundred tokens, so add them where they pay.
- **Strict schemas** `GA`. With `strict: true`, `tool_use.input` is guaranteed to match the schema. That removes a whole
  class of runtime validation bugs. Still validate the *meaning* of the arguments, for example whether this user may read that
  ticket. Schema-valid isn't the same as authorised.

**`tool_choice`.** `auto` (the default: Claude decides) and `none` (no tools this turn) work on every model.

> **Syllabus says:** `any` and `tool` return 400 on Opus 5.5, Sonnet 5.5 and Fable 5.1, so design around it. · **Current
> (verified 2026-11-28, platform.claude.com define-tools docs):** confirmed, and extended. They also return 400 on Fable 5.2 and Mythos 5.1/5.2, including
> on `count_tokens` and Batches. Older Fable 5 and Opus 5 still accept them. The design rule doesn't change.

```python
# Don't: this now fails (400) on current models
tool_choice={"type": "tool", "name": "get_ticket"}

# Do: auto + strict schema + say it in the prompt. If you only wanted JSON back, use structured outputs.
tool_choice={"type": "auto"}
messages=[{"role": "user", "content": "Use get_ticket to fetch OPS-1234, then summarise its status."}]
```

`auto` doesn't *guarantee* a call. If your workflow needs one, check for a `tool_use` block and re-prompt when it's missing.

**Parallel tool calls** are on by default. One assistant turn can request several tools at once. Run them concurrently,
then return **all** results in a **single** user message. If you split them across messages, Claude learns to stop
calling in parallel. When order matters (create, then update, then notify), set
`tool_choice={"type": "auto", "disable_parallel_tool_use": True}` to get at most one call per turn.

### 2. Structured outputs

When the *answer itself* must be machine-readable, constrain the response format. Don't parse prose.

```python
from pydantic import BaseModel
from typing import Literal
import anthropic

class Triage(BaseModel):
    severity: Literal["SEV1", "SEV2", "SEV3"]
    service: str
    owner_team: str
    customer_impact: bool

client = anthropic.Anthropic()
r = client.messages.parse(
    model="claude-opus-5-5",
    max_tokens=2048,
    output_format=Triage,                        # SDK parse helper: validated instance back
    messages=[{"role": "user", "content": f"<alert>{alert_text}</alert>\nTriage this alert."}],
)
if r.stop_reason == "end_turn":
    triage: Triage = r.parsed_output
```

Without Pydantic, use the raw form: `output_config={"format": {"type": "json_schema", "schema": {...}}}` on
`messages.create()`. The first text block is then valid JSON for that schema.

- **The SDK parse helpers** (`messages.parse()` → `parsed_output`) validate the response for you. Prefer them.
- **The older `output_format` request parameter is deprecated** `DEPR`. Sent through `messages.create()` without its old beta
  header, it fails. Put the schema in `output_config.format`, or pass a model class to `parse()` as above.
- **Still check `stop_reason`.** If the output is cut off at `max_tokens`, the JSON is truncated.
- Structured outputs are **incompatible with citations** (M7.1) and with prefill. Use two calls if you need both.

**Choosing between the two:**

| You want | Use |
|---|---|
| Claude's **answer** in a fixed shape | `output_config.format` / `parse()` |
| Claude to **act** through your code (fetch, write, call an API) | Tools with `strict: true` |
| Both | Strict tools for actions, then a structured final answer |

### 3. Server-side tools

Server tools run **on Anthropic's infrastructure**. You declare them in `tools`, and their results arrive in the same
response. You don't execute anything.

| Tool | Type (verified 2026-11-28) | What it does | Billing note |
|---|---|---|---|
| Web search | `web_search_20260209` | Searches and returns results with citations | Per-search fee plus tokens. Failed searches aren't billed |
| Web fetch | `web_fetch_20260209` | Fetches a URL **already present in the conversation** | Tokens only |
| Code execution | `code_execution_20260521` | Sandboxed code. Variant `code_execution_20260120` adds **programmatic tool calling**. The Skills guide (§4) still shows `code_execution_20250825`; use the version the guide for your feature documents | Container-hours beyond a free allowance. Free when used with the current web tools |

```python
search_tools = [{"type": "web_search_20260209", "name": "web_search", "max_uses": 5,
                 "allowed_domains": ["nvd.nist.gov", "github.com"]}]
msgs = [{"role": "user", "content": "Is there a published CVE for libfoo 2.3.1? Cite sources."}]
resp = client.messages.create(model="claude-opus-5-5", max_tokens=16000, tools=search_tools, messages=msgs)
while resp.stop_reason == "pause_turn":                       # long server-tool turns can pause
    msgs.append({"role": "assistant", "content": resp.content})   # resend to let it continue
    resp = client.messages.create(model="claude-opus-5-5", max_tokens=16000,
                                  tools=search_tools, messages=msgs)
```

Server-tool errors **don't raise exceptions**. They come back as HTTP 200 with an error object inside the result block,
for example `max_uses_exceeded`. Check for them. Constrain search with `allowed_domains` and `max_uses`, both for cost and to keep
untrusted pages out of the context. Search results are retrieval, not verification (M3.4, M8.2).

**Programmatic tool calling.** Claude writes code in the sandbox that calls *your* tools in a loop, for example "fetch all
40 tickets and aggregate them". Only the final result returns to the model's context, which saves tokens and round trips. Enable it by adding
`code_execution_20260120` and setting `"allowed_callers": ["code_execution_20260120"]` on your tool.

**Anthropic-defined client tools.** These are schema-less, and **you** execute them:

| Tool | Declaration | Your responsibility |
|---|---|---|
| Memory | `{"type": "memory_20250818", "name": "memory"}` `GA` | You store the files. Scope them per user or tenant, and never let paths escape the memory root |
| Text editor | `{"type": "text_editor_20250728", "name": "str_replace_based_edit_tool"}` | Confine paths to a project root. Treat the model's path as untrusted |
| Bash | `{"type": "bash_20250124", "name": "bash"}` | Run in a sandbox or container with no secrets and limited network access |
| Computer use | `{"type": "computer_toolset_20260801"}` | Use a VM you control. Require human approval for consequential actions |
| Browser | `{"type": "browser_toolset_20260801"}` | Your app hosts the browser. Treat page content as untrusted (prompt injection) |

> **Syllabus says:** the computer-use toolset has been GA since August 2026, alongside the browser toolset. · **Current (verified 2026-11-28, computer-use docs):**
> confirmed. `computer_toolset_20260801` is GA. The older single `computer_20251124` tool is still `BETA` and is rejected on
> current models outside Bedrock. The SDK helper classes for the toolsets are beta. The wire format isn't.

**Cost and policy, tool by tool:** web search has a per-call fee, code execution has a container-time fee, and the computer and browser toolsets add
thousands of input tokens per request. Policy matters too. Bash, computer and browser tools act in the world, so they need
scope limits, logging and an off switch (M8.3).

### 4. Skills through the API

The **Skills API** `GA` manages Skills (`/v1/skills`: create, list, versions, delete). A request attaches **up to 20
Skills** to a **code-execution container**. Anthropic's built-ins are **`pptx`, `xlsx`, `docx` and `pdf`**. It's the **same
`SKILL.md` format** as the app Skills in M4.2 and Claude Code's in M6.4: one Skill, three surfaces.

```python
resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    container={"skills": [{"type": "anthropic", "skill_id": "xlsx", "version": "latest"}]},
    tools=[{"type": "code_execution_20250825", "name": "code_execution"}],
    messages=[{"role": "user", "content": "Build a monthly utilisation workbook from this CSV: ..."}],
)
# Generated files come back as file IDs in the code-execution result; download with client.files.download(id)
```

> **Source note (verified 2026-11-28):** the live Skills guide uses plain `messages.create` with
> `code_execution_20250825`, as shown above. The bundled SDK reference shows a beta-client variant with a newer
> code-execution type. This snippet follows **the docs form**. Check the Skills guide before you ship.

Upload a custom Skill with `client.skills.create(files=files_from_dir("my_skill"))` (`from anthropic.lib import
files_from_dir`). Version it like code. It must contain no secrets and no personal data (M4.2).

### 5. Context management at API level

Long agent loops fill the context with old tool results. You have three levers:

| Lever | Status | What it does | Reach for it when |
|---|---|---|---|
| **Memory tool** | `GA` | Claude writes notes to *your* storage and reads them back in later sessions | State must survive across conversations (preferences, project facts) |
| **Context editing** | `BETA` | Server **clears** old tool results or thinking blocks past a threshold | Tool results are bulky and their detail isn't needed again |
| **Server-side compaction** | `BETA` | Server **summarises** earlier context into a compaction block | The conversation itself is long and its gist still matters |

**Order of reach:** first keep tool outputs small (return IDs and summaries, not whole payloads). Then clear stale tool
results with context editing. Then compact. Use memory for anything that must persist beyond the conversation.

```python
# BETA — explained and demonstrated, not assessed
client.beta.messages.create(
    model="claude-opus-5-5", max_tokens=4096,
    betas=["context-management-2025-06-27"],
    context_management={"edits": [{"type": "clear_tool_uses_20250919"}]},
    tools=tools, messages=msgs,
)
```

> **Syllabus says:** server-side compaction `BETA`. · **Current (verified 2026-11-28, compaction docs):** still BETA, and there are now
> two forms. **On-demand compaction** (`compact-2026-09-04`) is the recommended default, and **threshold compaction**
> (`compact-2026-01-12`) is the original. With either form, append the **full** `response.content` back to history,
> not only the text. Otherwise the compaction state is lost.

### 6. Robust loops

| Rule | Why |
|---|---|
| **Idempotent tools** | The model, the SDK or your job runner may retry. A retried "create ticket" must not create two. Key side effects on the `tool_use.id` or a client-generated idempotency key |
| **Return errors as results** | `{"type": "tool_result", "tool_use_id": …, "content": "Ticket OPS-99 not found", "is_error": true}` lets Claude recover by trying another key or asking the user. An exception kills the loop and loses the turn |
| **Timeouts** | Every tool call has a deadline. A hung tool means a hung agent and a held connection |
| **Iteration cap** | A loop without a cap is a cost incident. When the cap is hit, stop, log it, and return what you have |
| **Log every call** | Tool name, arguments (redacted), duration, result size and error. That's your audit trail and your debugger (M8.3) |

## Under the hood

### The tool loop as a state machine

```
          ┌──────────────── messages.create ────────────────┐
          ▼                                                  │
   [CALL MODEL] ──stop_reason──┬─ end_turn ───────────► [DONE]
                               ├─ max_tokens / refusal ─► [STOP: handle, don't run tools]
                               ├─ pause_turn ─► append assistant turn ─┘ (server tool continues)
                               └─ tool_use ──► [RUN TOOLS] ─► append assistant turn
                                                    │        + ONE user turn of tool_results
                                                    └─ iteration < cap? ─yes─┘   no ─► [STOP: cap hit]
```

### A production-shaped manual loop

```python
import json, logging, time
import anthropic

client = anthropic.Anthropic()
log = logging.getLogger("agent")
MAX_ITERATIONS = 8
TOOL_TIMEOUT_S = 20

def run_tool(name: str, args: dict, tool_use_id: str) -> tuple[str, bool]:
    """Returns (content, is_error). Never raises into the loop."""
    try:
        if name == "get_ticket":
            return json.dumps(jira.get(args["key"], timeout=TOOL_TIMEOUT_S)), False
        if name == "add_comment":
            # Idempotency: the same tool_use_id always maps to the same comment
            jira.add_comment(args["key"], args["body"], idempotency_key=tool_use_id,
                             timeout=TOOL_TIMEOUT_S)
            return "comment added", False
        return f"Unknown tool {name}", True
    except jira.NotFound:
        return f"Ticket {args.get('key')} not found. Check the key with the user.", True
    except TimeoutError:
        return f"{name} timed out after {TOOL_TIMEOUT_S}s; try again later or skip.", True

messages = [{"role": "user", "content": user_request}]
for iteration in range(MAX_ITERATIONS):
    resp = client.messages.create(model="claude-opus-5-5", max_tokens=16000,
                                  tools=tools, messages=messages)
    if resp.stop_reason != "tool_use":
        break                                   # end_turn, max_tokens, refusal, ... handled below
    messages.append({"role": "assistant", "content": resp.content})
    results = []
    for block in (b for b in resp.content if b.type == "tool_use"):
        t0 = time.monotonic()
        content, is_error = run_tool(block.name, block.input, block.id)
        log.info("tool_call", extra={"tool": block.name, "id": block.id, "error": is_error,
                                     "ms": int((time.monotonic() - t0) * 1000)})
        results.append({"type": "tool_result", "tool_use_id": block.id,
                        "content": content, "is_error": is_error})
    messages.append({"role": "user", "content": results})   # all results, one message
else:
    log.warning("iteration_cap_hit", extra={"cap": MAX_ITERATIONS})

if resp.stop_reason in ("max_tokens", "refusal"):
    handle_incomplete(resp)                      # don't present it as a finished answer
```

The SDK also has a **Tool Runner** helper `BETA` (`client.beta.messages.tool_runner`) that drives this loop for you, with
per-turn hooks. Learn the manual loop first, so you know what the runner is doing for you.

### Why errors-as-results beat exceptions

The model can only reason about what's in its context. An exception ends your loop, and the model never learns that
the key was wrong. A `tool_result` with `is_error: true` puts the failure into the context: "not found, check the key".
The model then retries with a corrected argument, picks another path, or asks the user. Failing *inside* the
conversation degrades gracefully. Failing *outside* it is a crash.

## In production

**1. Invoice extraction service.**
*Situation:* 30K supplier invoices a month into the ERP.
*Right move:* a Pydantic model passed to `messages.parse()`, then business validation on top: totals equal the sum of lines, the
VAT ID format is right, the currency is allowed. Run in Batches for the backlog. Anything failing validation goes to a human queue.
*Failure mode:* "reply in JSON" plus `json.loads` on prose, which breaks on the first invoice with a note in the margin.

**2. Ticketing assistant duplicates comments.**
*Situation:* the network blips, the job retries, and the customer sees the same comment three times.
*Right move:* make `add_comment` idempotent, keyed on `tool_use.id`. Log every call.
*Why:* in agent systems retries are normal, so every side effect must tolerate them.

**3. Runaway agent bill.**
*Situation:* the agent loops on a failing tool for 200 iterations overnight.
*Right move:* an iteration cap, per-tool timeouts, `is_error` results with actionable messages, and an alert on cap hits.

**4. Reporting service producing Excel and PowerPoint.**
*Situation:* the finance team wants a monthly branded pack.
*Right move:* the `xlsx` and `pptx` Skills plus a custom Skill carrying the brand template, all in one code-execution container.
Download outputs by file ID. Have a human review before the pack goes out (M8.2).

**5. Security research with web search.**
*Situation:* the agent checks dependencies for CVEs.
*Right move:* restrict `allowed_domains` to primary sources (NVD, vendor advisories), cap `max_uses`, require
citations, and treat fetched pages as untrusted data. They can carry injected instructions.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| Forcing a tool with `tool_choice` `tool`/`any` | 400 on current models | `auto` + `strict` + name the tool in the prompt |
| Parsing JSON out of free text | Breaks on the first unusual input | `output_config.format` / `parse()` |
| Tool results split across several user messages | Teaches Claude to stop parallel calls. Can mismatch IDs | All results in one user message |
| Raising on tool failure | The loop dies and the model never sees the error | `is_error: true` with an actionable message |
| No iteration cap | Infinite loops become cost incidents | Cap, log and alert |
| Non-idempotent side effects | Retries duplicate the actions | Key on `tool_use.id` |
| Trusting schema-valid args as authorised | Strict guarantees shape, not permission | Check authorisation in the tool |
| Bash or text-editor tool on the host with secrets | The model's commands run with your privileges | Sandbox, confined paths, no credentials |
| Appending only text when compaction is on | Compaction state is silently lost | Append the full `response.content` |
| Assessing yourself on BETA features | They change or disappear | Learn the GA forms. Demo BETA ones |

## Hands-on exercises

1. **Typed extraction service** for one document type (an invoice, contract or CV), with a JSON schema and validation.
   **Done when:** outputs come from `parse()` or `output_config.format`; business-rule validation runs on top; `max_tokens`
   and `refusal` are handled; and 20 sample documents produce valid objects, or route to review with a stated reason.
2. **Tool loop over an internal REST API**, with idempotency and an iteration cap.
   **Done when:** a forced retry of a write creates no duplicate; a 404 from the API reaches Claude as `is_error` and Claude
   recovers; hitting the cap logs and stops cleanly; and every call is logged with its duration.
3. **Branded report pack as XLSX and PPTX** through Skills and code execution.
   **Done when:** both files download by file ID, open without repair, and follow the template. You can name the Skills
   attached and why.
4. **Compaction or the memory tool** on a long conversation. Measure the context-size difference.
   **Done when:** you have a table of `usage.input_tokens` per turn with and without the feature over the same 30-turn script,
   plus one paragraph on what was lost or kept. (BETA features: demonstration only.)
