# M1.3 — Interaction patterns, settings and personalisation

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| CORE | All clusters | 1 | M1.1 (ecosystem), M1.2 (models, context, limits) |

**Objective:** configure Claude for your own work and use the conversation controls deliberately, instead
of starting every chat from zero.

> At Foundational you learned what Claude is and how to prompt it. This module is about the controls that
> sit *around* the prompt: what loads into every chat before you type, which branch of a conversation you
> keep, and what persists afterwards. Most "Claude got worse" complaints are really a setting, or a
> polluted conversation, that the user didn't know about.

---

## TL;DR

- **A fresh chat is a fix, not a defeat.** When a chat has drifted, start clean with a short handover.
  Don't argue it back on course for ten more turns.
- **Edit an earlier message to branch.** Edit the turn where things went wrong, regenerate, and compare
  the branches. Every later turn is conditioned on that one.
- **Settings shape every answer before you type:** account Instructions, Style, default model and effort,
  memory, response language, web search and connectors. Set them once, on purpose.
- **"Create and edit files" is the hidden gate** [app]. It enables file creation, Artifacts and Skills.
  When it's off, those features fail silently or are missing.
- **Memory is context you didn't type.** Decide per workstream. Pause it, or use incognito, for client
  material under NDA. Reset it when it has learned the wrong things.
- **Incognito is not invisibility.** It stays out of your history and memory, and it isn't used for
  training. On Team and Enterprise it **still appears in the organisation's data exports**.
- **A thumbs rating is a data-sharing action.** It sends the whole conversation for review and keeps it.
  Don't rate client chats.
- **Have a personal setup checklist, and get it peer-checked** against policy: Instructions, Style, memory
  decision, default model, file creation on, approved connectors only.

## Concepts

> **Status tags in this module.** Only Voice mode carries a BETA tag in the syllabus. Features marked
> "no GA/BETA label" below are generally available on the plans named, but neither the syllabus nor the
> help centre gives them a status tag, so none is invented here. Everything in this module is `[app]`.

### 1. Conversation mechanics

**New chat versus continuing one.** Everything earlier in a chat is re-read on every turn (M1.2). That
is a strength when the history is relevant and a liability when it isn't.

| Continue the chat when… | Start a fresh chat when… |
|---|---|
| The next step builds directly on the last answer | You're switching task, client or audience |
| The context is still accurate | Claude keeps repeating a mistake you've corrected twice |
| You're refining a good draft | Earlier turns contain wrong drafts or a premise you've abandoned |
| | The chat is long and answers are getting generic, or are ignoring earlier instructions |

**"When a fresh chat is the fix":** three corrections in a row that don't stick is the signal. The wrong
drafts and your corrections are now part of the context and keep pulling answers back (M2.3 §4–5).
Write a five-line handover (goal, decisions so far, constraints, current draft, next step) and start clean.

**Editing an earlier message to branch** [app] (GA). Editing a past user message and resending it
creates a **branch**. The conversation after that point is regenerated from the edited message, and the
original branch is kept. You can switch between branches with the arrows on the edited message.
Use it to:
- fix a bad spec at its source, rather than patching it with follow-ups (M2.1 §7);
- **A/B-test a prompt change** on the same history, and compare the branches side by side;
- recover from a wrong turn without losing the good work before it.

**Retrying with a different model** [app]. Regenerating a reply lets you pick a different model for that
retry. That's useful when a cheap model gave a shallow answer, or when you want a second opinion (M8.2).
Judge on the output, not on the model name.

**Chat history search** [app]. Search past chats by keyword. Combined with past-chat search in memory
(§3), Claude itself can also reference earlier chats when that's enabled.

**The "+" menu** [app]. The composer's "+" is where you attach files and photos, add Project knowledge or
Drive files, and turn on tools for this chat: web search, Research, connectors, and Style selection where
it's still offered. If a tool "isn't working", check here first. It is usually not enabled for this chat.

### 2. Settings that change results

Every setting below is input to Claude before your first message. Treat them as part of the prompt you
didn't write.

**Instructions (account-wide)** [app]. Standing preferences applied to every chat: your role, your stack,
the format you like, what to avoid. Org instructions on Team and Enterprise sit above these (M2.3 §2).

> **Syllabus says:** "Instructions for Claude", under Settings → Your Claude · **Current (verified
> 2026-11-28, support.claude.com/en/articles/10185728):** the new layout labels it Settings → **Your
> Claude → Instructions**. The older layout used Settings → Account → "Instructions for Claude". Same
> feature.

Good account Instructions are short, durable and true for *all* your work:

```text
I'm a backend engineer (Go, Postgres, Kubernetes) at a consultancy; much of my work is client code under NDA.
Default to concise, technical answers; use tables for comparisons.
Times in UTC. British English.
When you're unsure or a fact may be out of date, say so explicitly instead of guessing.
For anything involving a version, limit or price, tell me to verify it against the official docs.
```

Keep task-specific rules out of here. They belong in Project instructions (M3.3) or a Skill (M4.2).

**Styles** [app] (being migrated to skills; see the callout below). These control the *voice* of the reply: Normal, Concise, Formal, Explanatory, plus
**custom styles** built by uploading your own writing samples or describing the voice you want.

> **Syllabus says:** Styles: Normal, Concise, Formal, Explanatory, plus custom styles from writing samples ·
> **Current (verified 2026-11-28, support.claude.com/en/articles/10181068, search snippet):** "Styles are
> moving to skills." Concise, Formal and Explanatory are being removed. Custom styles migrate
> automatically to skills (invoked as `/<name>-style`). The styles menu goes away when the migration
> finishes. No completion date is published. **For the exam,** know the four presets and custom
> styles. **At work,** expect your house voice to live in a Skill (M4.2).

The principle survives the change. Put voice in a reusable artefact, not in every prompt. "Consistent
tone across a team" means one shared style or skill, not ten people's adjectives.

**Default model and effort** [app]. Set the model you want most chats to start on, and its effort
level. Raise either one per chat for hard reasoning (M2.2 §2). Don't pay Opus-at-max latency for a
one-line rewrite. The app labels the `xhigh` level "Extra high" (Level 1 fact-status #19).

**"Create and edit files"** [app] (GA). This is the capability toggle that lets Claude run code in a
sandbox to create files (XLSX, DOCX, PPTX, PDF, CSV), build Artifacts, and use Skills.

> **Syllabus says:** the "Create and edit files" setting · **Current (verified 2026-11-28,
> support.claude.com/en/articles/12111783):** the same toggle is labelled **"Code execution and file
> creation"** in the older settings layout, and "Create and edit files" in the updated one (Settings →
> Capabilities; Team and Enterprise: Organisation settings → Capabilities). It's on by default for most
> plans. Network egress from the sandbox is a separate control.

The trap: people are blocked by this setting without knowing it. Claude replies with text instead of a
file, no Skill triggers, or the Artifact options are missing. On Team and Enterprise an **owner** may
have turned it off org-wide, and then you can't fix it yourself. Ask your admin.

**Web search** [app] (available on all plans; no GA/BETA label in the docs; owner-enabled on Team/Enterprise).
- **Team and Enterprise:** an Owner enables it at org level. Then members can use it.
- **Newer experience:** there's no toggle. Claude searches when it judges a search helps.
- Either way, search is **retrieval, not verification** (M3.4). A searched answer still needs its
  sources checked.

**Response language** [app]. Set it explicitly if you work in more than one language. You can also set
it per prompt: "Reply in German; keep code identifiers and log lines in English."

### 3. Memory

**What it is** [app]. Memory lets Claude carry information between chats. It has two mechanisms:

| Mechanism | What it does | Where you see it |
|---|---|---|
| **Memory topics** (per-topic memory) | Claude keeps a summary of durable facts about you and your work, grouped by topic | Settings → "Your memory" → Topics (view and edit) |
| **Search and reference chats** (past-chat search) | Claude can search your earlier chats and pull relevant ones into the current answer | Setting toggle (Pro and above) |

**What it changes about answers.** Remembered facts are added to the context, so answers start assuming
them: your stack, your client's name, last week's decision. That's useful for continuity. It's harmful
when the remembered fact is stale or belongs to a different client.

**Controls** [app] (no GA/BETA label in the docs):
- **Pause memory:** stop using and updating memory without deleting it. Use it for a sensitive stretch of work.
- **Reset memory:** delete it. Reset also deletes project memories.
- **Sensitive-topics opt-in** ("Include sensitive topics in memory"): off unless you opt in, and the
  opt-in is per user (fact-status #5).
- **Project memory:** each Project keeps its own memory space, separate from your other Projects and
  from chats outside Projects. That separation is what makes "one Project per client" work. (Whether a
  Project can also be set to ignore your account-level memory isn't in the sources checked: **unverified**.)
- **Import and export** (experimental): you can bring memory in from another assistant, or export it.
  Treat an import like any other upload. Read it first (M8.1).

**Organisation control** [app]. On Team and Enterprise the **owner** turns memory on or off for the org.
Each user then opts in. Owners can't switch it on for an individual on their behalf, and sensitive topics
always need the user's own opt-in.

> **Syllabus says:** memory is unavailable under HIPAA configurations · **Current (verified 2026-11-28,
> support.claude.com/en/articles/11817273):** in HIPAA organisations memory doesn't start on, and the
> *new* memory experience isn't available with HIPAA or public-sector agreements. That's narrower than a
> blanket ban. Memory is on by default only for orgs created on or after 31 Oct 2026. Check your own org's
> setting rather than assuming either way.

**Rule for client work under NDA:** memory follows *you*, not the engagement. A fact about Client A that
surfaces in a chat about Client B is a confidentiality incident. Keep each client's work in its own
Project (separate project memory), pause memory for general chats that touch client work, or use incognito
for one-off sensitive chats.

### 4. Incognito chats

[app] (GA). Start one with the **ghost icon** (top right of a new chat, outside a Project). An incognito chat:
- is **not saved to your chat history** and **not used for memory**;
- is **never used for training**;
- **is still retained** for a period (30 days by default, longer under Enterprise custom retention), and
  **is included in Team and Enterprise data exports available to Owners.**

**Incognito is not invisibility from your employer.** It keeps the chat out of *your* history and *your*
memory. It doesn't hide the chat from the organisation that administers your seat, and it doesn't
change what you're allowed to paste (M8.1).

**When to use it:**
- sensitive client material where you don't want any trace in memory or history: a one-off analysis of
  a contract under NDA, an HR matter;
- anything you don't want shaping later answers: a "what if" premise, a hostile draft, a test of a bad prompt;
- quick experiments, where a clean context with no memory gives a fair test.

**When not to rely on it:** to "hide" policy-violating use (it doesn't), or for work you'll need again
(it isn't in your history, so you can't come back to it).

### 5. Where output lands

There are three destinations, and the choice depends on what happens to the output next:

| Destination | Use when | Example |
|---|---|---|
| **In the reply** | You'll read it once, or copy a snippet | A regex explanation, a quick answer |
| **As an artifact** (Docs, Slides, Design, code, sites, diagrams…) | Someone will view, iterate on, co-edit or comment on it | A decision brief your lead will comment on |
| **As a downloadable file** (XLSX, DOCX, PPTX, PDF) | It goes into another system, or someone edits it outside Claude | A workbook for finance, a deck for the client's template |

The full treatment, including types, limits and Claude Docs, is **M3.2**. The rule to carry now: *who
edits it next decides.*

### 6. Mobile and voice patterns

- **Voice mode** [app] (BETA, **all plans**): a spoken back-and-forth conversation, best on a phone. **It's not
  available for Fable models.** Good for thinking out loud on a commute, rehearsing an explanation, or
  triaging an idea before you write it up.
- **Camera and photo input** [app]: snap a whiteboard, an error on a screen, or a printed form, and attach it from
  the mobile "+". (The camera inside voice mode is documented only in an older article version, so treat that
  detail as **unverified**.) Vision has limits on small text and exact numbers (M3.2 §2).
- **Dictation** [app]: speech-to-text into the composer on desktop. **It's not available in the Linux desktop app**
  (beta) (code.claude.com/docs/en/desktop-linux).

Engineering habit: voice and photos are capture tools. Whatever you capture still goes through the same
data rules. Don't photograph a client's whiteboard if you couldn't type its contents into Claude.

### 7. Working habits that compound

- **Iterate rather than restart, when the base is good.** Refine with targeted follow-ups ("tighten §2,
  keep the table"). Restart when the *spec* was wrong (§1).
- **Ask for options.** "Give me three approaches with trade-offs" beats one answer you must take or leave.
  It surfaces alternatives you'd have missed, and it makes Claude's assumptions visible.
- **Ask Claude to ask you questions.** "Before you start, ask me up to five questions about anything you'd
  otherwise guess." This turns Claude's guesses into your decisions (M2.2 §7).
- **Feedback inside the chat**, not just in your head. Say what was wrong and why. That fixes this chat.
- **Thumbs ratings are different.** A 👍/👎 **sends the whole conversation to Anthropic for review, and it's
  retained.**

> **Syllabus says:** a thumbs rating sends the conversation for review and is retained; owners can
> disable "Rate chats" · **Current (verified 2026-11-28, privacy.claude.com/en/articles/7996868):**
> confirmed. Rated conversations are stored for **up to 5 years** and may be used for training once
> de-linked from your user ID. Owners control **"Rate chats"** under Organisation settings → Data and Privacy.

  Practical rule: **don't rate chats that contain client or personal data**, whatever your plan's
  training defaults. Rating is an explicit act of sharing.
- **When to abandon a chat and start clean:** repeated ignored instructions, an abandoned premise still
  colouring the answers, a switch of client or task, or a chat so long that answers turn generic.

### 8. Your personal setup checklist

Complete it once, then re-check it each quarter or whenever you join a new engagement. **Have a peer verify it
against your organisation's policy.**

| ✓ | Item | "Done" looks like |
|---|---|---|
| ☐ | **Instructions written** | 5–10 durable lines: role, stack, format, "say when unsure". No client names, no secrets |
| ☐ | **A Style chosen** | A preset or custom style (or its skill successor) matching your normal output. Tested on three real tasks |
| ☐ | **Memory setting decided** | On or off, with a reason. Sensitive topics opt-in decided. One Project per client; general-chat rule for client work written down |
| ☐ | **Default model set** | A sensible default, plus a stated rule for when you raise model or effort |
| ☐ | **File creation on** | "Create and edit files" (or "Code execution and file creation") confirmed on, or an admin ticket raised |
| ☐ | **Only approved connectors enabled** | Every connector is on the org's approved list. Personal connectors are off for client work |

## Under the hood

### What loads before your first word

Every chat starts with a context Claude assembles from several sources. In rough order of breadth:

```text
┌─ Anthropic system prompt (product behaviour, tools available)
├─ Organisation instructions / admin settings (Team, Enterprise)
├─ Project instructions + Project knowledge (if in a Project)
├─ Your account Instructions + Style (or style skill)
├─ Memory: topic summaries, plus any past chats pulled in by search
├─ Connector / tool results fetched during the chat
└─ The conversation so far → your new message
```

You only see the bottom line. A surprising answer often comes from a higher layer: a stale memory topic, a
Style that forces brevity, a Project instruction written months ago. Debugging order: **check the layers
before rewriting the prompt.** The precedence rules between layers are M2.3 §2.

### Why branching beats correcting

A model's next reply is conditioned on everything in the context. Correcting by follow-up *adds* tokens:
the wrong draft stays, and your correction sits beside it. Branching *replaces* tokens: the wrong draft
never exists in the new branch. That's the same context-pollution mechanism as M2.1 §7, applied to
navigation.

### Why memory changes answers even when you don't mention it

Memory content is inserted as context, and the model uses relevant context. If memory says "works on the
Contoso migration", a vague question about "the migration" is resolved to Contoso. That's helpful when it's
right, and a leak when you're now working for Fabrikam. Past-chat search works like retrieval: it pulls in
whatever earlier chats score as relevant, which may be a different client's.

### Incognito and exports: two different stores

Your personal history and memory are one store. The organisation's retention and export system is
another. Incognito opts the chat out of the first, not the second. The same split explains why deleting a
chat from your sidebar is not the same as the org deleting its records.

### Why a long chat drifts

Instructions given at turn 3 are a small fraction of the context by turn 60, and they compete with
everything since. The model hasn't "forgotten" in a human sense. Its attention is spread across a much
larger, noisier context, and recent turns dominate. The fix is structural: a fresh chat with a handover
(M2.3 §4), not louder instructions.

## In production

**1. Client work under NDA, two clients in one week**
*Situation:* You support Contoso on Monday and Fabrikam on Tuesday, on the same seat, with memory on.
*Right move:* Make one Project per client and keep that client's work inside it (each Project's memory is
separate). Never discuss a client outside its Project. Pause memory if you must work in general chats.
*Why:* memory follows the user, not the engagement. Project scoping and memory isolation keep each
client's facts in its own box.
*Failure mode:* Tuesday's answer mentions "the Contoso cut-over plan" in a Fabrikam draft.

**2. The vanishing PPTX**
*Situation:* A teammate asks Claude for "a 6-slide deck as PPTX" and gets slide text in Markdown.
They retry three times.
*Right move:* Check "Create and edit files". It's off, maybe org-wide. Turn it on, or raise an admin ticket.
*Why:* file creation, Artifacts and Skills all depend on that sandbox. Without it Claude can only reply in text.
*Failure mode:* blaming the model or the prompt, and losing an hour.

**3. A design review that went sideways**
*Situation:* At turn 4 of a design chat you asserted "we must stay on MySQL". By turn 20 you've dropped
that constraint, but every answer still works around MySQL.
*Right move:* Edit the turn-4 message to remove the constraint and regenerate. Compare the two branches'
proposals side by side.
*Why:* the constraint is baked into 16 turns of context. Editing it out at the source is cheaper and
cleaner than arguing.

**4. Sensitive HR question from a lead**
*Situation:* A tech lead wants help wording a performance conversation and opens an incognito chat
"so nobody sees it".
*Right move:* Incognito is right for keeping it out of memory and history. But tell them the org can still
export it, and that personal data rules still apply. Anonymise the person ("engineer A").
*Failure mode:* treating incognito as a privacy guarantee against the employer.

**5. Consistent tone for a support rotation**
*Situation:* Five engineers write customer-facing incident updates in five different voices.
*Right move:* Build one custom style (or a style skill) from three approved past updates, and share it
(M4.2). Each engineer adds it. Their account Instructions stay personal.
*Why:* voice is a shared, versioned artefact, not five sets of adjectives.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| Ten follow-ups to fix one bad premise | The wrong drafts stay in context and keep pulling answers back | Edit the original turn (branch), or start fresh with a handover |
| Client names and project details in account Instructions | They apply to *every* chat, including other clients' | Keep Instructions generic; put client context in that client's Project |
| Memory on, multiple clients, no Projects | Cross-client recall becomes a confidentiality incident | One Project per client (separate memory); pause memory or use incognito outside them |
| "Incognito, so the company can't see it" | Team and Enterprise exports still include it | Treat incognito as history and memory hygiene, not secrecy |
| Rating client chats 👎 to "help improve Claude" | Sends and retains the whole conversation for review | Give feedback in the chat. Rate only chats with no client or personal data |
| "Claude can't make files" | Usually "Create and edit files" is off, possibly at org level | Check the capability toggle first; then ask the admin |
| Using Opus at max effort for everything | Slow and costly, with no gain on simple tasks | A sensible default model, raised per chat for hard problems |
| Enabling every connector "in case" | More data in reach, more injection surface, possible policy breach | Only approved connectors, only those the work needs |

## Hands-on exercises

1. **Instructions and a Style.** Write your Instructions (≤10 lines) and build a custom Style from three
   samples of your own writing (or the style-skill equivalent, if your account has migrated). Run three real
   tasks with and without them.
   **Done when:** for all three tasks you can point to a concrete difference the setup made (format, tone,
   a "not sure" flag), and the Instructions contain no client names or secrets.
2. **Memory drill.** Run a sensitive-work scenario (synthetic client contract) in incognito, and an
   ordinary task with memory on. Afterwards inspect history and the memory Topics.
   **Done when:** you can show what persisted in each case (history entry, memory topic, nothing), and you can
   explain in two sentences why the incognito chat would still appear in a Team or Enterprise export.
3. **Branch and compare.** In an existing chat, edit an earlier turn to change one constraint, and regenerate.
   **Done when:** you've written a three-line judgement of which branch is better *and why*, citing the
   specific turn that made the difference.
4. **Setup checklist.** Complete the §8 checklist and have a peer verify it against your organisation's AI
   policy and approved-connector list.
   **Done when:** every row is ticked or has a written exception, and the peer has signed it.
