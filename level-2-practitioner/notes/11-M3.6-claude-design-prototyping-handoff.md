# M3.6 — Design, prototyping and handoff with Claude Design

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| ELECTIVE | Cluster G; frontend and mobile engineers in A; F (clusters are **undefined in source**) | 1.5 | M3.2 |

**Objective:** take an idea from **brief → prototype → code** without losing fidelity at each handoff.

> Every handoff in a design-to-engineering pipeline is a lossy compression step. Brief to mock-up loses
> intent. Mock-up to screenshot loses structure. Screenshot to code loses tokens, states and spacing.
> This module is about handing over the *design itself*, never a picture of it.

---

## TL;DR

- **Claude Design** [app] makes designs, prototypes and one-pagers. It's on by default on every plan
  (Free→Enterprise). The source page shows **no GA/BETA label**, so treat specifics as volatile.
- The **standalone claude.ai/design site closes on 14 December 2026.** Move design systems into Claude
  before then. **Put it on the project calendar.**
- **Specify up front:** audience, platform, constraints and brand. Then iterate in conversation with *written*
  feedback.
- **Import the design system** so output matches house tokens and components. Know who owns it.
- **Choose the export by what the recipient does next:** edit it in a tool, present it, host it, or build from it.
- **Hand off the design, not a PNG.** A handoff to Claude Code (local or on the web) continues from the existing
  work. A screenshot makes the developer reverse-engineer it.
- **Review before handoff:** a heuristic evaluation (Nielsen's 10), WCAG 2.2 AA contrast (4.5:1 for text,
  3:1 for large text and UI components), and UX copy in brand voice.
- A **handoff note** lists what the developer still has to decide. Those are the things no design file carries.

### 2. Working from a brief

Turn a written brief into a first design, then iterate in conversation. The brief does the same job as a
good prompt (M2.1): Claude fills every gap you leave with a plausible guess.

**Specify up front:**

| Element | Why it matters | Example |
|---|---|---|
| **Audience** | It drives density, vocabulary and the emphasis on actions | "Dispatch supervisors on a 24" monitor, 8-hour shifts" |
| **Platform** | Layout, input model and conventions | "iOS app, iPhone 15 and up; one-handed use" |
| **Constraints** | It stops designs that can't ship | "Must work offline; WCAG 2.2 AA; no custom fonts" |
| **Brand** | Matches the house style before the design system is applied | "Northwind design system; calm, utilitarian tone" |
| **Goal and success** | What the user must achieve, and how you'll judge it | "Reassign a delayed shipment in ≤3 taps" |

**Brief template**

```text
Product / feature:   <one line>
Users and context:   <who, where, device, frequency>
Platform:            <web / iOS / Android / responsive breakpoints>
Primary task:        <the one job this screen set must make easy>
Screens:             <list, in flow order>
Constraints:         <accessibility level, tech limits, content limits, legal>
Brand / system:      <design system name, or "none — neutral">
Out of scope:        <what not to design>
Review criteria:     <how we will judge the first draft>
```

**Iterating by conversation:** give feedback as specific, testable changes ("move the primary action
above the fold on 390 px width; make 'Reassign' the only filled button"), not reactions ("make it pop").
Each round should resolve named issues. If you're on round five with vague feedback, the brief is the problem.

### 5. The brief → prototype → code handoff

- **Handing a finished design to a local Claude Code agent, or to Claude Code on the web** [app][code]
  ("Send to local coding agent" / "Send to Claude Code Web").
- **The handoff continues from the existing work rather than restarting from a screenshot.** That's the
  whole point, and the reason not to hand over a PNG. The coding agent receives the design's structure
  (components, tokens, layout, copy) and builds from it, rather than guessing from pixels.
- **From Claude Code, `/design`** [code] imports a design into the codebase, exports code as a live
  prototype, or has Claude build it.

> **Current (verified 2026-11-28, code.claude.com/docs/en/commands):** `/design [brief]` is a bundled skill.
> It needs Claude Code v2.1.265 or later, artifacts available, and the Design template enabled. It runs on
> the **Anthropic API only** (not Bedrock, Agent Platform, Foundry or Claude Platform on AWS). On a cloud
> route, plan the handoff another way.

**What survives the handoff, and what doesn't:**

| Survives | Doesn't survive. The developer still decides |
|---|---|
| Layout, hierarchy, spacing (as tokens if the design system was applied) | Data model, API contracts, where state lives |
| Components and their visual states that were designed | States nobody designed: loading, empty, error, partial, offline |
| Copy and microcopy | Validation rules and error-message logic |
| Colours and type from the design system | Performance budgets, image sizes, lazy loading |
| The flow between designed screens | Auth, permissions, analytics events, feature flags |
| Responsive variants that were actually designed | Breakpoints that weren't designed, RTL and localisation expansion |

The handoff note (chapter 7) exists to cover the right-hand column.

### 7. Review and accessibility

**Heuristic evaluation of a screen set.** Ask Claude to evaluate against Nielsen's 10 heuristics, citing the
screen and element for every finding. Then *you* check each finding on the screen. Vision misreads
small text and exact measurements (M3.2), and a heuristic finding about a misread element is noise.

| # | Heuristic (Nielsen) | Typical finding |
|---|---|---|
| 1 | Visibility of system status | No progress indicator on the "Reassign" submit |
| 2 | Match between system and the real world | Uses "Consignment ID"; dispatchers say "load number" |
| 3 | User control and freedom | No undo after bulk reassignment |
| 4 | Consistency and standards | Two different date formats across screens |
| 5 | Error prevention | Destructive "Cancel shipment" next to "Save", same style |
| 6 | Recognition rather than recall | Driver picker needs the ID typed from memory |
| 7 | Flexibility and efficiency of use | No keyboard shortcuts for a power-user screen |
| 8 | Aesthetic and minimalist design | Six equal-weight buttons; no primary action |
| 9 | Help users recognise, diagnose, recover from errors | "Error 422" shown raw |
| 10 | Help and documentation | No inline help for the SLA field |

**WCAG review of flows and contrast** (WCAG 2.2 level AA, the usual contractual target):

| Check | AA requirement |
|---|---|
| Text contrast | **4.5:1** for normal text; **3:1** for large text (≥24 px regular or ≥18.66 px bold) |
| Non-text contrast | **3:1** for UI components (input borders, icons that convey meaning) and focus indicators |
| Colour alone | Never the only way to convey status (pair red/green with an icon or text) |
| Target size (2.2) | Pointer targets at least 24×24 CSS px, or spaced so they don't overlap |
| Focus | Visible and not obscured; logical tab order through the flow |
| Labels | Every input has a programmatic label, not just placeholder text |

Compute contrast ratios with a contrast checker on the **actual token values**, never from Claude's visual
estimate of a screenshot. "Approximately 4.5:1" is a fail when the real value is 4.4:1. This is the M3.2
rule: where approximately right is wrong, measure.

**UX copy and microcopy in brand voice:** buttons as verbs ("Reassign load", not "Submit"), error messages
that say what happened and what to do, empty states that point to the first action. Give Claude the voice
guide as a resource, or make it a Skill (M4.2).

**Handoff notes a developer can actually implement from.** Template:

```markdown
## Handoff: <feature>, <date>, design owner <name>

**Design link:** <Claude Design artifact / handed off to Claude Code session>
**Design system:** <name + version>; deviations: <list or "none">
**Screens and flow:** <list, entry points, exit points>
**States designed:** default, loading, empty, error (per screen; note any missing)
**Behaviour not visible in the design:**
- Validation: <rules>
- Errors: <API failure → message + action>
- Responsiveness: <breakpoints designed; behaviour between>
**Accessibility:** contrast verified on tokens (tool + date); focus order; labels; target sizes
**Copy:** final / placeholder (mark placeholders)
**Open decisions for engineering:** <data, state, analytics, flags — the right-hand column>
**Review record:** heuristic review <date, reviewer>; stakeholder sign-off <name, date>
```

## Under the hood

### What a design-system import actually carries

A design system isn't a style guide PDF. It's structured data:

```text
Design tokens        color.primary.600 = #0B4A6E    space.4 = 16px    radius.md = 6px
                     font.body = "IBM Plex Sans" 16/24
Components           Button {variant: primary|secondary|danger, size: sm|md, state: default|hover|disabled|loading}
                     TextField {label, helper, error, required}
Patterns / rules     "One primary button per view"  "Danger actions require confirmation"
```

When the system is imported, Claude composes screens from **named components with token values**, not
from approximate hex codes and pixel guesses. That's what makes the later code handoff faithful. The coding
agent can map `Button variant=primary` to the codebase's actual `<Button variant="primary">`, rather than
recreating a blue rectangle.

### Why a PNG handoff loses structure

A screenshot is a grid of pixels. To rebuild from it, the receiver (human or model) has to **infer**:

- which elements are the same component (two similar buttons: same component, or a one-off?);
- the token behind each colour (is `#0C4B6F` meant to be `primary.600`, or a new colour?);
- the spacing scale (is that 15 px or 16 px, and is it `space.4`?);
- every state not in the picture (hover, disabled, error).

Every inference is a chance for drift, and vision is weakest at exactly these: small text, exact sizes,
near-identical colours (M3.2). A handoff that carries the design keeps the structure explicit, so the
inferences never happen. That's why "send the PNG" is the anti-pattern this module exists to remove.

### Where fidelity is lost, and the counter

```text
brief ──(1)──▶ design ──(2)──▶ prototype ──(3)──▶ code
 (1) intent lost       → brief template; written review criteria
 (2) structure lost    → design system imported before iterating
 (3) states/logic lost → handoff of the design (not PNG) + handoff note's open-decisions list
```

## In production

**1. Client concept pitch on a deadline**
*Situation:* Pre-sales needs three screens of a mobile concept for a client pitch on Thursday.
*Right move:* Write the brief template (audience, platform, primary task, brand). Generate, then iterate
twice with written, specific feedback. Export as PPTX for the pitch deck and send a hosted HTML link for the
client to tap through.
*Why:* the export follows what the recipient does: present, then click.
*Failure mode:* exporting a PDF of a clickable prototype. The interaction is the selling point, and it's gone.

**2. Design-to-dev handoff mid-sprint**
*Situation:* A designer finishes a three-screen flow. The developer asks for "screenshots in the ticket".
*Right move:* Send the design to Claude Code (local or web) and attach the handoff note. The
developer builds from the design. The note lists undesigned states and open decisions.
*Why:* the handoff continues the existing work. Structure, tokens and copy survive.
*Failure mode:* PNGs in Jira. The developer re-traces spacing by eye, invents the error state, and QA
finds 14 visual diffs.

**3. The design-system migration deadline**
*Situation:* A client's design system lives only on the standalone design site. It's late November.
*Right move:* Raise it as a dated risk in the engagement Project (M3.3), assign the design-system owner, and
migrate before 14 December 2026. Verify the migrated system against a known screen.
*Failure mode:* discovering on 15 December that the house style is gone, mid-deliverable.

**4. Accessibility review that would have shipped a fail**
*Situation:* Claude's review of a screenshot says the grey helper text "appears to meet 4.5:1".
*Right move:* Take the token values (`#8A949C` on `#FFFFFF`) and compute the ratio with a checker. It's
3.09:1: a fail for normal text, and only just above the 3:1 large-text line. Fix the token, not the one screen.
*Why:* a visual estimate is approximately right, and for contrast approximately right is wrong.

**5. Internal tool mock-up with an executive one-pager**
*Situation:* An ops lead wants a mock-up of an internal triage tool and a one-pager to get funding.
*Right move:* A prototype artifact for the ops team to click through, and a one-pager exported as PDF for the
executive. Note that an AI-powered prototype runs on each viewer's own usage.
*Failure mode:* one artifact trying to be both. The exec gets a tool they can't read in 60 seconds.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| "Design me a dashboard" with no brief | Claude fills audience, platform and constraints with guesses | Use the brief template |
| Iterating with "make it pop" | Untestable feedback leads to endless rounds | Specific, checkable changes per round |
| Designing before importing the design system | Every screen needs re-skinning, and tokens drift | Import first, then iterate |
| Importing a design system without knowing its owner | A stale copy becomes the house style | Confirm the owner and canonical source |
| Handing over PNGs | Structure, tokens and states are lost. The developer reverse-engineers | Send the design to Claude Code, plus a handoff note |
| Exporting by habit (always PDF) | Interaction or editability lost | Choose by what the recipient does next |
| Trusting a visual contrast estimate | Near-threshold values fail | Compute ratios on token values |
| A handoff note listing only what's designed | Missing states get invented in code | List undesigned states and open decisions |
| Ignoring the 14 Dec 2026 closure | The design system becomes unavailable mid-project | Calendar it and migrate early |

## Hands-on exercises

1. **From a one-paragraph brief, produce a three-screen prototype**, then iterate it twice against written
   feedback.
   **Done when:** you have the brief (template filled), the three versions, and for each round a list of
   the specific changes requested and whether each one landed.
2. **Import a design system** and show the same design before and after it's applied.
   **Done when:** you can point to at least five elements that changed to house tokens or components, and you
   name the design-system owner and source you imported from.
3. **Hand a design to Claude Code and build one screen.** Report what the handoff preserved and what you
   had to specify again.
   **Done when:** you have a two-column table (preserved / re-specified) with at least four rows each, and
   the built screen runs.
4. **Run a heuristic and accessibility review** on a provided screen set, and produce the revised copy plus
   a handoff note.
   **Done when:** every finding cites a screen and element and is checked by you on the actual screen,
   every contrast claim is computed from token values, and the handoff note uses the template with "open
   decisions" filled in.
