# M3.5 — Spreadsheet and data analysis

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| CORE | All clusters | 1.5 | M3.2 (documents, files, images and Artifacts) |

**Objective:** analyse tabular data correctly, and present results a reviewer can recompute.

> A number in a report is a claim. At Practitioner level, every number you ship comes with a way to
> reproduce it: the code that computed it, the cells behind it, and the caveats on the data it came from.
> If a reviewer can't recompute it, it isn't finished.

---

## TL;DR

- **Describe the data before you ask about it**, and ask for **profiling first**: columns, types, missing
  values, duplicates, outliers. Most wrong answers come from data nobody looked at.
- **Make Claude compute with code, not estimate in prose.** This is the single most important habit in the
  module. "Roughly 3.1 hours" is a guess. A figure printed by executed pandas code is a computation.
- **Read the generated code, and recompute the key figure independently** in a second tool (Excel, Sheets, SQL).
  Code that runs can still compute the wrong thing.
- In spreadsheets, use the **Excel add-in** [app] or the **Google Sheets connector** [app] to explain, repair and
  clean formulas in place. Generate XLSX when the reader works offline.
- **Choose the chart from the question.** Be honest: zero baselines for bars, units on axes, no truncation to
  make a point.
- **Anonymise before upload.** Aggregates are usually fine. Row-level personal data and client financials follow M8.1.
- Every report states its **assumptions and data-quality caveats with counts** ("41 duplicate rows removed").

## Concepts

### 1. Data in, questions out

**Uploading CSV and XLSX** [app] GA. Both are accepted, and the app limits from M3.2 apply (500 MB per file,
20 files per chat). XLSX keeps sheets, so tell Claude which sheet and range holds the data.

**Describe the data before asking about it.** Two lines of context prevent most misreadings:

```text
<about_the_data>
tickets_2026.csv — one row per support ticket, exported from Zendesk on 2026-11-20.
created_at / resolved_at are UTC. priority is P1–P4. resolved_at is blank for open tickets.
"Resolution time" = resolved_at − created_at in wall-clock hours (not business hours).
</about_the_data>
```

**Ask for profiling first**, as its own step, and before any business question:

```text
Profile this dataset before any analysis. Using code, report:
1. Row and column count; each column's inferred type and 3 example values.
2. Missing values per column (count and %).
3. Exact duplicate rows, and duplicates on the key column(s) ticket_id.
4. Numeric columns: min, max, mean, median; flag negative or impossible values.
5. Categorical columns: distinct values and counts (flag typos/variants like "P1"/"p1"/"Priority 1").
6. Date columns: range, and any values outside 2026.
Do not answer business questions yet. End with a list of data-quality issues and proposed fixes.
```

Profiling turns hidden problems into a list you decide on. That matters because every later number inherits them.

### 2. Computation versus estimation

**Make Claude compute with code rather than estimate in prose.** When Claude has a code-execution sandbox [app]
(enabled by the "Create and edit files" setting, M1.3), it can load the file and calculate. Without that instruction
it may read a sample of rows and **estimate**. The estimate comes out fluent and plausible, and you can't recompute it.

| Estimation (reject) | Computation (accept) |
|---|---|
| "Average P1 resolution is roughly 3 hours" | `df[df.priority=="P1"].res_hours.mean()` → `3.14`, with the code shown |
| "P1 is clearly getting worse, up ~40%" | A table of quarterly means and medians with n per quarter, and the % change computed |
| No mention of excluded rows | "Excluded 212 open tickets (blank resolved_at)" |

Prompt pattern: *"Compute every figure with code. Show the code and the printed output. Don't state a number that
the code didn't print."*

**Reading the generated code.** You don't need to be a pandas expert, but check these five things:

1. **Filters:** the right rows? (P1 only? This quarter only? Open tickets excluded?)
2. **Joins:** a merge that duplicates rows inflates every sum after it.
3. **Units:** hours versus minutes, USD versus EUR, thousands versus units.
4. **Aggregation:** a mean where a median is honest (skewed data), or a sum of averages.
5. **Silent drops:** `dropna()`, `errors="coerce"` and inner joins all remove rows without saying so.

**Recompute the key figure independently.** Take the one number the decision rests on and reproduce it in a
different tool: a pivot table in Excel, a `SUMIFS` in Sheets, or a SQL query on the source. If they disagree, the
difference *is* the finding: a filter, a unit or a duplicate.

### 3. Working in spreadsheets

> **Syllabus says:** the Excel add-in (PLAN: Pro and above) for formulas, cleaning and explanation. ·
> **Current (verified 2026-11-14, claude.com/docs/office-agents/excel):** GA on Pro, Max, Team and Enterprise.
> The plan gating matches the syllabus.

- **Excel add-in** [app] PLAN: works inside the live workbook. Ask it to explain a formula, find why a total is off,
  clean a column or build a pivot. Each write is a change you approve (M3.2 §6).
- **Google Sheets connector** [app]: the same idea for Sheets, with live editing on the open file.
- **Generating XLSX** [app]: Claude builds a workbook in the sandbox. Ask for **live formulas, not pasted values**
  (`=SUMIFS(...)`, not `41,230`), so the reader can trace and recompute.
- **Formula explanation and repair:** "Explain this formula as a sentence, then tell me which ranges it depends on."
  For repair: "List every cell returning an error, the cause, and the proposed formula. Don't write yet."
  Then approve fixes one at a time.

Common repairs: `#REF!` after a deleted column, `VLOOKUP` with approximate match by accident (missing `FALSE`/`0`),
absolute/relative reference errors when filling down, text-formatted numbers that `SUM` ignores.

### 4. Charts and dashboards

**Choose a chart that matches the question:**

| Question | Chart | Avoid |
|---|---|---|
| Compare categories (cost per service) | Bar (horizontal if labels are long) | Pie with more than 5 slices |
| Change over time (weekly tickets) | Line | Bars for 50 time points |
| Part of a whole, few parts | Stacked bar or a single pie | 3D anything |
| Distribution (resolution times) | Histogram or box plot | A mean-only bar that hides the skew |
| Relationship (load vs latency) | Scatter | Two lines with two y-axes |

> **Syllabus says:** Dashboards artifacts (BETA, Pro and above). · **Current (verified 2026-11-28,
> support.claude.com/en/articles/17454700 and /17153992):** Dashboards has been **renamed "Claude Data"** and is
> **GA on Pro and above**. Certified queries and live sharing are still BETA. A **Sheets** artifact template is new (BETA,
> Pro and above). For the exam, answer the syllabus version. At work, use "Claude Data".

**Chart honesty checklist:** run it on every chart before it ships.

- [ ] **Bar charts start at zero.** A truncated bar axis exaggerates differences. (Line charts may zoom, but label it.)
- [ ] **Units on every axis** ("hours", "USD thousands"), plus the time zone for time axes.
- [ ] **Same scale** when charts sit side by side for comparison.
- [ ] **n shown**, or available, for each bar or point when groups differ in size.
- [ ] **No cherry-picked window.** The time range is stated and justified.
- [ ] **Exclusions stated** in the caption ("open tickets excluded, n=212").
- [ ] **The title states the question**, not the conclusion you hoped for.

### 5. Data hygiene and privacy

- **Anonymise before upload** (M8.1): drop or hash direct identifiers (names, emails, phone numbers, account IDs)
  that the question doesn't need. Bucket quasi-identifiers (exact DOB → age band; full postcode → district).
  Do it in your own tool *before* the file goes anywhere.
- **Aggregate versus row-level personal data:** "tickets per priority per week" is aggregate and usually safe.
  "Every ticket with customer email" is row-level personal data and needs a lawful, approved purpose. Ask:
  *does the question need rows, or only counts?*
- **Client financials** (M8.1): treat them as confidential client data. Use only an approved plan and surface,
  minimise the columns, and never use personal accounts. If the contract restricts AI processing, the restriction
  wins (M8.3).

### 6. Reporting

**Variance explanations.** Show actual against plan, the delta and the % delta, then the drivers *with their size*:

> Cloud spend was **$48.2k against a $41.0k plan (+$7.2k, +17.6%)**. Two drivers account for $6.5k of the $7.2k:
> log ingest rose 2.1 TB after verbose logging stayed on following the 3 Nov incident (+$4.1k), and the new
> staging cluster ran 24/7 instead of business hours (+$2.4k). The remaining $0.7k is spread across 11
> services, none above $150. *Data: billing export of 25 Nov; EUR line items converted at 1.07 USD/EUR.*

**Narrative from numbers:** lead with the answer and the size of the effect, then the evidence. Every sentence
with a number traces to a computed cell.

**State assumptions and data-quality caveats.** A report without them implies the data was clean. Data-quality
report template:

```markdown
## Data-quality report — <dataset>, <date>
**Source:** <system, export date, who exported it> · **Rows in / rows used:** 5,200 / 5,103
| Issue | Rows affected | Action | Effect on results |
|---|---|---|---|
| Exact duplicate rows (March re-send) | 41 | Removed | Totals −0.8% |
| Negative ingest values | 3 | Set to null, excluded from means | Negligible |
| One service billed in EUR | 365 | Converted at 1.07 (ECB, 2026-11-20) | +$2.1k vs naive sum |
| Missing resolved_at (open tickets) | 212 | Excluded from resolution time | Resolution stats cover closed tickets only |
**Assumptions:** <FX rate, growth rate, business vs wall-clock hours> · **Recomputed by:** <name>, in <tool>
```

## Under the hood

### Where the computation actually happens

When code execution is on, Claude writes code, a **sandbox** runs it against your uploaded file, and the printed
output comes back into the context. Claude then writes prose *about* that output.

```text
your CSV ─► sandbox filesystem ─► Python (pandas) runs ─► stdout / charts / XLSX
                                         ▲                        │
                          code written by Claude ◄── context ◄────┘
```

Three consequences:

1. **Figures from executed code are deterministic and recomputable.** The same code on the same file gives the same
   number, and you can rerun it yourself.
2. **The prose layer can still drift.** Claude may round, mislabel or misquote a number when it writes the summary.
   Check that numbers in the narrative match the printed output.
3. **Without execution, it's all prose.** If the setting is off, or the model wasn't told to compute, the model reasons
   over whatever part of the file is in context and *predicts* figures. A large CSV may not even fit fully in context
   as text. Code reads every row. Eyeballing does not.

### What a good generated analysis looks like

```python
import pandas as pd

df = pd.read_csv("tickets_2026.csv", parse_dates=["created_at", "resolved_at"])
n_raw = len(df)
df = df.drop_duplicates(subset="ticket_id")
n_dupes = n_raw - len(df)

df["priority"] = df["priority"].str.upper().str.strip()   # "p1 " -> "P1"
closed = df.dropna(subset=["resolved_at"])
n_open = len(df) - len(closed)

closed = closed.assign(res_hours=(closed.resolved_at - closed.created_at).dt.total_seconds() / 3600,
                       quarter=closed.created_at.dt.to_period("Q"))
bad = closed[closed.res_hours < 0]                          # resolved before created?
closed = closed[closed.res_hours >= 0]

summary = (closed.groupby(["priority", "quarter"])["res_hours"]
           .agg(n="count", mean="mean", median="median").round(2))
print(f"rows={n_raw} dupes_removed={n_dupes} open_excluded={n_open} negative_excluded={len(bad)}")
print(summary.loc["P1"])

# Recompute check: one figure, a second way, must match
p1_q3 = closed[(closed.priority == "P1") & (closed.quarter == "2026Q3")].res_hours
assert abs(p1_q3.mean() - summary.loc[("P1", "2026Q3"), "mean"]) < 0.01
```

What to notice: every exclusion is **counted and printed**, the median sits beside the mean (resolution times are
skewed), and the key figure is computed a second way. The real independent check is still a different *tool*,
because the same author's code can share the same wrong filter. The in-code assert only catches mechanical slips.

### Why a median beside the mean

Operational durations are right-skewed: most tickets close fast and a few take weeks. One 400-hour outlier moves the mean
of 50 P1 tickets by 8 hours. If the mean and median diverge sharply, report both and look at the outliers before you claim a
trend. A "40% worse" P1 mean may be one ticket.

## In production

**1. Utilisation analysis for the delivery lead**
*Situation:* A timesheet export (6 months, 40 people) and a question: "Who's over-allocated?"
*Right move:* Anonymise names to IDs if the question allows it. Profile first (public holidays, partial-month joiners).
Compute utilisation with code against *available* hours. Recompute two people in Excel.
*Failure mode:* utilisation based on 40 h/week for part-timers, which flags the wrong people as "under-utilised".

**2. Budget variance for the monthly review**
*Situation:* Actuals against plan across 30 cost centres. The finance partner wants the story.
*Right move:* Compute the variance table with code. Ask for drivers above a threshold (>$1k or >10%), sized. Have the
narrative cite the table. Recompute the top-line variance in the source workbook.
*Failure mode:* a fluent narrative naming a "driver" that the numbers don't show.

**3. Test-result trend for a release go/no-go**
*Situation:* 12 weeks of CI results. Is flakiness rising?
*Right move:* Define flaky first ("failed then passed on retry, same commit"). Compute weekly rates with n per week.
Chart a line with a zero baseline.
*Failure mode:* "failure rate" mixing genuine failures with flakes, so the decision rests on the wrong metric.

**4. Support-ticket trends for the ops review**
*Situation:* 4,800 tickets, and the director wants "is P1 getting worse?"
*Right move:* Profile, then compute the mean and median by quarter with n, and caveat the exclusions. Make an honest chart.
*Failure mode:* the Pair 2 pattern in the prompt-and-output review: prose estimates and a truncated axis.

**5. Pipeline summary from a CRM export with client names**
*Situation:* Sales asks for a pipeline summary. The export includes contact names, emails and deal notes.
*Right move:* Drop contacts and notes before upload. The question needs stage, value, close date and owner. Aggregate.
*Failure mode:* uploading the full export "because it's easier". That's personal data and client confidences in a
place the question never needed them.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| Asking the business question first | Data issues silently shape the answer | Profile first, as its own step |
| Accepting "roughly", "≈" or "about" figures | Estimated in prose; not recomputable | "Compute with code; show the code and output" |
| Not reading the code | Wrong filter, join or unit goes unnoticed | Check filters, joins, units, aggregation, drops |
| Recomputing in the same chat | Same assumptions, same error | A second tool, independently |
| Mean only for durations or costs | Skew and outliers distort it | Mean and median, with n |
| Truncated bar axis | Exaggerates change; misleads the decision | Zero baseline; units; state exclusions |
| Pasted values in a generated workbook | The reader can't trace or recompute | Live formulas |
| Uploading row-level personal data for an aggregate question | Unnecessary exposure (M8.1) | Minimise or aggregate before upload |
| Silent exclusions | The reader assumes complete data | Count and state every exclusion |

## Hands-on exercises

1. **Profile and clean.** Take a messy 5,000-row CSV, profile it, clean it and produce a data-quality report (template above).
   **Done when:** every issue has a row count, an action and an effect on results, and someone else can rerun your
   cleaning code to reach the same row count.
2. **Answer and recompute.** Answer five business questions on the dataset with code, then recompute each one in Excel or Sheets.
   **Done when:** a table lists each question, Claude's figure, your recomputed figure, and the cause of any discrepancy.
3. **Charts and narrative.** Build a Claude Data (formerly Dashboards) artifact or a chart set, and write the narrative.
   **Done when:** every chart passes the honesty checklist and every number in the narrative traces to a computed cell.
4. **Workbook repair.** Repair a broken workbook and explain every change.
   **Done when:** a change log lists each cell, the old and new formula and the reason, and the workbook's control totals
   match an independent calculation.
