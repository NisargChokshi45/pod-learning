# M2.2 — Reasoning guidance and advanced prompting

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| CORE | All clusters | 1.5 | M2.1 Prompting fundamentals (Level 1) |

**Objective:** get dependable results on **complex, multi-constraint and multi-step** tasks, not just on
easy ones.

> M2.1 taught you to write a good spec. This module is about tasks where a good spec isn't enough: the
> answer depends on reasoning across many facts, the constraints pull against each other, or the work has
> to be split into steps. The skill is choosing **how much reasoning to buy** and **where to put the checks**.

---

## TL;DR

- **Match technique to task type.** Lookup and transformation need a clear prompt and low effort. Analysis
  and open-ended reasoning justify higher effort, decomposition and a verification step. Spending more on
  every task is a cost and latency bug.
- **Thinking is the model's own reasoning budget, controlled by effort.** Raise effort when the task is hard,
  not when the prompt is vague. On thinking-on models, "think step by step" is mostly redundant. Ask instead
  for a *visible, checkable* structure such as assumptions, a plan or a calculation table.
- **Decompose, then chain.** Split the work into subtasks, mark which ones are sequential and which are
  independent, and use **plan-then-execute**: review the plan *before* any work is done.
- **A manual chain that you repeat is a candidate for reuse.** Run it by hand while you're learning it. Once
  you're repeating it, turn it into a Project (M3.3), a Skill (M4.2) or an automation (M4.3, Advanced).
- **When constraints conflict, state the priority order and a tie-break rule.** Add a checklist Claude must
  satisfy before it answers.
- **Build the check into the prompt:** a rubric self-check, generate-then-select, "list what you're unsure
  about", or an adversarial review of its own draft. A self-check filters errors. It doesn't guarantee
  correctness (M8.2).
- **Manage ambiguity explicitly:** "ask before guessing", an assumption log, and stop conditions.
- **Know the five failure modes on sight:** sycophancy, over-confidence, instruction drift, verbosity and
  invented specifics. For each one, know how you notice it and what you change.

## Concepts

### 1. Matching technique to task complexity

Not every task deserves the same machinery. Classify the task first, then pick the technique.

| Task type | Example | What it needs | Effort / cost it justifies |
|---|---|---|---|
| **Lookup** | "What port does our staging Redis use?" (with the config pasted) | Grounding material and a direct question | Lowest. Fast and cheap. Extra reasoning adds latency, not accuracy |
| **Transformation** | Convert a changelog into release notes; JSON → table | A clear output spec and an example | Low to medium. The work is format, not judgement |
| **Analysis** | Root cause from logs and a timeline; compare three vendor SOWs | Structured input, a required evidence trail, decomposition | Medium to high. Errors are costly and reasoning is multi-hop |
| **Open-ended reasoning** | A design that satisfies conflicting constraints; an RFP response strategy | Decomposition, explicit priorities, a plan review, self-critique | High to max. Each wrong turn compounds |

**The cost rule:** higher effort means more thinking tokens, which means more latency and more cost
(API) or more usage consumed (app plans). Buy reasoning where an error would cost more than the tokens. A
1-second lookup that takes 40 seconds at max effort is not "more careful". It's slower, and it isn't any
more right.

### 2. Extended thinking versus prompted reasoning

**What the thinking setting does.** With thinking on, the model works through the problem in a reasoning
phase before it writes the answer. **Effort** sets how much of that reasoning (and how many tool calls) it
is prepared to spend. On current models thinking is **adaptive** [api]: the model decides how deeply to
think within the effort level you set.

- [app] The model picker's effort control offers Low, Medium, High, **Extra high** and Max. (The app labels
  it "Extra high". The API value is `xhigh`, which the syllabus writes as "xhigh".)
- [api] `output_config={"effort": "low" | "medium" | "high" | "xhigh" | "max"}`, with `thinking={"type": "adaptive"}`
  or `thinking` omitted.
- [code] `/effort low|medium|high|xhigh|max`, covered in M6.2 (`/effort auto` clears your saved level; it isn't a level).

**When to raise effort:** multi-hop analysis, mathematics, code that has to be right first time,
reconciling conflicting sources, and any case where the first answer at a lower effort was plausible but
wrong. **Don't raise effort to fix a vague prompt.** More thinking about a bad spec gives you a more
elaborate wrong answer.

**What "work through this step by step" still adds.** With thinking on, the model already reasons before
it answers, so the classic chain-of-thought phrase adds little to the *reasoning*. It still adds value when
you want reasoning that is **visible and checkable** in the answer. Thinking output is summarised or hidden
by default, so ask for named artefacts instead:

- "Before the recommendation, show the assumptions you relied on as a numbered list."
- "Show the arithmetic as a table: line item | quantity | rate | subtotal."
- "Give the timeline you reconstructed, then the root-cause hypothesis, citing log line numbers."

**Don't over-prompt reasoning when thinking is on.** Instructions such as "think very carefully, consider
every possibility, double-check everything at every step" push the model to over-think simple parts, pad
the answer and run slower. Prompts written for older models often shout like this. Current models follow
instructions literally (see M2.1), so calm, specific guidance works better.

**Thinking can't be disabled on 5.5-generation models.** Effort is the lever.

> true in the **app** [app] and on the API for Opus 5.5 [api]. On the **API**, Haiku 5.5 accepts disabled thinking at effort ≤ high, and
> Sonnet 5.5 offers a `between_tools` thinking-off mode at effort ≤ high. For the exam, use the syllabus statement.

### 3. Task decomposition

**Split the task into subtasks** that each have one clear output. Then mark the dependencies:

- **Sequential** parts need the previous output. You can't write the RCA until the timeline exists.
- **Independent** parts can run in parallel chats, or in any order. You can summarise three vendor SOWs
  separately, then compare them.

Two smells tell you a task needs decomposing: the prompt contains three or more verbs ("analyse, compare,
recommend, draft"), or the output would mix audiences or formats.

**Plan-then-execute.** Ask for the plan first and review it before any work happens:

```text
Before doing any analysis, propose a plan: the steps you will take, the inputs each step uses,
and the output each step produces. Flag any step where you would need information I haven't given.
Stop after the plan and wait for my approval.
```

Reviewing a plan takes a minute. Reviewing a 3,000-word answer built on a wrong plan takes an hour, and
you may never notice the wrong framing. This is the same loop as plan mode in Claude Code (M6.2).

### 4. Prompt chaining

**A chain passes one step's output to the next as input.** In chat you run it by hand: run step 1, read the
output, correct it if needed, then paste it into the step 2 prompt (or refer to it in the same chat).

Example: an RFP security section, as a four-step chain.

| Step | Prompt does | Output | Your check |
|---|---|---|---|
| 1. Extract | List every requirement in RFP §7 with its clause number | Requirement table | Count matches the RFP |
| 2. Map | Map each requirement to our capability doc, quoting the supporting passage | Requirement → evidence table | Quotes exist (M8.2) |
| 3. Gap | List requirements with no or partial evidence | Gap list | Agree or disagree with each gap |
| 4. Draft | Write the response section from the mapped table, gaps marked "to confirm" | Draft section | Rubric review |

**Why chain instead of one big prompt:** each step has a single job, an inspectable output and a place
where you can fix an error before it spreads. A one-shot prompt hides the intermediate state.

**When a chain should stop being manual:**

| Signal | Move it to |
|---|---|
| You run the same chain weekly with the same reference documents | A **Project** with the instructions and knowledge files (M3.3) |
| The steps, template and checklist are stable, and others need them | A **Skill** (M4.2) |
| It runs on a trigger or a schedule, with no judgement between steps | An **automation** (M4.3, Advanced; API chains in M7.1) |

Keep it manual while you're still changing the steps. Automating a chain you don't understand just runs
the mistakes faster.

### 5. Constraint handling

Real tasks have constraints that conflict: "under 2 pages", "address all 14 requirements", "no
commitments beyond the SOW", "persuasive". If you don't rank them, Claude makes the trade-off silently,
and often in the wrong direction.

**State the priorities explicitly, with a tie-break rule:**

```text
Priorities, in order:
1. Accuracy: no claim beyond what the capability doc supports.
2. Coverage: every requirement in §7 gets a response, even if it's "partial; to confirm".
3. Length: aim for 2 pages. If coverage requires more, exceed the length and tell me by how much.
Tie-break: if two priorities conflict, the higher one wins. Report each conflict you resolved.
```

**Checklists Claude must satisfy before answering:**

```text
Before you answer, confirm each item and state any that fail:
- [ ] every requirement ID from step 1 appears
- [ ] every capability claim has a quoted source
- [ ] no dates or prices that aren't in the source documents
```

A checklist turns vague quality into specific, testable conditions. It also tells you where to look when
you verify.

### 6. Self-critique and verification prompts

| Technique | Prompt shape | Best for |
|---|---|---|
| **Rubric-based self-check** | "Score your draft against this rubric (criteria + pass condition). Fix every failing item, then show the scores." | Design notes, proposals, documents with known quality bars |
| **Generate-then-select** | "Produce three distinct approaches. Evaluate each against the criteria. Recommend one and say why the others lost." | Design choices, wording of a sensitive message |
| **"List what you're unsure about"** | "After the answer, list every claim you're less than confident in, and what would confirm it." | Anything with facts, numbers or names |
| **Adversarial review** | "Now act as a sceptical principal engineer reviewing this design. Find the three strongest objections." | Designs, RCAs, estimates |

Adversarial review works better in a **fresh chat**. The original chat has already committed to the draft
and tends to defend it (see sycophancy below). M8.2 calls this the second-opinion pass.

**A self-check filters errors. It doesn't certify correctness.** The model checks with the same knowledge
that produced the error, so it catches slips (a missed requirement, an arithmetic error, a format breach)
far better than it catches wrong beliefs (a fabricated API, a stale fact). Exercise 3 asks you to
*count* the defects a self-review catches. Expect it to find some, not all.

### 7. Ambiguity management

Ambiguity is where invented specifics come from: when a detail is missing, the model fills it with
something plausible. Three tools:

1. **Ask before guessing.** "If any required input is missing or ambiguous, ask me up to five questions
   before you start. Don't fill gaps with assumptions."
2. **Assumption log.** When you can't stop to answer questions, have the assumptions made visible instead:
   "Proceed, but record every assumption in a table: assumption | why needed | impact if wrong." This
   makes each guess a reviewable line item, which matters most for **effort estimates** (estimates without
   stated assumptions are guesses with false precision).
3. **Stop conditions.** "If the logs don't cover 02:10–02:40, stop and tell me rather than inferring what
   happened." "If you'd need to commit to a date, stop and flag it." A stop condition is a rule for
   *when not to continue*.

### 8. Failure modes and the counter for each

| Failure mode | What it looks like | How you notice | What you change |
|---|---|---|---|
| **Sycophancy** (it agrees with your framing) | "You're right that the cache is the cause…" when you suggested it | The answer mirrors your hypothesis. Pushback makes it flip | Ask neutrally ("what are the candidate causes?"). Ask for the case *against* your view. Use a fresh chat for the review |
| **Over-confidence** (fluent and wrong) | A precise, well-written answer with a wrong number or API | Confidence without citations. Specifics you can't trace to an input | Require sources, quotes or calculations. Ask for "what you're least sure about". Verify (M8.2) |
| **Instruction drift** in long chats | Turn 40 ignores the format rule from turn 2 | Format or constraints slowly erode. Generic answers creep back | Restate key rules. Start a fresh chat with a written handover (M2.3). Put durable rules in Project instructions |
| **Verbosity** | 900 words when 150 were wanted. Restating the question. Hedges | Length grows. The summary is buried | Give a length with a reason. Say "answer first, then the evidence". Ask for tables |
| **Invented specifics** | A config flag, a clause number or a person's name that doesn't exist | The detail isn't in any input. It's suspiciously convenient | Use "only from the material provided". Add an assumption log and "mark anything not in the sources as unconfirmed" |

## Under the hood

### What thinking actually is

Thinking is generated text: reasoning tokens the model produces before the final answer, in a separate
`thinking` content block [api]. It helps because a transformer does a fixed amount of computation per
token, so a hard problem gets more computation when the model can write intermediate steps and then attend
to them. **Effort** biases how many of those steps (and how many tool calls) the model takes.

Practical consequences:

- **Thinking costs tokens.** On the API, thinking tokens are billed as output tokens whether or not they
  are displayed [api]. Hiding the thinking hides the text, not the cost.
- **The raw reasoning isn't returned on current models.** Display options return a summary, or nothing
  (the default on current models) [api]. Don't build a workflow that depends on reading the chain of thought.
  Ask for the checkable artefacts in the answer instead.
- **Thinking isn't a guarantee.** The model can reason carefully from a wrong premise. Reasoning quality is
  capped by the input quality.

### Why prompted reasoning still has a place

With thinking on, "show your working" changes *what's in the answer*, not *whether reasoning happens*.
The visible version is for **you**: a reviewer can check a calculation table or an assumption list, but
can't check an internal reasoning trace they never see. Design the output for verification.

### Why decomposition beats one big prompt

1. **Attention is finite.** A prompt with four goals spreads the model's effort across all four. A
   single-goal step concentrates it.
2. **Errors compound silently.** In a one-shot answer, a wrong early inference (the wrong root cause)
   shapes everything after it, and you only see the polished end result. In a chain, you see the
   intermediate output and can stop it.
3. **Checks need checkpoints.** You can only verify what you can see. Each chain step is a verification
   point.

### Why fresh-chat review beats same-chat review

In the same chat, the draft and your earlier approval are in context. The model is conditioned on having
produced and defended that draft, which is the sycophancy and consistency pressure. A fresh chat with only
the draft and a reviewer role removes that conditioning. It's the same principle as human code review,
where the author is the worst reviewer of their own code.

### Inconsistency across runs: where it comes from

If five runs of the same prompt give five different answers, the task is **under-determined**: several
answers fit the spec equally well, and sampling picks a different one each time. Don't try to force
determinism with sampling parameters. `temperature`, `top_p` and `top_k` are removed on the current API
version [api] (DEPR). Remove the ambiguity instead:

- add the missing decision criteria and their priorities;
- fix the output format with an example (M2.1);
- add a checklist and an assumption log;
- for classification, define every label with a boundary example.

Measure it: run five times, diff the outputs, and find *where* they diverge. That tells you which part of
the spec is missing.

### API pattern: generate-then-select, then a fresh-context critique [api]

```python
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment
MODEL = "claude-opus-5-5"

constraints = open("design-constraints.md").read()  # internal, already cleared for use (M8.1)

# Step 1: generate three options at higher effort (open-ended reasoning).
draft = client.messages.create(
    model=MODEL,
    max_tokens=16000,
    output_config={"effort": "high"},
    messages=[{"role": "user", "content": (
        f"<constraints>\n{constraints}\n</constraints>\n\n"
        "Propose three distinct designs that satisfy the constraints. "
        "Priorities: 1) data residency 2) p99 latency 3) cost. Higher priority wins a conflict. "
        "For each design, list its assumptions and which constraint it trades off. "
        "Then recommend one and say why the other two lost."
    )}],
)
if draft.stop_reason == "refusal":
    raise SystemExit("Model declined; review the request")
draft_text = "".join(b.text for b in draft.content if b.type == "text")

# Step 2: adversarial review in a *fresh* context, with only the draft and constraints.
review = client.messages.create(
    model=MODEL,
    max_tokens=8000,
    output_config={"effort": "high"},
    system="You are a sceptical principal engineer. You did not write this design.",
    messages=[{"role": "user", "content": (
        f"<constraints>\n{constraints}\n</constraints>\n<design>\n{draft_text}\n</design>\n\n"
        "List the three strongest objections to the recommended design, each with the constraint "
        "it threatens. Then list any claim in the design you cannot verify from the constraints."
    )}],
)
print("".join(b.text for b in review.content if b.type == "text"))
```

Note what's absent: no `temperature`, no `budget_tokens`, no prefill. Effort is the reasoning lever. The
second call is a separate request, so it can't see the first call's reasoning or your approval.

## In production

**1. RFP section under deadline**
*Situation:* A 40-page RFP. The security section has 22 requirements, and it's due tomorrow.
*Right move:* Use the four-step chain (extract → map with quotes → gap → draft). Set priorities
explicitly: accuracy > coverage > length. Add a pre-answer checklist that every requirement ID appears.
*Why:* each step is checkable, and the gap list becomes your to-do list for the subject-matter experts.
*Failure mode:* one prompt saying "write our response to §7". You get fluent prose that silently skips four
requirements and claims a certification you don't hold.

**2. Root-cause analysis from logs and a timeline**
*Situation:* A SEV2 payment-latency incident. You have 2,000 log lines, a deploy timeline and a Grafana screenshot.
*Right move:* Reconstruct the timeline first (step 1), then ask for "candidate causes ranked by evidence,
each citing log lines" (step 2), with a stop condition: "if no log line supports a cause, say so". Raise
effort for step 2.
*Failure mode:* "I think it's the connection pool. Can you confirm?" That invites sycophancy. Claude
"confirms" your hypothesis, and the real cause (a DNS TTL change in the deploy) never gets considered.

**3. Effort estimate for a client change request**
*Situation:* A PM wants a number for "add SSO to the admin portal" by end of day.
*Right move:* Decompose into a work breakdown, require an assumption log (identity provider, number of
roles, existing session model), and give the estimate as a range tied to the assumptions. A human owner
signs it off (M5.1, M8.3).
*Failure mode:* a single figure ("12 days") with no assumptions. It becomes a commitment, and every hidden
assumption becomes scope creep.

**4. Design under conflicting constraints**
*Situation:* EU data residency, a p99 under 200 ms for US users and a fixed infrastructure budget.
*Right move:* Generate-then-select with an explicit priority order and tie-break. Then get an adversarial
review in a fresh chat.
*Why:* the priority order makes the trade-off explicit and reviewable instead of buried in prose.
*Failure mode:* no priorities given. Claude quietly optimises latency, and you find the residency breach
in the architecture review.

**5. Weekly status synthesis that drifts**
*Situation:* By week three of a long chat, the status reports have lost the RAG-status table, and the tone
has gone generic.
*Right move:* Recognise instruction drift. Move the template and rules into Project instructions (M3.3),
and start each week's report in a fresh chat inside the Project.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| Max effort for every task | Latency and cost with no accuracy gain on lookups and transforms | Classify the task, then pick the effort |
| Raising effort to fix a vague prompt | More reasoning about a bad spec makes a more elaborate wrong answer | Fix the spec first |
| "THINK VERY CAREFULLY STEP BY STEP" on a thinking-on model | Over-thinking, padding, slower runs | Ask for specific checkable artefacts |
| One prompt for analyse + compare + recommend + draft | Hidden intermediate errors, diluted attention | Decompose and chain, with a checkpoint per step |
| Executing without reviewing the plan | A wrong framing costs the whole output | Plan-then-execute. Approve the plan first |
| Unranked conflicting constraints | A silent, often wrong, trade-off | Priority order, tie-break rule, "report conflicts" |
| Leading questions ("confirm it's the cache") | Sycophancy: it agrees with you | Ask neutrally. Ask for the case against |
| Same-chat self-review as the only check | The model defends its own draft. A self-check isn't a guarantee | Fresh-chat adversarial review, then human verification |
| Fighting inconsistency with sampling settings | Removed on the current API. It masks the real cause | Remove ambiguity: criteria, examples, checklists |
| Automating a chain you're still changing | Errors run faster and with less visibility | Keep it manual until it's stable, then Project, Skill or automation |

## Hands-on exercises

1. **RFP chain.** Decompose a real RFP section into a four-step chain (extract → map → gap → draft) and
   run it by hand.
   **Done when:** you have kept all four intermediate outputs, the final draft covers every requirement ID
   from step 1, and you've written one line per step on what you corrected before passing it on.
2. **Effort comparison.** Run the same analytical task (for example an RCA from a provided log set) at Low
   and at Max effort.
   **Done when:** you have a table of wall-clock time, a quality score against a fixed 5-point rubric, and
   the specific errors each run made, plus one sentence on whether the quality gain justified the time.
3. **Rubric self-check.** Draft a design note, then apply a rubric self-check prompt.
   **Done when:** you've counted the defects the self-review caught, then had a human (or you, cold, the
   next day) count the defects it *missed*, and you've recorded both numbers.
4. **Fix an inconsistent prompt.** Take a prompt that gives different answers across five runs.
   **Done when:** you've identified the diverging element, added the missing criteria, examples or
   checklist, and five new runs agree on the substance (wording may differ).
