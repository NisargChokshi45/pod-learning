# M6.2 — The agentic coding workflow

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| ELECTIVE | Clusters A, B, C, D, E (cluster letters are **undefined in source**) | 2 | M6.1 (Level 1), M2.3 |

**Objective:** run the **explore → plan → implement → verify** loop with persistent project context and
controlled context size.

> At Level 1 you got Claude Code installed and ran a session safely. At Level 2 you run it as a *method*.
> The loop, CLAUDE.md, plan mode and context controls are how you get the same quality on day 30 as on day 1,
> and how a whole team gets it. Every surface claim below is `[code]`, and the details drift every week.
> Learn the principle and check the flag.

---

## TL;DR

- **The loop:** explore (read, ask) → plan (agree the approach) → implement (small steps) → verify (tests,
  lint, run). Skipping the plan saves five minutes and costs an afternoon of unwinding the wrong approach.
- **Plan mode** [code] GA: Claude explores and writes a plan but doesn't edit source. Enter it with
  `Shift+Tab`, `/plan` or `--permission-mode plan`. Approve, edit (`Ctrl+G`) or reject the plan before anything changes.
- **CLAUDE.md is your standing brief.** Files load from managed → user → project → local, and they're
  **concatenated, not overridden**. Put build and test commands, conventions and boundaries in it. Leave
  out anything that changes weekly.
- **Auto memory is Claude's notes, not your instructions.** It's machine-local, unreviewed and on by
  default. Turn it off where policy requires.
- **Context is a budget.** Use `/context` to see where it goes and `/compact <instructions>` to choose what
  survives. Auto-compact fires near ~967K tokens on 1M-window models. Starting fresh with a handover note
  beats limping on.
- **Checkpoints are a safety net with holes.** A snapshot is taken per prompt, and `Esc Esc` or `/rewind`
  restores code, conversation or both. Files changed *only* by Bash, and most subagent edits, are **not** restored.
- **Pick model and effort per task:** `/model`, `/effort`. Thinking can't be switched off on 5.5-generation models.
- **Never accept a diff you haven't read.** The whole level depends on this habit.

## Concepts

### 1. The loop

| Phase | What you do | What Claude does | Exit criterion |
|---|---|---|---|
| **Explore** | Ask questions; point at the entry files | Reads code, greps, runs read-only commands | You can both state how the current code works |
| **Plan** | Review, edit and approve | Writes the approach: files, order, risks, tests | Plan approved, or edited and then approved |
| **Implement** | Watch it, interrupt if needed | Makes small, reviewable edits that follow the plan | Each step compiles |
| **Verify** | Read the diff; run the checks | Runs tests, lint and the app; reports results | Tests green, diff read, behaviour observed |

**Why skipping the plan costs more than it saves.** Without an agreed plan, Claude picks an approach on
the first plausible reading of your request. It then makes coherent changes across many files *in that
direction*. If the direction is wrong (wrong layer, wrong abstraction, a missed existing helper), you're
not reviewing one bad line. You're unwinding a consistent wrong design spread over a dozen files. A plan
costs one reading pass. A wrong direction costs the whole diff plus the conversation context it filled.
The plan is also the cheapest place to inject knowledge Claude lacks ("we already have a retry helper in
`lib/http`").

### 2. Plan mode

- **Entering plan mode** [code] GA: `/plan` (optionally with a description, for example `/plan fix the
  auth token refresh`), `claude --permission-mode plan`, or `Shift+Tab` to cycle modes. You can make it the
  project default with `"permissions": {"defaultMode": "plan"}`.
- **What it does:** Claude reads files, runs exploratory shell commands and writes a plan, but **doesn't edit
  your source**.
- **The read-only Plan subagent:** a built-in subagent with read-only tools (Write and Edit are denied) that
  plan mode uses for research, so exploration doesn't fill your main context.

> **Syllabus says:** plan mode and "the read-only Plan subagent". · **Current (verified 2026-11-28,
> code.claude.com/docs/en/permission-modes):** the Plan *subagent* is read-only, but plan mode itself may run
> shell commands to explore. It doesn't edit source, but **a shell command can still have side effects**. Keep
> permission prompts on for anything that isn't obviously read-only.

- **Approving, editing or rejecting a plan:** when the plan is ready, Claude offers a choice: proceed with
  edits auto-approved, proceed with manual approval of each edit, or keep planning. `Ctrl+G` opens the plan
  in your editor so you can change it directly. Rejecting the plan with a reason ("use the existing retry
  helper; don't add a dependency") is the most valuable input you'll give in the session.
- **Turning a plan into tasks:** ask for the plan as numbered, independently verifiable steps, each with
  its test ("Step 3: add `RefreshPolicy`; test: `test_refresh_backoff` passes"). Implement one step,
  verify it, then go on. A good plan step is small enough to review as one diff.

### 3. CLAUDE.md and the memory hierarchy

**Precedence (load order)** [code] GA:

```
managed policy CLAUDE.md          ← org-wide, set by IT (e.g. /etc/claude-code/CLAUDE.md on Linux)
  → ~/.claude/CLAUDE.md           ← you, every project
    → ./CLAUDE.md or ./.claude/CLAUDE.md   ← the team, committed
      → ./CLAUDE.local.md         ← you, this project only, not committed
```

> **Mechanism:** these files are **concatenated, not overridden**. All of them go into context, and the
> more specific file is read **last**, so it tends to win when two instructions conflict. "Precedence" means
> load order plus recency, not a hard override. If a managed rule and your local file contradict each other,
> you've built an ambiguity. Remove it instead of hoping recency resolves it.

- **Nested directory files load on demand.** A `services/billing/CLAUDE.md` loads when Claude reads, writes
  or edits a file under `services/billing/`. Monorepos use this to keep per-package rules out of context
  until they're relevant.
- **Path-scoped rules in `.claude/rules/`.** These are Markdown files whose `paths:` frontmatter scopes them
  to matching files. They're introduced here and built out in M6.4 (Advanced).

```markdown
---
paths:
  - "src/api/**/*.ts"
---
# API handlers
- Validate request bodies with the zod schema in src/api/schemas/, never by hand.
- Every handler returns errors through `toProblemJson()` (RFC 9457).
```

- **Imports with `@path`.** For example `See @docs/testing.md for fixtures`. Paths are relative to the
  importing file and nest at most 4 levels deep. Imports from outside the project need a one-time approval.
- **AGENTS.md is read natively.** Teams sharing a repo with other coding agents can keep one file.

> **Syllabus says:** "AGENTS.md read natively". · **Current (verified 2026-11-28, code.claude.com/docs/en/memory):**
> yes, but by default **only when there is no CLAUDE.md**, `.claude/CLAUDE.md` or `CLAUDE.local.md`. A
> setting can load both. If you have both files and expect both to apply, check that setting.

- **`/init`** generates a first-draft CLAUDE.md from the repo, or suggests improvements to an existing one.
  Treat the draft as a junior's first attempt. Cut anything generic.

**What belongs in it:** build, test and lint commands (exact invocations); conventions Claude can't infer
from the code; boundaries ("never edit `migrations/` by hand"; "no new dependencies without asking").
**What doesn't:** anything that changes weekly (sprint goals, the current bug, who's on call). It goes
stale, stays in every session's context, and quietly misleads.

```markdown
# CLAUDE.md — payments-api

## Commands
- Build: `make build` · Test: `make test` (needs `docker compose up -d db`) · Lint: `make lint`
- Single test: `pytest tests/unit/test_refunds.py -k <name>`

## Conventions
- Python 3.12, type hints everywhere; `ruff` config in pyproject.toml is the style authority.
- Money is `Decimal` in minor units. Never float.
- DB access only through repositories in `app/repos/`; no ORM calls in handlers.

## Boundaries
- Never edit `alembic/versions/` by hand; generate migrations with `make migration name=...`.
- No new third-party dependencies without asking first (licence review: see M8.3).
- Never commit `.env*` files or anything under `secrets/`.

See @docs/testing.md for fixture conventions.
```

### 4. Auto memory

- **What it is:** notes Claude writes *for itself* at `~/.claude/projects/<project>/memory/MEMORY.md`
  [code] GA, for example "tests need the db container up", or "user prefers small commits". Topic files load on
  demand. Only the first part of MEMORY.md (about 200 lines or 25 KB) loads at session start.
- **Defaults and switches:** it's on by default in local sessions. Toggle it with `/memory`, set
  `"autoMemoryEnabled": false` in settings, or export `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`.
- **How it differs from CLAUDE.md:** CLAUDE.md is **you instructing Claude**. It's reviewed, committed
  and shared. Auto memory is **Claude noting things for itself**. It's machine-local, unreviewed and not shared.
  The full comparison, and what to promote from one into the other, is M6.8.

### 5. Context management

- **`/context`** shows what's using the window: system prompt, CLAUDE.md files, tools and MCP definitions,
  conversation, files read. Check it before a big task and again when quality dips.
- **`/compact <instructions>`** replaces the conversation with a summary that you steer: `/compact keep
  the failing test names, the plan steps still open and the decision to keep the v1 endpoint; drop the
  exploration`. Without instructions, the summary keeps whatever the model judges important, which may not
  be what you need next.
- **Auto-compact** fires when the window nears its threshold, about 967K tokens by default on 1M-window
  models. `autoCompactWindow` (setting), `/autocompact` and the `CLAUDE_CODE_AUTO_COMPACT_WINDOW` env var
  move the trigger point.
- **Keeping tasks scoped:** one task per session. A session that fixed a bug, then refactored a module,
  then wrote docs carries all three tasks' file reads into the fourth.
- **Starting fresh with a handover note:** at a natural boundary, ask Claude to write the handover (goal,
  decisions, files touched, open steps, commands that work), save it as a file, `/clear`, and start the
  next session from it. A handover you've read is better than a summary you haven't.

### 6. Checkpoints and rewind

- **Automatic snapshots** [code] GA: every prompt that starts a turn creates a checkpoint, and the most
  recent 100 are kept. Open rewind with `Esc` twice on an empty prompt, or with `/rewind`.
- **Restore code, conversation, or both.** Restore code to undo the edits but keep what you learned in
  the chat. Restore the conversation to take a different branch of the discussion while keeping the code.
  Restore both to go fully back.
- **Know the gap before you rely on it:** checkpoints track edits made by Claude's **file tools**.

> **Syllabus says:** "Bash and subagent edits are not tracked". · **Current (verified 2026-11-28,
> code.claude.com/docs/en/checkpointing):** a file changed **only** by Bash (`sed -i`, `npm install`, a
> codegen script, `rm`) isn't restored. Bash changes to a file Claude had already edited with its file tools
> *are* undone. Subagent edits are not restored, **except** edits made by a skill forked in the
> foreground. Rewind also offers "Summarize from here / up to here". **Working rule:** treat rewind as an undo for
> Claude's own edits, and Git as the real safety net. Commit before risky steps.

Things rewind can never recover: anything outside the working tree (a dropped database table, a pushed
branch, a sent message, a deleted file in another directory, an API call that changed remote state).

### 7. Models, thinking and effort

- **Aliases** [code]: `default`, `best`, `fable`, `sonnet`, `opus`, `haiku`, `sonnet[1m]`, `opus[1m]`,
  `opusplan` (Opus while planning, Sonnet while executing). Switch with `/model`.
- **Effort:** `/effort low|medium|high|xhigh|max`. Higher effort means more thinking and more tokens. Raise
  it for hard debugging or design, and lower it for mechanical edits.

> **Syllabus says:** `/effort … |auto`; ultrathink maps to xhigh. · **Current (verified 2026-11-28,
> code.claude.com/docs/en/model-config):** `auto` isn't an effort level. It **clears** your saved level.
> `max` lasts for the current session only. The default effort on the 5.5 models is `medium`. Typing
> **ultrathink** asks for deeper reasoning on that turn, and raises the turn to `xhigh` only in the terminal, VS
> Code or a desktop local session.

- **Thinking toggle:** `Option+T` / `Alt+T`. **Thinking can't be disabled on 5.5-generation models**, and the
  toggle has no effect there, so effort is your real lever.

### 8. Inputs and output styles

- **Pasting screenshots** [code] GA: `Ctrl+V`, `Cmd+V` in iTerm2, `Alt+V` on Windows and WSL. An
  `[Image #N]` chip appears in the prompt. Paste the failing UI, the dashboard spike, or the error dialog
  instead of describing it.
- **Output styles** [code] GA: **Default**, **Proactive**, **Concise**, **Explanatory**, **Learning**.
  Set one with `/output-style` or `/config`. Explanatory and Learning suit onboarding to an unfamiliar stack
  (Learning asks *you* to write parts of the code). Concise suits experienced users on routine work.

### 9. Reading the work

- **Reviewing diffs:** read every hunk. Check that it does what the plan said, that nothing outside the
  plan changed, and that there are no deleted tests, no weakened assertions, no new dependencies and no
  secrets.
- **The `/diff` panel:**

> **Syllabus says:** "the /diff live panel in the desktop app". · **Current (verified 2026-11-28,
> code.claude.com/docs/en/interactive-mode, …/desktop):** the **live, updating `/diff` panel is a terminal
> (CLI) feature** in fullscreen rendering. The **desktop app** has its own diff view (the Changes card, with
> inline comments). Either works. The habit is what counts.

- **Never accept a diff unread.** "Tests pass" is evidence, not proof. Claude can make tests pass by
  changing the tests. Signing off on code you haven't read makes you the accountable human (M8.3) for
  something you never reviewed.

## Under the hood

### What a "turn" in the loop actually is

```
you ──prompt──▶ model ──tool_use(Read/Grep/Bash/Edit)──▶ harness
                  ▲                                       │ permission check (mode, allow/deny rules)
                  └──────────── tool_result ◀─────────────┘ executes, returns output
          (repeat until the model returns text with no tool call → turn ends → checkpoint for next prompt)
```

Each tool result goes into the context window. **Exploration is the expensive part.** Reading 40 files
to answer a question can use more context than the whole implementation. That's why the Plan subagent
exists: it explores in its *own* context and returns only a summary.

### Why CLAUDE.md is concatenated, not merged

CLAUDE.md files are plain text put into context at session start. There's no rule engine. The
"hierarchy" is order and position. Two consequences: (1) every line costs tokens in **every** session, so
keep the file short; (2) contradictions aren't resolved deterministically, so you resolve them in
the files.

### Compaction is lossy summarisation

`/compact` asks the model to summarise the conversation, then swaps the summary in for the history. Detail
is lost by design: exact error strings, line numbers, the reason a dead end was rejected. Tell it what must
survive. Anything critical (the plan, the decision log) belongs in a **file**, not only in the chat. Files
survive compaction. Chat turns don't.

### Why checkpoints miss Bash

Checkpoints snapshot the files Claude's Edit and Write tools touch, because the harness sees those writes.
A Bash command is opaque. The harness can't know in advance that `./gen.sh` rewrites 30 files. Hence the
rule: if a step runs scripts that write files, commit first.

## In production

**1. Feature work on a client codebase**
*Situation:* add a CSV export to a client's Django reporting app that you've never seen.
*Right move:* explore ("how do existing exports work? which permissions guard reports?") → `/plan` → reject
the first plan because it adds `pandas` (the CLAUDE.md boundary says no new dependencies) → approve the
revised plan that uses the stdlib `csv` → implement step by step → run tests → read the diff.
*Why:* the plan review caught a dependency the contract would have needed licence review for (M8.3).
*Failure mode:* "just add CSV export" in default mode. You get 9 files changed and a new dependency, and
you find out in PR review.

**2. Onboarding to a legacy repository**
*Situation:* a new joiner inherits a 12-year-old Java monolith.
*Right move:* Explanatory output style, explore-only questions in plan mode, then `/init` to draft a
CLAUDE.md that the senior dev corrects. Save a handover note per area explored.
*Failure mode:* letting auto memory be the knowledge base. It's local to one laptop, unreviewed, and gone
when the laptop is reimaged.

**3. Standardising how a team briefs Claude**
*Situation:* five developers, five results. One person's Claude runs `npm test`, another's runs `yarn jest`.
*Right move:* a committed project CLAUDE.md with the canonical commands and boundaries, reviewed like code.
Personal preferences go in `~/.claude/CLAUDE.md` or `CLAUDE.local.md`. A rule that is only Claude's opinion
gets promoted out of auto memory or deleted.
*Why:* this is a context problem, not a prompting problem (M2.3).

**4. The long session that went soft**
*Situation:* three hours in, Claude starts repeating fixed bugs and forgets the agreed naming.
*Right move:* `/context` shows the window mostly full of old test output. Write a handover file, `/clear`,
start fresh from it. Next time, `/compact keep …` at the phase boundary.
*Failure mode:* pushing on and "reminding" it every few turns. Each reminder adds more context.

**5. The rewind that didn't**
*Situation:* Claude ran a codemod script via Bash, and then you rewound because the result was wrong.
Half the files stayed modified.
*Right move:* `git status` / `git restore`. Afterwards: commit before running scripts, and know the
checkpoint gap.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| Straight to "implement X" on unfamiliar code | A coherent wrong design across many files | Explore → plan → approve first |
| Approving the plan unread | Plan mode becomes theatre | Edit or reject with reasons. That's where your knowledge goes in |
| CLAUDE.md as a wiki (300 lines, sprint notes) | Costs tokens every session and goes stale | Commands, conventions, boundaries. Link the rest with `@` imports |
| Contradicting rules in user and project files | Concatenated, not resolved. Behaviour flips | Remove the conflict in the files |
| Treating auto memory as team knowledge | Machine-local, unreviewed, not shared | Promote what matters to CLAUDE.md or rules (M6.8) |
| `/compact` with no instructions mid-task | The summary drops what you need next | `/compact keep <specific items>`, or a handover file |
| Trusting rewind after Bash scripts | Bash-only file changes aren't restored | Commit before scripts. Git is the real undo |
| `max` effort for everything | Slow and expensive, with no gain on mechanical edits | Match effort to the task. Raise it for hard reasoning |
| Accepting a diff because "tests pass" | Tests may have been edited to pass | Read every hunk, tests included |

## Hands-on exercises

1. **Write a project CLAUDE.md** with build, test and convention rules for a sandbox repo. Prove it changed
   behaviour on two tasks.
   **Done when:** you can show two before/after pairs where Claude used your exact test command and followed
   a convention it didn't follow before, and the file is under 60 lines.
2. **Implement a small feature through plan mode.** Keep the plan and the diff for review.
   **Done when:** the saved plan has numbered steps with a test each, you edited or rejected at least one
   step with a reason, and the final diff matches the approved plan (or the deviations are explained).
3. **Fill the context deliberately, compact with instructions, and show what survived.**
   **Done when:** you have `/context` output before and after, your `/compact` instruction, and a list of
   three facts you told it to keep (all present) and one you didn't (lost or garbled).
4. **Rewind a bad change three ways** (code only, conversation only, both) and find a change rewind can't
   recover.
   **Done when:** you've shown all three restores and demonstrated one unrecoverable change (a Bash-only file
   edit or an external side effect), with the Git command that actually recovered it.
