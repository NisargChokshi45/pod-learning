**Objective:** generate and maintain tests at every level, and judge whether a generated test proves
anything.

> Claude writes tests fast. That is the problem as much as the benefit. A suite that grows by 200 tests in
> an afternoon and stays green tells you nothing until you know what those tests would *catch*. This module
> is about generating tests and then interrogating them.

**Minimum "M5.4 concepts" you need here** (the full treatment is at Advanced):
- **Review generated code as if a stranger wrote it.** Read every line, check every dependency exists and is
  approved, and run it yourself. "It compiled" is not review.
- **Never trust a claim you didn't observe.** "All tests pass" from Claude is a report. A test run you
  watched, in your CI or terminal, is evidence.
- **Security-relevant paths get human-designed tests** (auth, permissions, payments, input validation).
  Generated tests on these paths are a supplement, not the plan.

---

## TL;DR

- **The central risk: tests that pass but prove nothing.** Generated tests often mirror the
  implementation, assert on mocks, or assert nothing at all. Green is not evidence until you know the test can
  fail.
- **Think in mutations.** For each test, ask what bug it would catch. Mutation testing (mutmut, Stryker,
  PIT) automates the question. **Coverage tells you what code ran, not whether anything was checked.**
- **Generate from the spec, not only from the code.** Tests derived from code inherit its bugs. Tests derived
  from acceptance criteria can disagree with the code, and that disagreement is the point.
- **Strategy before generation:** shape the pyramid by risk. Automate what is stable, repeated and
  high-impact. Leave exploratory and one-off checks to humans.
- **Contract tests come from the OpenAPI file.** Integration tests use real dependencies via fixtures
  or containers. E2E tests cover a few critical journeys through page objects.
- **Flaky tests are usually timing, shared state or environment.** The fix is to wait on conditions, not on
  time (`sleep` is the bug).
- **Test data is synthetic or anonymised.** Production records never go into fixtures or prompts (M8.1).
- **Traceability:** every story maps to tests, and every test to a story. Orphans on either side are findings.

## Concepts

### 1. Test strategy

**Test pyramid decisions.** You need many fast unit tests, fewer integration tests, and a handful of E2E journeys. The
pyramid is a cost model. Tests higher up are slower, flakier and costlier to debug, but they prove more about real
behaviour. Claude can generate any layer equally fast, so the generation cost no longer limits you.
**Maintenance cost and run time do.** Don't let cheap generation turn your pyramid into an ice-cream cone
(mostly E2E).

**Risk-based selection.** Rank areas by *likelihood of defect × impact of failure*:

| Area | Likelihood | Impact | Test investment |
|---|---|---|---|
| Invoice total calculation | Medium (frequent changes) | High (money) | Dense unit + property tests, mutation-tested |
| Auth / permission checks | Medium | Critical | Human-designed cases + integration tests |
| Admin settings page layout | Low | Low | One smoke E2E, no more |
| CSV export | High (edge cases) | Medium | Boundary datasets + golden files |

Ask Claude to draft this table from the codebase and the incident history, then **you** set the ranks. The
risk judgement is the human part.

**What to automate and what not to:**
- *Automate:* regression-prone logic, anything run on every release, contracts between teams, data
  transformations.
- *Don't automate (yet):* volatile UI under active design, one-off migrations (verify by hand plus a
  reconciliation query), exploratory testing, usability judgement.

### 2. Unit tests

**Generating from code vs from specification.**

| Source | What you get | Danger |
|---|---|---|
| From code ("write tests for this function") | High coverage quickly; locks in current behaviour | Encodes existing bugs as "expected"; mirrors implementation |
| From spec ("here are the acceptance criteria; write tests; don't read the implementation") | Tests that can disagree with the code | Needs a decent spec; may miss implementation-specific edge cases |

Best practice: generate the spec-derived tests first, run them, then let Claude add code-derived tests for
the branches the spec didn't mention. When a spec test fails, **don't let Claude "fix" the test to match
the code** until a human decides which one is wrong.

**Edge cases.** Ask explicitly for an edge-case enumeration *before* the tests: empty, one, many, max,
max+1, negative, zero, null/None, Unicode, time zones and DST, leap years, concurrent calls, duplicate
submissions. Review the list, then generate.

**Mocking and stubbing.** A *stub* returns canned data. A *mock* also verifies how it was called. Mock at
boundaries you don't own (HTTP, clock, payment gateway). Don't mock the unit under test or its pure
helpers. Over-mocked tests verify your mock setup, not your code.

**Frameworks.** Claude generates idiomatic tests for all of these. Name the framework and version in the
prompt and paste one existing test file as the convention sample:

| Stack | Frameworks | Convention to pin in the prompt |
|---|---|---|
| JS/TS | **Jest**, **Vitest** | `describe/it`, `vi.fn()` vs `jest.fn()`, file naming `*.test.ts` |
| .NET | **xUnit**, **NUnit** | `[Fact]`/`[Theory]` vs `[Test]`/`[TestCase]`, assertion library |
| Python | **pytest** | fixtures over setUp, `parametrize`, `tmp_path`, `monkeypatch` |
| Java | **JUnit** (5) | `@Test`, `@ParameterizedTest`, AssertJ vs Hamcrest |
| Swift | **XCTest** | `XCTAssertEqual`, async `await fulfillment(of:)` |

```ts
// Vitest — spec-derived, with the clock controlled rather than mocked away
import { describe, it, expect, vi, afterEach } from "vitest";
import { isLinkExpired } from "./share-link";

describe("isLinkExpired (AC-3: links expire 24h after creation)", () => {
  afterEach(() => vi.useRealTimers());

  it("is valid at 23h59m", () => {
    vi.useFakeTimers().setSystemTime(new Date("2026-03-02T09:59:00Z"));
    expect(isLinkExpired(new Date("2026-03-01T10:00:00Z"))).toBe(false);
  });

  it("is expired at exactly 24h", () => {
    vi.useFakeTimers().setSystemTime(new Date("2026-03-02T10:00:00Z"));
    expect(isLinkExpired(new Date("2026-03-01T10:00:00Z"))).toBe(true);
  });
});
```

### 3. Integration and API tests

**Contract tests from OpenAPI.** The OpenAPI file is the contract. There are two directions:
- *Provider side:* generate requests from the spec and check that the real service's responses conform.
  Property-based options include **Schemathesis**, or **Dredd** for example-driven checks.
- *Consumer side:* run the client against a mock generated from the same spec, for example **Prism**. Consumer-driven
  contract tools such as **Pact** invert this, so that consumers publish expectations and the provider verifies them.

```bash
# Mock server from the spec (consumer tests point at http://127.0.0.1:4010)
npx @stoplight/prism-cli mock openapi.yaml
```

```bash
# Property-based conformance against a running provider (flags vary by version; check --help)
schemathesis run openapi.yaml --url http://localhost:8000
```

Claude is good at turning an OpenAPI file into a contract-test plan: status codes per operation, required
fields, enum values, pagination and error shapes. It is bad at knowing which undocumented behaviour clients
actually rely on. You supply that.

**Database tests with fixtures.** Each test gets known data and leaves nothing behind. Use transactions rolled back
per test, or a fresh schema. Ask Claude for fixtures that cover the boundary rows (soft-deleted, multi-tenant,
null foreign keys), not just the happy row.

**Test containers.** Run the real dependency (Postgres, Kafka, Redis) in a throwaway container instead of an
in-memory fake that behaves differently:

```python
# pytest + testcontainers: real Postgres per test session
import pytest
from testcontainers.postgres import PostgresContainer

@pytest.fixture(scope="session")
def pg_url():
    with PostgresContainer("postgres:16") as pg:
        yield pg.get_connection_url()
```

**Postman or REST client collections.** Claude converts an OpenAPI file or a set of curl calls into a
Postman collection or `.http` (REST Client) files with environment variables. Check that tokens are
variables, never literals, before anyone commits the file.

### 4. End-to-end and UI automation

**Scripts from user stories.** Give Claude the story, the acceptance criteria and the *real* DOM or
accessibility tree. A pasted screenshot isn't enough. Otherwise it invents selectors. Frameworks: **Playwright**,
**Cypress**, **Selenium** (web), **Appium** (mobile).

**Page-object generation.** Have Claude generate one page object per screen, so that selectors live in one place
and tests read like the acceptance criteria:

```ts
// Playwright — page object + web-first assertions (auto-waiting)
import { test, expect, type Page } from "@playwright/test";

class LoginPage {
  constructor(private page: Page) {}
  async goto() { await this.page.goto("/login"); }
  async signIn(email: string, password: string) {
    await this.page.getByLabel("Email").fill(email);
    await this.page.getByLabel("Password").fill(password);
    await this.page.getByRole("button", { name: "Sign in" }).click();
  }
}

test("AC-1: wrong password shows an error and stays on login", async ({ page }) => {
  const login = new LoginPage(page);
  await login.goto();
  await login.signIn("qa+user1@example.test", "wrong-password");
  await expect(page.getByRole("alert")).toHaveText(/incorrect email or password/i);
  await expect(page).toHaveURL(/\/login$/);
});
```

**Diagnosing a flaky test.** Give Claude the failing trace or log *and* a passing one, and ask for ranked
hypotheses. The usual culprits, in order:

| Cause | Symptom | Fix |
|---|---|---|
| Fixed waits (`waitForTimeout(2000)`, `sleep`) | Fails on slow CI, passes locally | Wait on a condition: web-first assertions, `expect.poll`, awaiting the network response |
| Shared state between tests | Fails only in certain orders or in parallel | Isolate data per test; no reliance on test order |
| Unawaited async | Intermittent "element detached" / assertion on stale value | `await` every action; lint for floating promises |
| Environment drift (time zone, locale, clock) | Fails on one runner | Pin TZ/locale; fake the clock |
| Real third-party calls | Fails when vendor is slow | Stub at the network boundary |

```ts
// Flaky:   await page.waitForTimeout(2000); expect(await page.textContent(".total")).toBe("€42.00");
// Fixed:   auto-waits until the condition holds (or times out with a useful message)
await expect(page.locator(".total")).toHaveText("€42.00");
```

Quarantining a flaky test is a temporary, *tracked* decision with an owner and a ticket. Deleting the
assertion to make it pass is not a fix.

### 5. Test data and fixtures

- **Synthetic data generation.** Ask Claude for generators (Faker, factory_boy, Bogus, fishery) or seeded
  datasets that match your schema and constraints. Seed the random generator so failures reproduce.
- **Anonymisation rules (M8.1).** Production data never goes into fixtures, prompts or repos. If you must start from
  production shape: drop direct identifiers, tokenise keys consistently, generalise quasi-identifiers (date
  of birth → year, postcode → district), and inject no real free text. Use reserved domains (`example.test`,
  `example.com`) and documented test card numbers. Check row-level data with the data owner before it leaves
  the system of record.
- **Boundary datasets.** These are small, deliberate datasets for limits: max-length strings, 0/1/many line items,
  the last day of the month, currency rounding cases (0.005), mixed encodings. A dozen well-chosen rows beat 10,000 random ones.

### 6. Reviewing and trusting generated tests

**Tests that pass but prove nothing** are the central risk of this module. The common shapes:

```python
# PROVES NOTHING — four different ways
def test_apply_discount(mocker):
    calc = mocker.patch("billing.discount.apply_discount", return_value=90)   # mocks the unit under test
    assert calc(100, "SAVE10") == 90                                         # asserts the mock's return value

def test_apply_discount_runs():
    apply_discount(100, "SAVE10")                                            # no assertion at all

def test_apply_discount_matches_impl():
    assert apply_discount(100, "SAVE10") == 100 - 100 * RATES["SAVE10"]      # re-implements the code

def test_invalid_code():
    try:
        apply_discount(100, "BOGUS")
    except Exception:
        pass                                                                 # swallows the failure
```

```python
# PROVES SOMETHING — expected values come from the spec, and the test fails if the logic breaks
import pytest
from billing.discount import apply_discount, InvalidCode

@pytest.mark.parametrize("amount,code,expected", [
    (100.00, "SAVE10", 90.00),     # AC-2: 10% off
    (0.00,   "SAVE10", 0.00),      # boundary: zero amount
    (10.05,  "SAVE10", 9.05),      # rounding: half-up to cents (AC-4)
])
def test_apply_discount(amount, code, expected):
    assert apply_discount(amount, code) == pytest.approx(expected, abs=0.001)

def test_unknown_code_is_rejected():
    with pytest.raises(InvalidCode):
        apply_discount(100.00, "BOGUS")
```

**A mutation-testing mindset.** For every test, ask: *"if I flipped this `>` to `>=`, deleted this line, or
returned a constant, would this test fail?"* If not, the test doesn't guard that behaviour. Tools automate
this: **mutmut** (Python), **Stryker** (JS/TS, C#, Scala), **PIT/PITest** (Java). The surviving mutants are the
to-do list.

**Coverage versus assertion quality.**

| Metric | Measures | Blind to |
|---|---|---|
| Line/branch coverage | Which code executed during tests | Whether any result was checked |
| Mutation score | % of injected bugs the suite caught | Bugs outside the mutation operators; slow on big code |
| Assertion density/review | Whether tests check outcomes | Needs human judgement |

Report coverage and assertion quality **separately**. A test with zero assertions earns 100% coverage. Review
checklist for any generated test: (1) does it assert on an outcome, not a mock? (2) where did the expected value
come from: the spec or the code? (3) would a plausible bug make it fail? (4) is the failure message useful?
(5) is it isolated and deterministic?

### 7. Test documentation

- **Test plans:** scope, risks, levels, environments, entry and exit criteria, owners. Claude drafts from the
  story set and the risk table. You approve the exit criteria.
- **Traceability matrices:** map requirement → test → result. Have Claude build them from story IDs and test
  names or tags. Then check them, because Claude will happily map a test to a story it doesn't exercise.

| Story / AC | Tests | Level | Last result | Gap? |
|---|---|---|---|---|
| ST-12 AC-1 wrong password error | `login.spec.ts › AC-1` | E2E | Pass | — |
| ST-12 AC-2 lockout after 5 tries | — | — | — | **Untested** |
| ST-14 AC-2 10% discount | `test_apply_discount[100-SAVE10]` | Unit | Pass | — |
| — | `test_legacy_promo_flag` | Unit | Pass | **Orphan test** (no story) |

- **Defect reports from logs and screenshots.** Claude turns a log excerpt plus screenshot into a structured
  report: summary, environment, steps, expected vs actual, evidence, severity *suggestion*. Redact the logs
  first (tokens, emails, IPs). Check that reproduction steps were actually reproduced, not inferred.

## Under the hood

### Why generated tests mirror the implementation

When Claude has the implementation in context, the most likely continuation of "write a test for this"
predicts the outputs **from that code**. It traces the logic and writes down what the code does. So a bug in the
code becomes the expected value in the test. The test agrees with the code by construction. It is a
**change detector**, not a **correctness check**. Remove the implementation from context (spec-only
prompting) or state the expected values yourself, and the test becomes an independent opinion again.

### Mutation testing mechanics

```text
source ──► mutate (one small change: > → >=, + → -, return x → return None, delete call)
        ──► run the tests that cover the mutated line
        ──► any failure?  yes → mutant "killed" (good)
                          no  → mutant "survived" (a gap: no test pins this behaviour)
mutation score = killed / (total − equivalent)
```

*Equivalent mutants* change the code but not the behaviour, so no test can kill them. Expect a few, and
don't chase 100%. Mutation runs are slow (tests × mutants), so run them on changed files in CI, or nightly.

### Root causes of flakiness

A test is flaky when its result depends on something other than the code under test: **time** (fixed
waits, real clocks), **order** (shared DB rows, global singletons), **concurrency** (unawaited promises, race
conditions in the app itself), or **environment** (network, locale, CPU speed on CI). Playwright's locators
and web-first assertions retry until a condition holds or a timeout expires. That's why replacing
`sleep` with an assertion fixes the first class but not the others. Sometimes the flake is a real race
in the product. Ask "could a user hit this?" before you stabilise the test.

### Claude Code in the test loop [code]

In Claude Code, Claude can run the suite, read failures and iterate. Two rules keep that honest:
(1) **instruct it not to edit tests to make them pass** without saying so, and check the diff for weakened
assertions, `skip`/`xfail`, or widened tolerances; (2) **the green run you trust is the one you see** in
your terminal or CI, not the summary in the chat. Bundled skills, hooks and CI wiring are M6.3 and M6.4.

## In production

**1. Raising coverage on a legacy billing module**
*Situation:* A manager wants coverage on `billing/` raised from 30% to 80% before a refactor.
*Right move:* Generate characterisation tests from the code (they lock in current behaviour, which is what you
want before a refactor) and label them as such. Then run mutmut on the core calculations and add spec-derived
tests for the survivors. Report coverage *and* mutation score.
*Why:* characterisation tests are legitimate when the goal is "don't change behaviour", as long as nobody
mistakes them for proof of correctness.
*Failure mode:* coverage reaches 80% through tests that assert mocks. The refactor breaks rounding and stays green.

**2. Regression suite for a release**
*Situation:* A release in three days. QA asks Claude to "write E2E tests for everything".
*Right move:* Build a risk table first. Pick 5–8 critical journeys (checkout, login, export), use page objects,
wait on conditions, and use synthetic accounts. Cover the rest at unit and contract level.
*Failure mode:* 120 generated E2E tests, 15% flaky, so the team starts ignoring red builds.

**3. Contract break between two teams**
*Situation:* The mobile app broke when the API team renamed a field that "no one used".
*Right move:* Generate provider conformance checks from the OpenAPI file in the API pipeline, and run consumer
tests against a Prism mock in the app pipeline. Have Claude diff two versions of the spec and list breaking changes.
*Why:* the contract becomes executable on both sides.

**4. Defect triage from a support escalation**
*Situation:* A ticket with a screenshot and 300 lines of logs.
*Right move:* Redact, then ask Claude for a defect report draft plus ranked hypotheses. Reproduce the steps yourself
before you file. Attach a failing test as the reproduction, so the fix PR has to turn it green.
*Failure mode:* filing Claude's inferred steps as "verified reproduction steps".

**5. Claude "fixed" the failing test**
*Situation:* In a Claude Code session, a spec-derived test fails. The next diff changes the expected value from
`9.05` to `9.04`.
*Right move:* Reject the change. Decide with the spec owner which side is wrong (here, rounding mode) and fix the code.
*Why:* a test edited to match the code no longer tests anything.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| "Write tests for this file" with the implementation in context | Tests mirror the code, so bugs become expected values | Give the spec and acceptance criteria; state expected values; then add code-derived tests |
| Celebrating the coverage % | Coverage counts executed lines, not checked outcomes | Report mutation score and assertion review separately |
| Mocking the unit under test | The test verifies the mock | Mock only boundaries you don't own |
| `sleep`/fixed waits in E2E | Flaky under load; slow | Web-first assertions and condition waits |
| Production rows as fixtures | Privacy breach; data leaks into repos and prompts | Synthetic, seeded, anonymised data (M8.1) |
| Letting Claude edit tests until green | Silently weakens assertions | Forbid it in the prompt; review test diffs line by line |
| Hundreds of generated E2E tests | Slow, flaky suite nobody trusts | Risk-based selection; push checks down the pyramid |
| Traceability matrix taken on trust | Claude maps tests to stories they don't exercise | Spot-check every "covered" row against the test body |
| Invented selectors from a screenshot | Tests fail or target the wrong element | Supply the DOM or accessibility tree; prefer role and label locators |

## Hands-on exercises

1. **Unit tests in two stacks.** Generate unit tests for an untested module in two stacks (for example pytest and
   Vitest). Measure coverage, then assess assertion quality separately: run a mutation tool or hand-mutate
   five lines.
   **Done when:** you report both numbers per stack, list every surviving mutant, and add at least one test that
   kills a survivor.
2. **Contract tests from OpenAPI.** From a provided OpenAPI file, produce contract tests and run them against a mock
   server (for example Prism).
   **Done when:** every operation has at least one success and one error-shape check, the suite runs green
   against the mock, and it fails when you change one response field in the mock.
3. **Playwright suite plus a flaky test.** Write a Playwright suite for a three-screen flow using page objects, then
   diagnose the seeded flaky test.
   **Done when:** the suite passes 10 consecutive runs with `--repeat-each=10`, the flaky test's root cause is
   named (time, order, concurrency or environment), and the fix contains no fixed waits.
4. **Traceability matrix.** Build a traceability matrix from stories to tests.
   **Done when:** every acceptance criterion has a row, every untested criterion and every orphan test is
   flagged, and you've checked at least five "covered" rows against the test bodies by hand.
