**Objective:** call the Messages API correctly on current models, with the inputs, thinking controls and
cost controls that production needs.

> In chat, someone checks every reply. In an integration, nobody does. A wrong parameter, an unhandled
> stop reason or a model retirement fails silently at 3 a.m. This module is the contract between your
> code and the API. Learn it as a contract: what you send, what comes back, and what changes under you.

All claims in this module are `[api]`. Volatile facts carry their status tag and a verification date: learn the
**principle** for the exam and check the **current value** at work ([fact-status.md](../reference/fact-status.md)).

## TL;DR

- **One endpoint does the work:** `POST /v1/messages`. Tools, structured output, thinking and caching are
  *features of that request*, not separate APIs. Batches, Files and token counting support it.
- **Authenticate from the environment, never in code.** The SDK reads `ANTHROPIC_API_KEY` from the environment. Each SDK major sends one
  `anthropic-version`. To change API versions, upgrade the SDK major.
- **Handle every `stop_reason`.** `end_turn` is the only "done, as intended". `max_tokens` means the output was truncated. `refusal` means
  the request was declined. `tool_use` and `pause_turn` mean the conversation continues. Read `stop_reason` before you read `content`.
- **Steer thinking with effort, not budgets.** Use `thinking={"type": "adaptive"}` (or omit it) and
  `output_config={"effort": …}`. Sampling knobs (`temperature`/`top_p`/`top_k`) and `budget_tokens` are gone
  on current models. Code that still sends them fails with 400.
- **Pin the model and plan the migration** before the retirement notice arrives. Retired models return 404.
- **Cost levers, in order:** cache the stable prefix → batch anything non-urgent (50% off) → choose the right effort
  → count tokens with the API, never a local tokenizer.
- **The OpenAI compatibility layer is for evaluation**, not production. Use the official SDK.
- **The cloud routes (Bedrock, Google Cloud, Foundry) have feature gaps.** Check the platform-availability table
  before you design around a feature.

## Concepts

### 1. Platform overview

**The Console** (`platform.claude.com`) is where you create **API keys** and organise **workspaces**.
A workspace is the unit of isolation for keys, spend limits and Files. You also use the Console to run requests in the
**Playground** `GA`.

- One workspace per environment (dev / staging / prod) or per client. A leaked dev key then can't touch
  prod data, and spend shows up per workspace.
- Keys have a type and an expiry. Rotate them like any credential. Keep them in a secret manager, never in a repo
  or a notebook.

> **Syllabus says:** the Workbench was retired in August 2026 `DEPR`; the Playground doesn't support saved prompts or
> evaluations. · **Current (verified 2026-11-28, platform.claude.com release notes):** confirmed. Legacy Workbench access
> ended 17 Aug 2026 and it became the Playground the next day. The Playground is stateless: drafts stay in your
> browser, and you can export any request as code. It has no saved prompts, versions, evals or sharing.

**Consequence:** prompts don't live in the Console. Version and test them in your repository (M2.4, Advanced).

**Rate-limit tiers advance with usage history.** Your org starts low and moves up automatically as usage and
account standing build. Limits apply per model class, to requests per minute and to input and output tokens per minute.
The engineering consequences: handle 429 everywhere, read the `retry-after` header, and plan a high-volume
launch with your account team. Don't assume headroom.

> **Syllabus says:** rate-limit tiers advance with usage history. · **Current (verified 2026-11-28, platform.claude.com/docs/en/api/rate-limits):**
> the principle holds. The tiers are now named Evaluation → Start → Build → Scale → Custom. There are also new **ramp limits**,
> which return a 429 with `error_code: ramp_limit_exceeded`. A spend-cap 429 has no `retry-after`, and retrying won't help.

**Cloud routes.** You can call Claude through a cloud provider's account, billing and IAM:

| Route | Why teams pick it | What to check first |
|---|---|---|
| **Amazon Bedrock** | AWS billing, IAM, VPC, existing contracts | No web search/fetch, code execution, Skills, Batches or Files API; a smaller request cap; its own retirement dates |
| **Google Cloud's Agent Platform** (formerly Vertex AI) | GCP billing and IAM | Web search is basic-only, and there's no web fetch, code execution, Files or Batches |
| **Microsoft Foundry** | Azure contracts and Entra ID | No Batches or mid-conversation system messages. Some features need "Hosted on Anthropic" deployments |

> **Syllabus says:** three cloud routes (Bedrock, Agent Platform, Foundry), each with feature gaps. · **Current (verified
> 2026-11-28, platform.claude.com/docs/en/api/overview):** there are **five** routes. Anthropic operates **Claude Platform on
> AWS**, **Claude Models on Google Cloud (Anthropic managed)** and Foundry, and these have near first-party parity. Partners operate
> **Bedrock** and **Google-managed Agent Platform**. The Python client for Agent Platform is still `AnthropicVertex`.

The gap lists change (see fact-status), but the rule doesn't: **design on the platform you'll ship on, and check its
availability table before you depend on a feature.**

### 2. SDKs and versioning

**Official SDKs:** Python, TypeScript, C#, Go, Java, PHP and Ruby, plus the **`ant` CLI** for scripting and auth
profiles. Use the official SDK. It handles retries, streaming, typed errors and the version header for you.

**API version `2026-10-21`.** Every request carries an `anthropic-version` header. Each SDK major sends
exactly one version, so **you move API versions by upgrading the SDK major**. Do it on a branch, with a regression run.

> **Current (verified 2026-11-28, SDK docs):** the majors that send `2026-10-21` are Python 2.0.0, TypeScript 1.0.0,
> Go 2.0.0 (`/v2`), Java 3.0.0, C# 13.0.0, PHP 1.0.0, Ruby 2.0.0 and `ant` 2.0.0. Breaking changes in this version: the
> sampling parameters are removed, a `document` block in an assistant turn returns 400, and a cited `text` block echoed in a user turn returns 400.

**Authentication.**

> **Syllabus says:** bearer-token authentication. · **Current (verified 2026-11-28, platform.claude.com/docs/en/api/overview):**
> `Authorization: Bearer <API key or workload-identity token>` is the **primary** header. `x-api-key` is a "legacy
> fallback, still supported". The new SDK majors send keys as Bearer, so **check any proxy or gateway that reads
> `X-Api-Key`** before you upgrade.

```bash
curl https://api.anthropic.com/v1/messages \
  -H "Authorization: Bearer $ANTHROPIC_API_KEY" \
  -H "anthropic-version: 2026-10-21" \
  -H "content-type: application/json" \
  -d '{"model": "claude-opus-5-5", "max_tokens": 1024,
       "messages": [{"role": "user", "content": "Classify: disk 91% on db-2"}]}'
# Legacy equivalent still accepted: -H "x-api-key: $ANTHROPIC_API_KEY"
```

On cloud and CI runners, prefer **Workload Identity Federation** `GA` over long-lived keys. The workload
exchanges its own identity token, so there's no stored secret to leak.

**The OpenAI SDK compatibility layer: for testing only, not production.** It lets you point existing
OpenAI-SDK code at Claude so you can compare models. It is documented as "not … a long-term or production-ready
solution". It ignores `strict`, has no prompt caching, doesn't return thinking, and hoists system messages.
Use it to evaluate. Then port to the official SDK before you ship.

### 3. The Messages API

```python
import anthropic

client = anthropic.Anthropic()  # ANTHROPIC_API_KEY from the environment; retries 2x by default

resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    system="You triage alerts for the payments platform. Reply with severity and the next diagnostic step.",
    output_config={"effort": "medium"},
    messages=[
        {"role": "user", "content": "<alert>p99 latency 4.1s on checkout-api, 12 min</alert>"},
    ],
)
```

- **System prompt.** The top-level `system` holds durable framing: role, rules, house style. Keep it stable,
  because that's what makes caching work (ch. 7).
- **Multi-turn.** The API is **stateless**. You resend the whole `messages` history every turn, alternating `user` and
  `assistant`. Your application owns the conversation state.
- **Mid-conversation system messages** `GA`. Append `{"role": "system", "content": "…"}` to `messages` to add an
  operator instruction partway through, for example "switch to incident-comms mode", *without* editing the top-level
  `system`. Editing the top-level system would invalidate the cached prefix. Placement rules: it must follow a `user` turn, and it can't be the first
  message. Model and platform support varies (not Foundry), so check before you rely on it.
- **Streaming.** Use streaming for long outputs or large `max_tokens`. It avoids HTTP timeouts and gives users
  first tokens fast. The SDK *requires* streaming for very large `max_tokens`. Over the wire it is server-sent events:
  `message_start`, then `content_block_start` / `content_block_delta` / `content_block_stop` per block, then
  `message_delta` (carrying `stop_reason` and output `usage`) and `message_stop`. The SDK helper assembles them:

```python
with client.messages.stream(model="claude-opus-5-5", max_tokens=64000, system=SYSTEM, messages=msgs) as stream:
    for text in stream.text_stream:
        send_to_client(text)                  # forward deltas as they arrive
    final = stream.get_final_message()        # the whole Message: content, stop_reason, usage
log_usage(final.usage); handle(final.stop_reason)
```

  The TypeScript SDK has the same helper (`client.messages.stream(...)` with `.on("text", …)` and `await stream.finalMessage()`).
  A stream that errors midway is **not** retried by the SDK, so retry the whole request at your level.
- **`max_tokens`** is required, and it's a hard ceiling the model doesn't see. Set it too low and the output is
  cut mid-sentence with `stop_reason: "max_tokens"`.
- **Stop reasons** (verified 2026-11-28; seven values). **Branch on all of them:**

| `stop_reason` | Meaning | Your code should |
|---|---|---|
| `end_turn` | Finished naturally | Use the output |
| `max_tokens` | Hit your ceiling | Treat as **truncated**: raise the limit, or continue; never parse it as complete JSON |
| `stop_sequence` | Hit a stop string you set | Use the output up to that point |
| `tool_use` | Wants a tool run | Run it and return `tool_result` (M7.2) |
| `pause_turn` | Server-tool loop paused | Append the assistant turn and resend to continue (M7.2) |
| `refusal` | Declined by safety classifiers (HTTP 200) | Don't read the content as an answer. Log `stop_details`, and fall back or tell the user |
| `model_context_window_exceeded` | Ran out of context window | Compact, trim or chunk. Don't retry unchanged |

**Errors and retries.** The SDK retries **2 times by default** on connection errors, 408, 409, 429 and 5xx (including 529
`overloaded`), with exponential backoff, and honours `retry-after`. Never retry 400, 401, 403 or 404 unchanged:
they're deterministic, so the same request fails the same way. Catch specific error classes first:

```python
try:
    resp = client.messages.create(model="claude-opus-5-5", max_tokens=1024, messages=msgs)
except (anthropic.RateLimitError, anthropic.APIConnectionError):  # after SDK retries: requeue the job
    requeue(job)
except anthropic.APIStatusError as e:     # 400/404 etc.: a bug or a retired model id; never retry unchanged
    log.error("claude_api_error", status=e.status_code, request_id=e.response.headers.get("request-id"))
    raise
```

Log the `request-id` response header on every failure. Support will ask you for it.

**Removed sampling parameters** `DEPR`. `temperature`, `top_p` and `top_k` were removed in API version
`2026-10-21`. Code that sets them **fails with 400 on every model**, even at the default values.

```python
# Don't: this now fails (400 invalid_request_error on 2026-10-21)
client.messages.create(model="claude-opus-5-5", max_tokens=1024, temperature=0.2, messages=msgs)

# Do: delete the parameter. For consistency, tighten the prompt (examples, explicit format) or use
# structured outputs; for variety, ask for N distinct options in one call.
client.messages.create(model="claude-opus-5-5", max_tokens=1024, messages=msgs)
```

### 4. Models in the API

| ID | Role |
|---|---|
| `claude-opus-5-5` | Default for complex work and agentic coding |
| `claude-sonnet-5-5` | Speed and capability balance |
| `claude-haiku-5-5` | High-volume, latency-sensitive work (classification, extraction) |
| `claude-fable-5-1` | Most capable (syllabus) |

> **Syllabus says:** `claude-fable-5-1`. · **Current (verified 2026-11-28, platform.claude.com model deprecations page):** `claude-fable-5-2`
> (released 9 Nov 2026) is the current Fable. `claude-fable-5-1` is still served. Use exact ID strings and never
> invent a date suffix.

- **1M-token context by default** on the current generation, with up to **128K output** tokens (stream large outputs).
- **Deprecation policy.** Models go Active → Legacy → Deprecated → Retired, with **at least 60 days' notice**
  before retirement. **Retired models return 404.** Partner clouds set their own dates.
  The syllabus example is Sonnet 4.5, **tentatively** retiring 30 November 2026 `DEPR`. Since the syllabus, Opus 4.5 has
  also been deprecated (Nov 2026) and retires 2027-01-22. Check the deprecations page for current dates.
- **Pinning.** Pin an exact model ID in **one config value**. A pin without a migration plan is a scheduled outage.
  Before you pin, write down: the eval set that proves a replacement works; the owner who watches the deprecations
  page; the cutover steps (config, regression, canary, rollout); and the deltas to re-test on each new model
  (thinking and effort defaults, forced tool use, prefill).

### 5. Thinking and effort

**Adaptive thinking** lets the model decide how much to reason for each request. On 5.x models it's on by default.
You steer depth and overall token spend with **`output_config.effort`**: `low`, `medium`, `high`,
`xhigh` or `max`.

```python
resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    thinking={"type": "adaptive", "display": "summarized"},  # or omit "thinking" entirely on 5.x
    output_config={"effort": "high"},                        # set explicitly; defaults differ by model
    messages=[{"role": "user", "content": incident_timeline}],
)
text = "".join(b.text for b in resp.content if b.type == "text")  # thinking blocks hold a summary at most
```

Rough guide: `low` for classification, routing and subagents; `medium` for routine drafting and Q&A; `high` for
analysis and code review; `xhigh`/`max` for hard reasoning and long agentic coding, only where measurement shows a gain.

Tune effort **per route**, using real samples. Judge cost per *completed task*. A cheaper call that needs a retry isn't cheaper.

**Display options** only control visibility (thinking is billed either way): `"summarized"` returns a readable summary,
`"omitted"` returns empty thinking text.
> **Syllabus says:** thinking display options. · **Current (verified 2026-11-28, platform.claude.com thinking docs):**
> `"omitted"` is the **default** on all 5.x models. If you stream reasoning to users, set `"summarized"`, or the UI
> shows a long silent pause. A third option, `"updates"` `BETA`, returns short progress notes between tool calls.
> Opus 5.5's default effort is `medium`, so set effort explicitly.

**Manual extended thinking** `DEPR`. `{"type": "enabled", "budget_tokens": N}` is deprecated on 4.6 models and
**rejected (400) on 4.7 and later**, including every 5.x model. On those models, thinking also can't be turned off on Opus 5.5 or
Fable 5.x. Effort is the control.

```python
# Don't: this now fails (400) on current models
thinking={"type": "enabled", "budget_tokens": 8000}
# Do:
thinking={"type": "adaptive"}, output_config={"effort": "medium"}
```

### 6. Multimodal inputs

**Images** can be sent three ways: `base64` (JPEG, PNG, GIF, WebP), `url`, or a Files API `file_id`, as an
`{"type": "image", "source": {...}}` block placed before the text that asks about it.

**PDFs:** up to **600 pages** on 1M-context models `[api]`. This is a different limit from the 1000 pages in the app `[app]`.
The two surfaces don't override each other, so route the work to the surface whose limit fits. Put the document **before**
the question.

**Files API** `GA`: upload once and reference the file by `file_id` across many requests. Limit: **500 MB per file**.
The upload and the `{"type": "document", "source": {"type": "file", "file_id": …}}` block are shown in ch. 8.

Files are **workspace-scoped**. Never accept a `file_id` from an end user, because it could point at another tenant's file in
the same workspace. You can't download uploaded files back. Only Skill and code-execution outputs are downloadable.

### 7. Cost and scale controls

**Prompt caching** reuses the processed prefix of a request. There are two ways to turn it on:

- **Explicit breakpoints:** `cache_control` on a block, up to 4 per request.
- **Top-level automatic:** a single `cache_control` on the request.

The TTL is **5 minutes** by default (`{"type": "ephemeral"}`), with a **1-hour** option (`"ttl": "1h"`).
Writes cost more than normal input and reads cost a fraction of it. A prefix shorter than the model's minimum
**silently doesn't cache**.

```python
resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=2048,
    system=[{"type": "text", "text": RUNBOOK_AND_STYLE_GUIDE,          # large, stable
             "cache_control": {"type": "ephemeral"}}],
    messages=[{"role": "user", "content": f"<ticket>{ticket}</ticket>"}],  # varies per call
)
u = resp.usage
metrics.record(written=u.cache_creation_input_tokens, read=u.cache_read_input_tokens,
               uncached=u.input_tokens, output=u.output_tokens)
```

> **Syllabus says:** minimum 512 tokens on 5.x models. · **Current (verified 2026-11-28, prompt-caching docs):** 512 on most
> 5.x models, **except Sonnet 5 at 1,024** (older models need 2,048–4,096). Reads cost 0.1× on most models, but
> **0.05× on Opus 5.5 and Sonnet 5.5** and 0.025× on Fable 5.1–5.2. Writes cost 1.25× for the 5-minute TTL and 2× for 1 hour.

**Message Batches API**: asynchronous, at **half price**. Use it for anything that doesn't need an answer
now, such as nightly classification, backfills and evals. Most batches finish within an hour, and a batch expires at 24 h.

```python
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

batch = client.messages.batches.create(requests=[
    Request(custom_id=f"ticket-{t.id}",
            params=MessageCreateParamsNonStreaming(
                model="claude-haiku-5-5", max_tokens=256,
                messages=[{"role": "user", "content": f"Label this ticket: {t.text}"}]))
    for t in tickets
])
# later: poll until processing_status == "ended"; key results by custom_id (order is not guaranteed)
for r in client.messages.batches.results(batch.id):
    if r.result.type == "succeeded": store(r.custom_id, r.result.message)
    else: retry_queue.append(r.custom_id)       # errored / expired / canceled
```

**Token counting endpoint**: `POST /v1/messages/count_tokens`. It's the only tokenizer that matches the model.
Local tokenizers from other vendors give wrong counts.

```python
n = client.messages.count_tokens(model="claude-opus-5-5", messages=msgs, system=SYSTEM).input_tokens
```

> **Request size cap. Syllabus says:** 128 MB. · **Current (verified 2026-11-28, API overview):** 128 MB for Messages and token
> counting **on the first-party API**. Batches allow 256 MB and Files 500 MB. Anthropic-operated cloud routes cap Messages at 32 MB,
> Bedrock at 20 MB and Google-managed at 30 MB. Over the cap you get a 413. For large inputs, use the Files API.

### 8. Citations

Set `"citations": {"enabled": True}` on **document** blocks. Claude then returns text split into blocks that carry
`citations` (cited text, plus page numbers for PDFs). That's how you make an API answer **checkable** (M8.2).

```python
f = client.files.upload(file=("msa-2026.pdf", open("msa-2026.pdf", "rb"), "application/pdf"))
doc = {"type": "document", "source": {"type": "file", "file_id": f.id},
       "title": "MSA 2026", "citations": {"enabled": True}}
resp = client.messages.create(model="claude-opus-5-5", max_tokens=4096,
    messages=[{"role": "user", "content": [doc, {"type": "text", "text": "What is the notice period?"}]}])
for b in resp.content:
    if b.type == "text":
        for c in (b.citations or []):
            if c.type == "page_location":            # PDFs; plain text uses char_location
                print(c.cited_text, c.start_page_number, c.end_page_number)
```

Citations are **incompatible with `output_config.format`** (400 if combined). Need both? Extract with citations, then structure.

## Under the hood

### Request lifecycle

```
your code ──► SDK ──► HTTPS (Bearer, anthropic-version) ──► API edge
                                                             │ auth → rate limit → size cap (413)
                                                             ▼
                                         render: tools → system → messages  (one token sequence)
                                                             │ cache lookup on the rendered prefix
                                                             ▼
                                         model: adaptive thinking (effort) → content blocks
                                                             │
SDK ◄── stream events / JSON ◄── stop_reason + usage {input, cache_creation, cache_read, output}
```

Everything you send is flattened into one sequence in a fixed order: **tools → system → messages**. That order
explains caching, cost and most "why did the answer change" bugs.

### How the cache prefix works

The cache key is the **exact byte prefix** up to a breakpoint. Change one byte anywhere before the breakpoint and
everything after it is a miss. Common silent invalidators:

| Invalidator | Fix |
|---|---|
| A timestamp or request ID in the system prompt | Move it into the user turn, after the breakpoint |
| `json.dumps` of a dict with unstable key order | `sort_keys=True` |
| The tool list built in a different order per request | Build it deterministically |
| Editing the system prompt mid-conversation | Use a mid-conversation system message |

Verify caching by watching `usage.cache_read_input_tokens`. If it stays at zero across identical-prefix calls, you have an invalidator.

## In production

**1. Ticket classifier blows the budget.** 400K tickets a month, labelled synchronously on Opus at high effort.
*Right move:* Batches (50%) for the backlog, a smaller model at `low` effort, and a cached system prompt holding the
taxonomy, validated on a 500-ticket golden set before cutover. *Failure mode:* the cheaper model ships without the golden
set, quality drops, and nobody notices.

**2. Model retirement.** The deprecation email names the model your contract-review service pins. *Right move:* the
pin lives in config. Run the eval set against the replacement, review the behavioural deltas, canary, and cut over before
the date. *Failure mode:* the ID is hard-coded in 14 places with no eval set, so retirement becomes a 404 outage.

**3. "Our integration broke overnight."** After an SDK bump every call returns 400. The code still sends
`temperature`, which the new major's API version rejects. Remove it, run the regression, and add a CI check.

**4. Contract Q&A for legal.** Upload through the Files API, enable citations, and show page-cited quotes that legal
can click through. *Failure mode:* uncited prose answers that legal can't check, so they stop trusting the tool.

**5. Client on Bedrock.** The client mandates AWS billing, and your design uses Batches and Files. *Right move:*
check the availability table at design time. Replace Batches with your own queue, inline documents instead of file
IDs, and record every gap in the design doc.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| API key in code, a notebook or the repo | It leaks through git history and screenshots | Environment variable or secret manager. Workload identity on CI |
| Reading `content[0].text` without checking `stop_reason` | Truncated or refused output gets treated as an answer | Branch on every stop reason |
| Sending `temperature` "for determinism" | 400 on the current API version | Remove it. Use examples, explicit format and structured outputs |
| A hard-coded model ID in many files | Retirement becomes an outage | One config value, an eval set and a migration runbook |
| Retrying 400s | Deterministic failure, wasted spend | Fix the request. Retry only 408/409/429/5xx |
| Accepting `file_id` from end users | Cross-tenant file access in a shared workspace | Map your own IDs to file IDs server-side |

## Hands-on exercises

1. **Streaming chat endpoint, in Python and TypeScript.** It needs a system prompt, prompt caching and token accounting.
   **Done when:** both implementations stream; log `cache_creation_input_tokens` on the first call and
   `cache_read_input_tokens > 0` on the second identical-prefix call; handle `max_tokens` and `refusal`
   explicitly; and keep no key in code.
2. **200 PDFs through the Files API and Batches.** Report the cost with and without caching.
   **Done when:** every result is keyed by `custom_id`; failed or expired items go to a retry list; and you
   have a cost table (uncached vs cached, sync vs batch) computed from `usage` fields, not estimated.
3. **Migrate a sample app off a deprecated model and off manual thinking.** Run a regression.
   **Done when:** the model ID lives in one config value; `budget_tokens` and sampling parameters are gone; effort is set
   explicitly; and a golden-set regression shows no unexplained quality drop.
4. **Deploy the same call on one cloud route.** Document every feature that's missing there.
   **Done when:** the same prompt runs through the route's client, and you have a gap table with one row per feature
   your app uses, each with its workaround, citing the availability docs and the date you checked.
