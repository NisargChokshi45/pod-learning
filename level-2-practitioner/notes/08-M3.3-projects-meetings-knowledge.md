# M3.3 — Meetings, requirements and knowledge management with Projects

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| CORE | All clusters | 1.5 | M2.3 (context engineering and instruction hierarchy) |

**Objective:** run Projects as working knowledge bases, and turn meetings into tracked outcomes rather
than notes nobody reads.

> A Project is a curated context: standing instructions plus a body of knowledge that every chat inside it
> starts from. Run well, it's the team's memory of an engagement. Left alone, it serves last quarter's
> SOW with complete confidence. This module covers how to design a Project, keep it current, and feed it
> the output of meetings, which is where most decisions get made.

---

## TL;DR

- A **Project = instructions + knowledge + project memory** [app]. Instructions say *how to behave*.
  Knowledge says *what is true*. Don't mix the two.
- **One Project per client engagement or per team function.** Name files so a stranger can tell what
  they are and how old they are. Set a **refresh cadence**, because a stale Project is worse than none: it's
  trusted.
- As knowledge grows, paid plans switch to **retrieval mode** automatically [app]. Claude then *searches*
  the knowledge instead of reading all of it. Ask for file and section references, and check them.
- **Meetings produce decisions and actions, each with a named owner and a date.** Minutes are a
  by-product. Separate "decided" from "discussed".
- **Requirements extraction** gives three lists: requirements, constraints, and **open questions**. A gap
  list and a change-impact note follow from those. Engineering depth is in M5.1.
- **Ask Your Org / enterprise search** [app] makes live calls to connected sources with no index. Treat
  every answer as a pointer to a source, then open the source.
- **Never put secrets, credentials or unneeded personal data in a shared Project** (M8.1). Everyone
  with access, now and later, can read them through Claude.

## Concepts

### 1. Projects as the unit of work

| Component | What it is | Engineering analogy |
|---|---|---|
| **Project instructions** | Standing guidance applied to every chat in the Project | A system prompt you control |
| **Project knowledge** | Uploaded files (and connected sources) available to every chat | A read-only docs folder mounted into each session |
| **Project memory** | What Claude remembers across chats *within this Project*, kept separate from your account memory | A per-repo cache, not committed |

**Limits and plan behaviour** [app]:
- **Knowledge files up to 30 MB each** [app, GA]. A large PDF that fits under the per-chat upload limit can still be refused here.
- **Retrieval mode turns on automatically on paid plans as knowledge grows** [app, GA]. Small Projects are
  read in full. Large ones are searched (see *Under the hood*).
- **Free plans: at most five Projects** [app, PLAN].
- **Sharing with "Can view" or "Can edit" rights on Team and Enterprise** [app, PLAN]. **Owners can turn
  off Project sharing** for the organisation, which also turns off public Projects.

### 2. Designing a Project

**What goes in instructions and what goes in knowledge.** Instructions are short, stable and
imperative. Knowledge is long, factual and versioned.

| Put in **instructions** | Put in **knowledge** |
|---|---|
| Audience and tone ("the reader is the client's CTO; no internal jargon") | SOW, contract, org chart, glossary |
| Output standards ("cite file and section for every factual claim") | Decisions log, risk register, architecture overview |
| Conflict rules ("SOW beats meeting notes; flag disagreements") | Meeting minutes, status reports |
| What not to do ("never estimate without listing assumptions") | Runbooks, FAQs, style guide |
| Pointers ("the glossary is `03-glossary`; use its terms") | Templates (status report, minutes) |

Rule of thumb: if it changes when the facts change, it belongs in knowledge. If it changes only when *how
you work* changes, it belongs in instructions. A fact in the instructions ("the go-live is 3 March") goes
stale silently and outranks the corrected file in knowledge.

**File hygiene and naming.** Retrieval and humans both depend on findable names.

```text
00-README-project-scope.md          ← what this Project is for, owner, refresh date
01-sow-v3-signed-2026-09-12.pdf
02-org-chart-client-2026-10.pdf
03-glossary.md
04-decisions-log.md                 ← append-only, one row per decision
05-risk-register.md
minutes/2026-11-24-steering.md
_archive/sow-v2-superseded.pdf      ← or delete; never leave two "current" SOWs
```

- Put the **version and date in the name**. Retrieval surfaces chunks, not file metadata you can see.
- **Keep one current version** of each document. Two SOWs means Claude may quote the wrong one.
- Put **plain text over scans** where you can. A scanned PDF is harder to retrieve from accurately.

**A refresh cadence, so it doesn't rot.** Give the Project a named owner and a date on the README.
Weekly for an active engagement: add the minutes, update the decisions log, archive superseded files.
Quarterly for a team-function Project: review every file, delete what nobody would miss.

**One Project per engagement, or per team function.** Mixing two clients in one Project is a
confidentiality breach waiting to happen (M8.1): their files sit in the same retrieval pool. Mixing unrelated
work dilutes retrieval and confuses the instructions.

**Project design template** (put it in `00-README`):

| Field | Example |
|---|---|
| Purpose | Delivery workspace for Northwind data-platform migration |
| Owner · refresh | A. Rao · weekly, Mondays |
| Audience of outputs | Client CTO and delivery lead |
| Knowledge index | 01–05 as above, with one line each |
| Must never contain | Credentials, customer personal data, other clients' material |
| Retention | Archive at engagement end; handover Project created (§6) |

### 3. Meetings

**Before: the agenda.** Give Claude the goal, the attendees and their roles, and the open items from the
decisions log. Ask for an agenda with time boxes and **the decision needed** for each item. An agenda item
with no decision attached is a status update and can usually go in an email.

**After: from notes to minutes, decisions and actions.** The deliverable is not the minutes. It's the
**decisions** and **actions with named owners and dates**.

```text
<transcript>…redacted transcript…</transcript>

From the transcript, produce:
1. Decisions: only items explicitly agreed. For each: decision, who agreed, supporting quote.
2. Actions: Action | Owner (a named person, not a team) | Due | Source quote.
   If no owner or date was stated, write "UNASSIGNED" / "NO DATE"; do not infer.
3. Discussed, not decided: one line each.
4. Open questions.
5. Minutes: ≤10 bullets.
```

The quote column is your verification hook (M8.2): check every decision against the transcript before you
circulate it. The **"UNASSIGNED" rule matters**. Claude will otherwise attach a plausible owner,
and a wrongly assigned action is worse than an unassigned one, because nobody chases it.

related events to help you prepare. It can also create or update events, so only approve writes you meant.

### 4. Requirement analysis for everyone

Any role receives requirements: in an email, a call, a ticket, an RFP or a change request. The
Practitioner skill is **extracting and separating** them.

| Output | What it holds | Prompt clause |
|---|---|---|
| **Requirements** | What must be true, as testable statements | "Each as one 'The system/team must…' sentence, with a source quote" |
| **Constraints** | Limits on *how*: budget, deadline, tech, regulatory | "List constraints separately from requirements" |
| **Open questions** | What the source doesn't answer | "List what you would have to guess; do not guess" |
| **Gap list** | Requirement × missing information | "For each requirement, what is unspecified (who, when, how much, what if)" |

**Requirement and gap list template:**

| ID | Requirement | Source (doc §/quote) | Type | Gap / ambiguity | Question to send | Owner |
|---|---|---|---|---|---|---|
| R1 | Reports must be exportable to Excel | Email 12 Nov: "need it in Excel" | Functional | Which reports? Format (.xlsx/.csv)? | "Which of the 6 reports need export?" | PM |
| C1 | Go-live before 31 Jan | SOW §2.1 | Constraint | Hard date or target? | "Is 31 Jan contractual?" | Delivery lead |

**Impact of a change request.** Give Claude the change request, the current scope (SOW), the decisions log
and the plan. Ask: which requirements, deliverables, dates and risks change; what is newly out of scope;
and what has to be decided, by whom. Claude finds candidate impacts. A human confirms them, because
Claude can't see the dependencies nobody wrote down.

*Engineering depth (INVEST stories, Given-When-Then, contracts) is M5.1. This chapter is the version
every role needs.*

### 5. Organisational knowledge

**Enterprise search, "Ask Your Org"** [app, PLAN: Team and Enterprise, owner-configured]. This searches across
connected sources such as SharePoint, Slack, Gmail and Drive **with live calls; nothing is indexed**. Two
consequences:
- It only sees what **your** account can see, at query time. Two people can get different answers.
- It can only return what someone wrote down. "We decided in the hallway" is invisible.

Use it to *find* sources, not as the source itself. Record every source it used (exercise 4).
(Not on mobile, per the Level 1 fact-status.)

**FAQ and runbook generation.** Feed real material (resolved tickets, incident postmortems, the Slack
thread where the answer was finally found) and ask for an FAQ or a runbook with **a source per entry**.
Then have the subject-matter owner review it before publishing. A generated runbook that nobody ran is a
hypothesis.

**Keeping knowledge current.** Every FAQ and runbook needs an owner, a "last verified" date and a
trigger for review (for example "any change to the deploy pipeline"). Stale runbooks cause incidents.

### 6. Team patterns

- **Shared Project templates.** Give each cluster a standard skeleton: README fields, instruction block and file
  numbering. New engagements then start consistent, and reviewers know where to look.
- **Onboarding Projects.** Curated knowledge (architecture, glossary, the five decisions that explain the
  system, a "who to ask" list) plus instructions such as "explain at new-joiner level; always cite the file".
  New joiners ask Claude first and humans second.
- **Hand-over Projects at engagement end.** Final decisions log, open risks, runbooks and contacts go in a
  clean Project for the client or the next team. **Don't hand over the working Project**, because it holds
  draft and superseded material, and possibly internal notes.
- **What must never be stored in a shared Project (M8.1):** credentials, API keys and connection
  strings; customer personal data beyond what the task strictly needs; another client's material;
  HR or performance content; anything the client contract restricts. Everyone who can open the Project,
  including people added later, can retrieve it by asking.

## Under the hood

### In-context knowledge versus retrieval mode

```text
Small Project                          Large Project (retrieval mode, paid plans)
┌───────────────────────────┐          ┌───────────────────────────┐
│ instructions              │          │ instructions              │
│ ALL knowledge files       │ ← in the │ top-k retrieved chunks    │ ← only what the
│ conversation              │   window │ conversation              │   search found
└───────────────────────────┘          └───────────────────────────┘
```

- **In context:** Claude reads every file, every time. Recall is as good as long-context reading allows,
  but every chat pays for the whole knowledge base in tokens and usage.
- **Retrieval:** files are split into chunks, and the chunks most relevant to your question are pulled in.
  This scales to far more material, but **a chunk that isn't retrieved doesn't exist for that answer.**
  Questions that need *all* instances ("list every change to the payment terms across all amendments")
  are where retrieval fails quietly. It returns three of five and presents them as complete.

Practitioner counters: ask for **file and section references** for every claim; for exhaustive questions,
open the specific files in a chat or ask per document; and write good file names and headings,
because they help both retrieval and you.

### Why instructions outrank stale knowledge

Project instructions sit at a higher level of the hierarchy than knowledge (M2.3). A date or fact written
into instructions is treated as a standing rule, so when the knowledge file is corrected, the instruction can
still win. Keep facts in knowledge, where updating the file is the fix.

### Why meeting extraction invents owners

Claude is completing a table. An empty "Owner" cell is an unusual continuation, while a name that appeared
near the action in the transcript is a likely one. That pressure toward completeness is why you need an
explicit "UNASSIGNED" escape hatch and a quote column. The same mechanism invents plausible dates.

### Ask Your Org: live federated search

No central index means no stale index and no copy of the data. It also means latency, results that depend
on each source's own search quality, and permission-scoped answers. Treat it as a federated query, not a
knowledge graph.

## In production

**1. Client engagement workspace**
*Situation:* Your team starts a 6-month data-platform engagement.
*Right move:* Create one Project from the cluster template: README with an owner and a weekly refresh,
the signed SOW (versioned name), the org chart, the glossary and an empty decisions log. Instructions set
the audience, the citation rule and "SOW wins over notes; flag conflicts". Share it with "Can edit" for the
delivery team only.
*Why:* consistent context for everyone, with a single source of truth for each fact.
*Failure mode:* SOW v2 and v3 both in knowledge. Claude quotes the superseded payment milestones in a
client email.

**2. Sprint ceremonies**
*Situation:* Retro and planning notes pile up and nobody follows up on the actions.
*Right move:* After each ceremony, extract decisions and actions with an owner, due date and source quote.
Append decisions to `04-decisions-log.md` and push actions to the tracker. Next ceremony's agenda starts
from the open actions.
*Failure mode:* the actions table lists "Team" as owner. Nobody owns it, so nothing happens.

**3. Onboarding a new joiner**
*Situation:* A developer joins mid-engagement.
*Right move:* An onboarding Project (not the working one) with an architecture overview, the glossary, the
key ADRs and a "who to ask" list. Instructions: "explain for a new joiner; cite the file for every claim".
*Why:* fast ramp-up with less exposure to draft or restricted material.
*Failure mode:* giving them the working Project, including draft pricing and HR notes about the client team.

**4. Change request under deadline**
*Situation:* The client emails a change: add a second region before go-live.
*Right move:* In the engagement Project, ask for impacted requirements, deliverables, dates and risks,
citing the SOW sections and decisions. Then verify each impact with the tech lead. Send the client a
question list and an impact summary, not an estimate (M5.1 owns estimation).
*Failure mode:* Claude's impact list misses the data-residency constraint because the retrieval never
surfaced the clause. You find out at contract review.

**5. Audit preparation**
*Situation:* An auditor asks how a control was decided and evidenced.
*Right move:* Use Ask Your Org (where enabled) to *locate* the decision thread, the ticket and the
document. Record each source link. Then quote from the sources themselves.
*Failure mode:* pasting Claude's summary into the audit response as evidence.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| Facts written into Project instructions | They outrank corrected knowledge and go stale silently | Keep facts in knowledge files; instructions say *how* |
| Two versions of the same document in knowledge | Claude may quote the superseded one | One current version; archive or delete old ones |
| No owner or refresh date on the Project | It rots while people keep trusting it | Owner and cadence in the README; prune on schedule |
| Actions with "team" or inferred owners | Nobody owns them, or the wrong person does | Named owner or "UNASSIGNED"; quote column |
| Exhaustive questions in a large Project | Retrieval returns some matches, presented as all | Ask per document, or open the files directly |
| Two clients in one Project | Confidentiality breach through retrieval | One Project per engagement |
| Credentials or personal data in shared knowledge | Anyone with access can retrieve them | Never store them (M8.1); link to the vault instead |
| Treating Ask Your Org answers as evidence | Live, permission-scoped, only what was written down | Use it to find sources, then cite the sources |
| Handing the working Project to the client | Drafts and internal notes leak | Build a clean hand-over Project |

## Hands-on exercises

1. **Client-engagement Project.** From a sample pack (SOW, org chart, glossary, decisions log), build a
   Project with a README, instructions and named files. Ask ten questions and verify each answer against its source.
   **Done when:** all ten answers cite file and section, you have checked every citation by hand, and any
   wrong or uncited answer is logged with the fix (an instruction or file change) you made.
2. **Transcript to tracked outcomes.** Convert a 45-minute transcript into minutes, decisions and actions.
   Reconcile your version against a second learner's.
   **Done when:** every decision has a supporting quote, every action has a named owner or "UNASSIGNED", and
   the reconciliation lists each difference and which version the transcript supports.
3. **Project template for your cluster.** Design the README fields, the instruction block, the file
   numbering and the "must never contain" list. Get it reviewed.
   **Done when:** a reviewer from another team can create a new Project from it without asking you
   anything, and has signed off the never-store list against M8.1.
4. **Enterprise search** (where enabled). Answer three organisational questions through Ask Your Org.
   **Done when:** each answer lists every source it used, you have opened each source, and you have noted
   one thing the search could not find.
