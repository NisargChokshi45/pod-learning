# M4.2 — Skills and reusable workflows

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| CORE | All clusters | 1.5 | "M2.4 concepts" (**forward reference**: M2.4 *Prompt templates and evaluation* is an Advanced, Level 3 module. The minimum you need is inline below) · M3.2 |

**Objective:** turn repeatable work into Skills that **trigger reliably** and can be **shared under
governance**.

> A Skill is a prompt you stopped retyping. You add the steps, the template and the checks that made it
> work, package them in a folder, and Claude loads that folder when the task calls for it. The hard part is
> not the instructions. It's the one-line description that decides *when* the Skill fires.

**The "M2.4 concepts" you need now** (the full treatment is at Advanced):
- **Prompt template:** a prompt with fixed parts (role, steps, format) and variable slots (`{ticket}`,
  `{week}`). It's the simplest reuse mechanism.
- **Evaluation:** before you call a reusable prompt "done", run it on several realistic inputs, compare the
  outputs against what you expect, and keep those inputs as a regression set. At this level, "five trigger
  phrasings plus three real inputs, checked by hand" is enough.

---

## TL;DR

- A **Skill** is a folder: a `SKILL.md` (frontmatter with `name` and `description`, then instructions),
  plus optional **scripts** and **resources** such as templates and examples. Claude loads it **when
  relevant**. You don't paste it in.
- The **description is the trigger.** Only the name and description sit in context until Claude decides the
  task matches. A vague description means the Skill never fires. An over-broad one means it fires on everything.
- **Choose the mechanism by three questions:** how often does it repeat, who else needs it, and does it
  involve files or scripts? The options are prompt template, Project instructions, Skill and scheduled task.
- **Anthropic Skills** for Excel, Word, PowerPoint and PDF ship built in. **Custom Skills** upload as a ZIP.
  Both need the **"Create and edit files"** setting [app].
- **Keep it short.** A long Skill dilutes its own instructions. Put the bulky material (templates, examples)
  in resource files that load only when a step needs them.
- **Governance:** a named owner, a version, no secrets, no personal data. Share it with people or publish it to the
  org library, where an admin can review and scan it.
- **One format, every surface:** the same `SKILL.md` runs in the app, in Claude Code and through the API.
  Each surface keeps its **own copy**, and scripts run with different reach on each, so publish from one versioned source.
- **Plugins** bundle Skills with connectors and more. Install only from your organisation's **approved list**.

## Concepts

### 1. What a Skill is

**A folder Claude loads when relevant** [app][code][api]:

```text
status-report/
├── SKILL.md              ← required: frontmatter (name, description) + instructions
├── templates/
│   └── weekly-status.md  ← resource: the house template
├── examples/
│   └── good-report.md    ← resource: one worked example
└── scripts/
    └── rag_from_jira.py  ← optional: deterministic step (runs in the code sandbox)
```

- **`SKILL.md`** holds the instructions: when to apply them, the steps, the checks and pointers to resources.
  Its YAML frontmatter needs **`name`** (≤64 chars; lowercase letters, digits and hyphens; must not contain
  "anthropic" or "claude") and **`description`** (non-empty, ≤1,024 chars, no XML tags) [app][api, GA].
- **Scripts** do work that must be deterministic, such as parsing a CSV, computing RAG status or filling a
  template. Code gives the same answer every run, and prose instructions don't.
- **Resources** are templates, examples, style guides and reference tables. Claude reads them when a step
  needs them.

**Anthropic Skills** [app, all plans; no GA/BETA label shown in the app]: Excel, Word, PowerPoint and PDF Skills that Claude uses automatically when
you ask for those files. They are why "make me a deck" produces a real `.pptx` and not Markdown.

**Custom Skills** [app][code][api]: in the app you upload a ZIP of the folder (Customize → Skills → "+" → Create skill → Upload a
skill). You can also create one in conversation.

**Availability:** all plans [app], and the **"Create and edit files"** setting must be on. This is the same
setting M1.3 flagged as the silent blocker. If a Skill "does nothing", check it first.

> **Syllabus says:** Skills are GA on all plans; the setting is "Create and edit files". · **Current
> (verified 2026-11-28, support.claude.com/en/articles/12512180 and /12111783):** Skills are available
> Free→Enterprise, but the app page shows **no GA/beta label**. The platform docs
> (platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) list *custom* Skill uploads on Pro, Max,
> Ultra, Team and Enterprise only, so **Free-plan custom Skills are unverified** (the sources disagree). Enterprise
> owners must also enable Skills in the Policy tab. The toggle is **"Code execution and file
> creation"** in the older settings layout and **"Create and edit files"** in the updated one (Settings →
> Capabilities; on Team and Enterprise, under Organization settings → Capabilities).

### 2. Choosing the mechanism

| Mechanism | Repeats | Who needs it | Files or scripts? | Use when |
|---|---|---|---|---|
| **Prompt template** (saved text you paste) | Occasionally | Just you | No | A one-person, low-frequency task. Cheapest to change |
| **Project instructions** (M3.3) | Every chat *in that Project* | The Project's members | Knowledge files, no scripts | The behaviour belongs to *one body of work* (a client, a team function) |
| **Skill** | Often, across contexts | You, a team or the org | Yes: templates, examples, scripts | The *procedure* is the reusable part and it should fire wherever the task turns up |
| **Scheduled task** | On a clock | Whoever receives the output | Via connectors | The trigger is *time*, not a request (preview of M4.3 automation) |

**Decision rule:** ask *how often* it repeats, *who else* needs it, and *whether files or scripts* are
involved. Two of three in the "Skill" column means build a Skill.

Common confusions:
- **Project instructions vs Skill.** Project instructions say *where you are* ("this is the Northwind
  engagement; their glossary is attached"). A Skill says *how to do a kind of task* ("this is how we write a
  defect report"). The defect-report Skill should work in every Project.
- **Skill vs scheduled task.** A Skill still waits for a request. If nobody should have to ask (for example a
  Monday 09:00 status pull), that's automation. M4.3 at Advanced covers it.

### 3. Writing a Skill without code

**The name and description decide when it fires. This is where most Skills fail.**

| Description | Problem |
|---|---|
| `Helps with reports.` | Too vague. It matches nothing specific, so Claude rarely picks it, or picks it for the wrong report |
| `Use for anything to do with projects, status, updates, Jira, or the team.` | Too broad. It fires on a Jira question, a team-lunch message, everything |
| `Writes the weekly client status report in our house template (RAG, milestones, risks, asks). Use when asked for a weekly status, client update or status report for an engagement.` | Good. It says what the Skill produces, names the template and lists the phrasings that should trigger it |

A good description says **what it produces**, **for whom or in what standard**, and **the words people
actually use** when they need it. Write it in the third person, as a capability, not a command.

**Step instructions** are numbered, with checks:
1. Gather inputs (ask for the missing ones, don't invent them).
2. Fill the template from `templates/…`.
3. Run the checklist.
4. Output in the stated format.

**Checklists** are conditions the output must meet before Claude replies. For example: every risk has an owner,
every date is absolute, RAG is justified in one line.

**Templates and examples as resources.** Keep them in files, not in `SKILL.md`. One good example teaches the
format better than a paragraph, but the M2.1 overfitting rule still applies: vary the examples.

**Test the trigger phrases.** Write five different ways a colleague would ask for this, including one
indirect phrasing ("can you get the Contoso update ready for Friday?"), plus two **near-misses** that
should *not* trigger it ("what's the status of PR 412?"). Run each in a fresh chat and record fire or no-fire.

**Keep it short enough to stay reliable.** Every line in `SKILL.md` competes for attention once the Skill
loads. If the file is past a page or two, move detail into resources and leave a pointer ("for the risk
taxonomy, read `reference/risk-levels.md`").

### 4. Sharing and governance

- **Sharing with people or groups** [app]: on Team and Enterprise you can share a Skill with colleagues.
  Recipients get it view-only.
- **Publishing to the organisation library** [app]: "Publish to org" sends the Skill to the org library.
  Owners can require **review** and a **security scan** first.
- **Admin policy** [app]: owners control Skills and plugins centrally.

> **Syllabus says:** share with people or groups; admin policy under Organisation settings → "Plugins and
> skills". · **Current (verified 2026-11-28, support.claude.com/en/articles/12512180):** the path is
> **Organization settings → "Plugins & skills"** (with an ampersand), Policy tab. Sharing with **groups is
> Enterprise-only**. Shared Skills are view-only for recipients.

- **Versioning and ownership.** Every shared Skill has a named owner, a version (in the frontmatter or a
  `CHANGELOG.md` resource) and a review date. A Skill nobody owns rots, because the template changes and
  the Skill keeps producing the old one.
- **No secrets and no personal data inside a Skill.** A Skill is a file that gets copied, shared, synced to
  laptops and attached to API containers. An API key in `scripts/` or a customer list in `examples/` leaks
  everywhere the Skill goes. Use connectors for access and synthetic data for examples (M8.1).

**Governance checklist (before you share or publish)**

| # | Check | Pass when |
|---|---|---|
| 1 | Owner | A named person, not a team alias |
| 2 | Version | A version number plus a one-line change note |
| 3 | Description | Triggers on ≥4 of 5 intended phrasings and on 0 of 2 near-misses |
| 4 | Secrets | No keys, tokens, passwords or internal URLs with credentials. Grep the folder |
| 5 | Personal or client data | Examples are synthetic or anonymised |
| 6 | Scripts | Read by a second person. No network calls the policy doesn't allow. No destructive operations |
| 7 | Scope | Does one job. If it needs "and also…", split it |
| 8 | Length | `SKILL.md` stays short. Bulk material lives in resources |
| 9 | Licence | Templates and examples are yours to share (M8.3) |

### 5. One format, every surface

The same `SKILL.md` folder works:
- in the **apps** [app] (uploaded or created in chat);
- in **Claude Code** [code] (`.claude/skills/` in a repo, or `~/.claude/skills/`; full treatment in M6.4);
- through the **API** [api, GA] (uploaded via `/v1/skills`, listed in `container.skills` alongside the code
  execution tool; M7.2).

**"One format" is not "one copy".** Per the platform docs, custom Skills **do not sync between the app and the
API**: each surface holds its own upload, and Claude Code reads its own folders. Keep one versioned source (a
Git repo) and publish each copy from it. Two portability traps:
- **Frontmatter.** Claude Code accepts extra fields (`allowed-tools`, `disable-model-invocation`, `context`,
  `paths`…). Outside Claude Code only `name`, `description`, `license`, `compatibility`, `metadata` and
  `allowed-tools` are accepted, and **other fields fail the upload** [code][app][api; verified 2026-11-28,
  code.claude.com/docs/en/skills].
- **Runtime.** Scripts run in different places with different reach (table under *Under the hood*). A script
  that calls an internal API works in Claude Code and fails on the API, which has no network access.

**Account Skills sync into Claude Code** [code]: when you sign in to Claude Code with your claude.ai
account, your account and org Skills download into it. The sync is one-way.

> **Syllabus says:** account Skills sync into Claude Code. · **Current (verified 2026-11-28,
> code.claude.com/docs/en/skills):** confirmed for terminal sessions signed in with a claude.ai account
> (v2.1.273+); this is the one documented exception to "custom Skills don't sync across surfaces". Skills land in `~/.claude/skills/synced/`. The sync is **download-only, and local edits are
> overwritten**. It doesn't happen with an API key, Bedrock, bare mode or `--safe-mode`. Opt out with
> `"syncClaudeAiSkills": false`.

Practical consequence: **edit the source, not the synced copy.** If you change a synced Skill locally, the
next sync silently throws your fix away.

### 6. Plugins from the user side

A **plugin** is a bundle installed as one unit: several Skills, plus the connectors and other pieces a
workflow needs. For example, a "sales-ops" plugin might bundle a CRM connector with account-research and
proposal Skills.

**The approved plugin list, and why it exists:** a plugin can carry connectors (data access) and commands
or agents (actions). Installing one is a **permission grant**, not a convenience. The org keeps an approved
list for the same reason it approves connectors (M4.1). Someone has checked what the plugin can read, what it
can do and who maintains it. Your org's approved list is **undefined in source**: find out where it lives
before you install anything.

> **Syllabus says:** plugins are bundles of Skills, connectors and settings installed into agentic sessions.
> · **Current (verified 2026-11-28, claude.com/docs/plugins/overview and support.claude.com/en/articles/13837433):**
> a plugin packages **skills, MCP connectors, commands and agents** ("settings" isn't listed). Plugins work in
> **chat (web, desktop, mobile), Cowork and Claude Code**, not only agentic sessions. Agents run only in
> Cowork and Claude Code. Admins set each plugin to *Installed by default*, *Available to install*,
> *Required* or *Not available* under Organization settings → Plugins & skills.

## Under the hood

### Progressive disclosure: why the description is the trigger

Skills are designed to cost almost nothing until they're needed. Loading happens in three stages:

```text
Stage 1  always in context    name + description of every enabled Skill  (~100 tokens each)
            │  Claude judges: "does this task match a description?"
            ▼
Stage 2  on match             the body of SKILL.md                       (aim for under ~5k tokens)
            │  a step says "use templates/weekly-status.md"
            ▼
Stage 3  on demand            resources and scripts                      (files read when needed; scripts run, only output enters context)
```

Token figures are from the platform docs (verified 2026-11-28) [api]. Mechanically, Claude reads `SKILL.md`
and resources with ordinary file reads (bash) in its environment, which is why Skills need a code/file
environment at all.

Consequences:
- **At decision time, Claude sees only the description.** It can't read your brilliant steps to decide
  whether they apply. The description has to carry the matching signal on its own.
- **You can install many Skills cheaply**, because stage 1 is tiny. This is also why a too-broad
  description is harmful: it wins matches it shouldn't, and the wrong instructions load.
- **Resources don't bloat the context** unless a step asks for them. Put the 3-page template there, not in
  `SKILL.md`.

### Why scripts beat prose for deterministic steps

"Compute the RAG status from the milestone dates" written as prose gets *estimated* (the M3.5 failure mode).
A script in `scripts/` gets *executed* and returns the same answer every time; the script's code never
enters context, only its output. Rule: **judgement in `SKILL.md`, arithmetic and formatting in scripts.** This
is also why Skills in the app require the "Create and edit files" (code execution) setting.

Where a script runs decides what it can reach (platform docs, verified 2026-11-28):

| Surface | Runs in | Network | Governance consequence |
|---|---|---|---|
| App [app] | Anthropic's code-execution sandbox | Full, partial or none, per user/admin settings | Network-dependent steps may work for one user and not another |
| API [api] | The code-execution container | **None**; no runtime package installs | Pre-installed packages only; design for offline |
| Claude Code [code] | **Your machine**, via Bash | Same as any program you run | A shared Skill's script runs with *your* credentials and files: review it like code you'd install |

### A complete example: the defect-report Skill

```markdown
---
name: defect-report
description: Writes a defect report in the team's QA template (summary, environment, steps to reproduce, expected vs actual, severity with justification, evidence). Use when asked to write up, log, file or report a bug, defect or regression from notes, logs or screenshots.
---

# Defect report

Produce one defect report per distinct defect, using `templates/defect.md`.

## Steps
1. Collect inputs: what was observed, where (app, version, environment), how to reproduce, and the evidence
   (logs, screenshots). If any is missing, ask for it. Don't invent reproduction steps or versions.
2. Fill `templates/defect.md`. Write the steps to reproduce as numbered, atomic actions a tester can
   follow cold.
3. Set severity from `reference/severity.md`. Justify it in one line that quotes the user impact.
4. Quote log lines verbatim, with timestamps. Never paraphrase an error message.

## Checklist before replying
- [ ] Expected and actual are both stated, and they differ.
- [ ] Every step is one action; no "etc."
- [ ] No customer names, emails, tokens or IPs. Replace them with placeholders (CUSTOMER_A, <TOKEN>).
- [ ] Anything inferred, not observed, is marked "unconfirmed".

## Output
The filled template in Markdown, then a line "Open questions:" listing anything you had to ask about or assume.
```

Folder: `defect-report/SKILL.md`, `templates/defect.md`, `reference/severity.md`. There are no scripts, because
nothing here is arithmetic.

Notice what the description does. It names the output and the standard, and it lists the verbs people
use ("write up, log, file, report") and the nouns ("bug, defect, regression"). It won't match "what's the
status of bug 412?", because nothing there asks for a report to be written.

### Skills vs plugins vs connectors

| Unit | What it adds | Risk surface |
|---|---|---|
| Connector (M4.1) | **Access**: tools that read or act on an external system | Data exposure, write actions |
| Skill | **Procedure**: instructions, templates, scripts | Wrong output, leaked content inside the folder, scripts that misbehave |
| Plugin | **A bundle** of the above, plus commands and agents | The union of everything it contains |

## In production

**1. Weekly client status across six engagements**
*Situation:* Six delivery leads each write a Friday status report, all slightly different. The PMO wants one format.
*Right move:* Build a `client-status` Skill: house template as a resource, a script that computes RAG from
milestone dates, and a checklist (owners on risks, absolute dates). Publish it to the org library with the
PMO lead as owner.
*Why:* it repeats weekly, many people need it, and it has a template and a script. That's all three Skill criteria.
*Failure mode:* putting the template in each engagement's Project instructions. Six copies drift within a month.

**2. A Skill that never fires**
*Situation:* A colleague built a `proposal-section` Skill. Asking "draft the security section for the Fabrikam
bid" produces generic text, and the Skill isn't used.
*Right move:* Read the description: "Proposal helper." Rewrite it as "Drafts a bid or RFP response section in
the house proposal template… Use when asked to draft, write or respond to a section of a bid, proposal,
tender or RFP." Re-test five phrasings.
*Why:* only the description is visible at match time.
*Failure mode:* adding more instructions to the body. That changes nothing about triggering.

**3. A secret in a shared Skill**
*Situation:* A `jira-digest` Skill on the org library has a script with a hard-coded Jira API token "for convenience".
*Right move:* Unpublish it, rotate the token, and treat it as a credential leak (M8.1). Rebuild the Skill to
use the approved Jira connector for access.
*Why:* Skills are copied, shared, synced to laptops and attached to API containers. A token in one spreads to all of them.
*Failure mode:* deleting the line and republishing without rotating. The old version already synced.

**4. Project instructions or a Skill for onboarding?**
*Situation:* The platform team wants new joiners to get answers about *their* runbooks and services.
*Right move:* Use a **Project** (knowledge files plus instructions, M3.3), not a Skill. The reusable part is the
*body of knowledge*, not a procedure.
*Failure mode:* a Skill with 40 pages of runbooks pasted into resources. It's slow, triggers awkwardly and goes stale.

**5. Fixing a synced Skill locally**
*Situation:* In Claude Code you edit a synced copy of the org's `defect-report` Skill to add a field. Next
morning, the field is gone.
*Right move:* Change the source (the org Skill, via its owner), bump the version, and let the sync bring
it down.
*Why:* the sync is download-only, so local edits get overwritten.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| A vague description ("helps with reports") | Only the description is seen at match time, so the Skill never fires | Say what it produces, in what standard, and the phrasings that trigger it |
| An over-broad description | It fires on unrelated tasks and loads the wrong instructions | Name the specific output. Test near-misses |
| A 6-page `SKILL.md` | Instructions dilute. Reliability drops | Keep it short. Move bulk into resources |
| Prose instructions for arithmetic | Estimates, not computation | A script in `scripts/` |
| API keys or tokens inside the folder | The Skill is copied everywhere, so the secret is too | Connectors for access. Rotate anything that leaked |
| Real client data in `examples/` | Personal data spreads with every share and sync | Synthetic or anonymised examples |
| A Skill with no owner or version | The template changes and the Skill keeps producing the old one | Named owner, version, review date |
| Installing an unapproved plugin | It's a permission grant: connectors and actions | Use the approved list only |
| Editing a synced copy | The next sync overwrites it | Edit the source and bump the version |
| "Does nothing" and nobody checks the setting | "Create and edit files" is off | Check the setting first |

## Hands-on exercises

1. **Build a Skill for one recurring task in your role**, with at least one template resource. Test five
   different trigger phrasings plus two near-misses, each in a fresh chat.
   **Done when:** it fires on ≥4 of 5 intended phrasings and on 0 of 2 near-misses, the output matches the
   template, and you've recorded the test table (phrasing → fired? → output OK?).
2. **Review a peer's Skill** against the governance checklist above, and submit it to the library (or a
   sandbox library, if yours isn't enabled).
   **Done when:** every checklist row has a pass/fail with evidence, at least one improvement is made and
   re-tested, and the owner and version are set.
3. **Convert a Project instruction set into a Skill** and compare the behaviour on the same three tasks,
   inside and outside the Project.
   **Done when:** you can show, with outputs, one thing the Skill does better (it fires outside the
   Project, carries a template) and one thing the Project still does better (it holds client knowledge).
   You can state which belongs where in one sentence.
