# M2.3 — Context engineering and instruction hierarchy

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| CORE | All clusters | 1.5 | M2.1 (prompting fundamentals) |

**Objective:** control what Claude knows during a task, and know which instruction wins when two
conflict.

> Prompting (M2.1) is about the message you type. Context engineering is about **everything else in the
> window**: settings, Project files, memory, tool results, and sixty turns of history. On long or shared
> work, the context does more to shape the answer than the prompt does. You manage it like any other
> budget.

---

## TL;DR

- **Context is everything in the window**, not just your message: org settings, Project instructions,
  preferences and Styles, memory, uploaded files, connector results, and the conversation so far.
- **The window is a budget.** Every irrelevant file, stale turn and verbose tool result costs attention
  and tokens. Curate what goes in.
- **App hierarchy:** organisation/admin → Project instructions → personal preferences → the current
  message. **Test precedence; don't assume it.** Run a deliberate conflict and see which instruction wins.
- **Ground on documents:** choose paste, upload or Project knowledge on purpose. Say "answer only from the
  material provided". Ask for **quotes before conclusions**, then **check the quotes**.
- **Long context:** put the material first and the question last. Summarise, then ask. Chunk big inputs.
  Watch for overflow: forgotten instructions, a quality drop, drift back to generic answers.
- **Hygiene:** one task per chat. Branch by editing. Carry state forward with **a summary you wrote**,
  not a 60-turn scroll.
- **Memory is context.** Switch it off, or use incognito, for sensitive work.
- **Team context is shared infrastructure.** When two people's prompts contradict each other, fix the
  shared instructions, versioned and reviewed, not each prompt.

## Concepts

### 1. What context actually is

**Everything in the window.** For one reply, Claude sees a single token sequence assembled from:

| Layer | Who controls it | Persists across chats? |
|---|---|---|
| Organisation settings and instructions (Team/Enterprise) | Owners and admins | Yes |
| Project instructions + Project knowledge | The Project owner and editors | Within the Project |
| Personal preferences (account Instructions) and Styles | You | Yes |
| Memory (topics, past-chat search, project memory) | Claude writes it; you control and review it | Yes, unless paused or off |
| Uploaded files | You, per chat | No, unless they're Project knowledge |
| Connector and tool results (Drive, Slack, web search…) | Fetched during the chat | No |
| The conversation so far | You and Claude | Within the chat |

**The window as a budget you are spending.** Current models have very large windows (1M tokens on the
5.x generation, M1.2), but *capacity is not the same as attention*. Two costs grow with every addition:

1. **Attention dilution.** Relevant facts compete with irrelevant ones. A 300-page dump with 3 relevant
   pages answers worse than those 3 pages alone.
2. **Usage and latency.** More tokens mean more cost, slower replies, and earlier hits on usage limits.

So every addition should earn its place: *does Claude need this to do this task?*

### 2. Instruction hierarchy in the Claude apps

**The order, broadest first** [app] (behaviour, not a feature; status tag n/a):

```text
Organisation / admin settings       ← set by owners; constrains everything below
   ↓
Project instructions                ← this workspace's standing rules
   ↓
Personal preferences (Instructions, Style)
   ↓
The current message                 ← most specific, most recent
```

**What wins on conflict.** The higher layers set the frame. Organisation instructions are documented to
take precedence over personal ones on direct conflict (support.claude.com/en/articles/10185728, search
snippet; Team/Enterprise org instructions are limited to 3,000 characters). Admin *settings* aren't
instructions at all: they're hard capability gates. If file creation or a connector is disabled, no prompt
re-enables it. Between Project instructions, preferences and the message, the model weighs them as
context. More specific and more recent instructions usually win for *this task*, but that's model behaviour,
not a guaranteed rule. That's why the next point matters.

**Test precedence rather than assume it.** Precedence is an empirical property of a configuration. Prove it
with a deliberate conflict:

| Test | Setup | Pass if |
|---|---|---|
| T1 Project vs preference | Preference: "use bullet points". Project instruction: "reply in prose paragraphs, no bullets" | Answers inside the Project come in prose |
| T2 Message vs Project | Project: "all costs in EUR". Message: "give this one in USD" | The one-off override is honoured for that answer only, and the next answer is back in EUR |
| T3 Project vs knowledge file | Project: "contract wins over meeting notes". Upload notes and a contract that disagree on the notice period | The answer uses the contract's figure *and flags the conflict* |

Design each test so the outcomes are **observable** (format, currency, a cited figure), and so each one
isolates a single pair of layers. Run each test twice, because one run can be luck. Record the result
next to the Project instructions so the next editor knows what was proven.

**Pointers, not covered here:**
- Claude Code has its own hierarchy (managed policy → user `~/.claude/CLAUDE.md` → project `CLAUDE.md` →
  `CLAUDE.local.md`, plus rules and imports). That is **M6.2**. Note one difference there: Claude Code
  **concatenates** those files rather than letting one override another (code.claude.com/docs/en/memory).
  That's another reason to test rather than assume.
- On the API, the operator's **system prompt** is the top layer you control. That is **M7.1**.

### 3. Grounding with documents

**Paste versus upload versus Project knowledge:**

| Method | Best for | Watch out for |
|---|---|---|
| **Paste** into the message | Short excerpts (a clause, a log snippet) you've already trimmed and redacted | Easy to paste too much. No file name for Claude to cite |
| **Upload** to the chat [app, GA] | One-off documents for this task (a contract, a CSV) | Gone when the chat ends. Re-upload elsewhere costs context again |
| **Project knowledge** [app, GA; retrieval on paid plans] | Reference material reused across many chats (glossary, SOW, runbooks) | Goes stale unless someone refreshes it (M3.3). Large knowledge switches to retrieval, so not every page is in view for every answer |

**"Answer only from the material provided."** This instruction turns a general-knowledge question into a
closed-book reading task. Add the escape hatch: *"If the material doesn't answer it, say 'not in the
provided material'."* Without the escape hatch, Claude fills gaps with plausible general knowledge.

**Quotes before conclusions, then check the quotes.** Ask for supporting quotes first, then the answer:

```text
<contract>…</contract>

Question: what notice period applies if we terminate for convenience?
First, extract the exact clauses relevant to this question as verbatim quotes, each with its
clause number and page. Then answer using only those quotes. If the quotes don't settle it, say so.
```

Then **check each quote against the source**: search the document for the exact string. A quote that
doesn't exist, or exists but says something different in context, is the most common grounding failure.
Quote extraction makes errors *checkable*. It doesn't make them impossible (M8.2).

### 4. Long-context practice

- **Material first, question last.** Put long documents at the top and the instruction and question at the
  end. Instructions placed last are the freshest tokens when generation starts (M2.1 under the hood).
- **Summarise-then-ask.** For a 100-page contract, first ask for a structured summary (parties, term,
  fees, liability, termination, data) with clause references. Check it, then ask your real questions
  against the document *plus* the checked summary.
- **Chunking.** Split very large or many-document inputs by section, run the same extraction on each chunk,
  then combine the results in a final step. This is a prompt chain (M2.2 §4).
- **Recognising overflow.** You rarely get an error. You get symptoms:

| Symptom | Example |
|---|---|
| **Forgotten instructions** | "No bullet points" from turn 2 is ignored at turn 45 |
| **Quality drop** | Answers get vaguer; specifics from the documents disappear |
| **Drift back to generic answers** | Advice reads like a textbook, not like *your* system |
| **Contradicting earlier decisions** | It re-proposes an option you rejected an hour ago |

- **When to start fresh with a written handover:** when two or more symptoms appear, after a major change
  of direction, or before a new phase of the work. Write the handover yourself, or have Claude draft it and
  then **edit it**. You own what carries forward.

**Handover summary template**

```markdown
## Handover — <task name> — <date>
**Goal:** <one sentence: what we're producing and for whom>
**Decisions made (don't revisit):**
- <decision> — <why, one clause>
**Constraints:** <hard limits: format, audience, policy, deadlines>
**Rejected options:** <option> — <reason>   ← stops the new chat re-proposing them
**Current state:** <what's drafted; attach the latest version, not the history>
**Open questions:** <what still needs an answer>
**Next step:** <the exact first thing to do in the new chat>
**Sources:** <files and Project knowledge the new chat needs; re-attach them>
```

### 5. Conversation hygiene

- **One task per chat.** A chat that did the RFP summary, then a pricing question, then an email has three
  tasks' worth of context interfering with one another.
- **Branching by editing an earlier turn** (M1.3 §1). Fix the spec where it went wrong. Don't stack corrections.
- **Carry state forward deliberately with a summary you wrote.** The next chat should start from a curated
  state (the handover above), not from "continue where we left off" or a pasted 60-turn transcript.
  Curating it is where you catch errors before they propagate.

### 6. Memory and personalisation as context

- **What memory stores:** summaries of durable facts about you and your work (topics), and optionally access to
  your past chats. **How it changes answers:** those facts are inserted as context, so ambiguous references get
  resolved by them, and defaults (stack, client, tone) get assumed (M1.3 §3).
- **Switching it off, or using incognito, for sensitive work.** Pause memory, turn off account memory inside a
  client Project, or use an incognito chat. Pick by scope: one chat → incognito; one engagement → Project with
  account memory off; a period → pause. Remember that incognito chats still appear in Team and Enterprise exports.
- Preferences and Styles are context too. A "concise" style can quietly cut the caveats a legal answer needs.
  Switch it off when it fights the task.

### 7. Context for teams

- **Shared Project instructions** are the team's system prompt. Everyone on the Project inherits them.
- **Instruction templates:** a standard skeleton (role, audience, standards, conflict rules, output
  formats, "what not to do") so Projects look alike across engagements.
- **Versioning and review:** keep the master copy of the instructions in Git or a shared doc, with an owner,
  a changelog line per edit, and peer review. The precedence tests from §2 double as the regression tests.
- **Two people's prompts contradicting is a context problem, not a prompting one.** If Alice's prompts say
  "formal" and Bob's say "casual", outputs diverge because the *shared* context doesn't decide. Fix it
  once, in the shared instructions (and Style or Skill), not by policing every prompt.

## Under the hood

### Assembly: one sequence, many authors

At inference time there are no separate "channels" for settings, memory and files. Everything is
serialised into one token sequence, roughly:

```text
[system: product + org + Project instructions + preferences + memory]
[Project knowledge / retrieved chunks]  [uploaded files]
[turn 1 user] [turn 1 assistant] … [tool results] … [turn N user]  → generate
```

Two consequences follow:
1. **Precedence is learned behaviour, not a lock.** The model has been trained to weight system-level and
   operator instructions above user turns, and specific above general. But it's still reading text. A
   strongly worded later instruction can win where you expected an earlier one to. Hence: test it.
2. **Retrieval changes what's visible.** When Project knowledge grows past what fits comfortably, the app
   retrieves relevant chunks per question instead of loading everything [app]. A fact that sits in the
   Project can still be *absent* from a given answer's context. "Quote first" exposes this.

### Why long chats degrade

Each new turn adds tokens, and the early instructions become a shrinking fraction of the context. Attention
favours recent and salient content, and conversational history full of drafts and corrections pulls towards
earlier patterns. How the app handles a chat that outgrows the window isn't covered by the sources checked
for this pack (**unverified**). The fix doesn't depend on it: start fresh with a curated state.

### Why quotes help and still need checking

Asking for verbatim quotes forces the model to locate the support *before* concluding, which reduces
unsupported answers. But a model generates quotes the same way it generates everything else. It can produce a
near-quote with a changed number, or merge two clauses. The check is mechanical: exact-string search in the
source. That asymmetry (cheap to check, expensive to miss) is why quote-first is the default for document Q&A.

### Contradictory instructions resolve unpredictably

If the Project says "≤200 words" and your preference says "be thorough", the model must trade them off. Small
wording or ordering changes can flip the outcome between runs. That shows up as "inconsistent answers"
(M2.2 exercise 4). The robust fix is to **remove the conflict**, or to **state the tie-break rule**:
"when length and completeness conflict, completeness wins; flag that the limit was exceeded."

## In production

**1. Q&A over a 100-page contract**
*Situation:* Legal wants answers on termination, liability caps and data return from a vendor MSA.
*Right move:* Upload it. Ask for a structured summary with clause and page references first, and check five of
them. Then for each question: "quote the relevant clauses verbatim, then answer only from them; say 'not in the
contract' if absent." Search each quote in the PDF before it goes in the memo.
*Failure mode:* one big "summarise the risks" prompt. You get fluent output with a liability cap that's off by a
zero and no way to see it.

**2. Onboarding a new joiner through a Project**
*Situation:* New engineers keep asking the same questions about the client's architecture.
*Right move:* An onboarding Project with instructions ("answer from the knowledge files; cite the file; say
when it's not covered"), plus a curated knowledge set: architecture overview, glossary, runbooks, ADR index.
Test precedence (instructions vs a conflicting old runbook). Name an owner and a monthly refresh (M3.3).
*Failure mode:* a dump of 80 stale Confluence exports. Retrieval surfaces the 2023 design as current.

**3. Keeping a week-long analysis coherent**
*Situation:* A capacity-planning analysis runs Monday to Friday. By Wednesday the chat is 70 turns long and
re-proposes an option rejected on Monday.
*Right move:* End each day with a handover (template in §4). Each morning, start fresh with the handover and
the current draft attached. Rejected options are listed explicitly.
*Why:* curated state beats accumulated state. The handover is also the audit trail.

**4. Two leads, two voices**
*Situation:* Client updates from the same Project read formal one day and chatty the next, depending on who
prompted.
*Right move:* Treat it as a context defect. Add the voice and audience to the shared Project instructions (or a
shared style or Skill), version the change, and run a two-prompt test from each lead.
*Failure mode:* a style guide in a wiki that nobody's prompts reference.

**5. Hidden precedence surprise**
*Situation:* A Project instruction says "always include a risks section", but outputs omit it for one engineer.
*Right move:* Check the layers. Their personal style is "Concise", and their Instructions say "no boilerplate
sections". Run the T1-type conflict test and record the result. Make the Project instruction explicit about
priority: "the risks section is mandatory even when brevity is requested."

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| Uploading everything "so Claude has context" | Dilutes attention, costs usage, and retrieval may surface the wrong file | Curate: only what this task needs |
| Assuming the Project instruction always wins | Precedence is model behaviour, not a lock | Run a deliberate conflict test and record it |
| "Answer only from the document" with no escape hatch | Gaps are filled with plausible general knowledge | Add "say 'not in the material' if absent" |
| Trusting quotes without searching the source | Near-quotes with altered figures look authoritative | Exact-string check every quote you rely on |
| Question at the top, 100 pages below | Instructions get buried | Material first, question last |
| "Continue from yesterday" in a 70-turn chat | Overflow symptoms, re-proposed rejected options | Fresh chat with a written handover |
| Handover generated by Claude and never read | Errors propagate with authority | Edit and own the handover |
| Fixing team inconsistency prompt by prompt | The shared context still doesn't decide | Shared, versioned, reviewed instructions |
| Memory on for NDA work across clients | Cross-client facts leak into answers | Project with account memory off, pause, or incognito |

## Hands-on exercises

1. **Precedence lab.** Build a Project with instructions and five documents. Design three tests that prove
   which instruction wins (use the §2 table as a pattern: one pair of layers per test, observable outcome).
   **Done when:** each test has run twice with the same result, the outcomes are recorded next to the
   instructions, and at least one test shows a conflict being *flagged*, not just resolved.
2. **Quote-mandatory Q&A.** Run long-document Q&A (≥40 pages) with mandatory verbatim quote extraction for
   five questions.
   **Done when:** every quote has been exact-string searched in the source, and you've recorded how many were
   exact, how many were near-quotes and how many were missing, with the fix for each non-exact one.
3. **Rescue a degraded chat.** Take (or simulate) a 60-turn chat showing overflow symptoms. Diagnose which
   symptoms appear, write a handover with the §4 template, and finish the task in a fresh chat.
   **Done when:** you can name at least two symptoms with turn references, and the fresh chat completes the
   task without re-proposing any rejected option.
4. **Team instruction set.** Write a team instruction set for a live project and get it peer-reviewed.
   **Done when:** it has an owner, a version line, an explicit tie-break rule for at least one likely
   conflict, and the reviewer has run one precedence test against it.
