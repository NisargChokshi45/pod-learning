# M3.2 — Documents, files, images and Artifacts

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| CORE | All clusters | 1.5 | M2.1 (prompting fundamentals), M8.1 (data privacy) |

**Objective:** analyse any file Claude accepts, and produce finished output in the right form, instead of
pasting text into an email.

> Two skills live in this module. **Input:** get a correct, checkable reading out of a PDF, a workbook or a
> photo. **Output:** put the result in the container its next reader needs. Most file mistakes are a
> confident wrong reading (an input problem) or a good answer in the wrong place (an output problem).

---

## TL;DR

- Claude reads PDF, DOCX, XLSX, CSV, TXT, HTML, ODT, RTF, EPUB, JSON and more. In the app the limits are
  **500 MB per file, 20 files per chat, PDFs up to 1000 pages, with visual analysis only up to 100 pages** [app].
  The API has its own, different limits [api]. Never mix the two up.
- **Vision is approximately right.** Small text, dense tables, exact measurements and handwriting are where
  it fails. When "approximately right" means wrong (prices, part numbers, dimensions), check against the source.
- **Artifacts** are the output layer [app]: Docs, Slides, Design, data views, code, sites and diagrams. They
  need the **"Create and edit files"** setting. AI-powered artifacts run on the **viewer's** account.
- **Claude Docs** are for anything someone else will edit or comment on. They have real-time co-editing,
  comments and `@Claude` inside a comment, and export to DOCX, PDF, Markdown or Google Docs.
- **File creation** produces XLSX, DOCX, PPTX and PDF. **Who edits it next decides** the form: a Doc for
  collaborators, a file for someone who'll take it offline or into their own tool.
- Office and Google integrations let Claude work **inside** the file. Every write action is an approval
  you give, so record what you approved.
- **Provenance is not optional:** demand page and cell references. Get quote-backed answers. Compare Claude's
  reading against the source before you act on it.

## Concepts

### 1. File analysis

**Accepted inputs [app] GA:** PDF, DOCX, XLSX, CSV, TXT, HTML, ODT, RTF, EPUB, JSON and others (code files,
Markdown). Images are covered in §2.

**Limits [app]:**

| Limit | Value | What it means in practice |
|---|---|---|
| Per file | 500 MB | Large exports fit, but large is not the same as readable (see "Under the hood") |
| Per chat | 20 files | Synthesis across more than 20 sources needs a Project (M3.3) or a staged chain |
| PDF pages | up to 1000 | Text is extracted for the whole document |
| PDF visual analysis | up to 100 pages | Beyond 100 pages, assume charts, diagrams and scanned pages were **not seen**. Whether the first 100 pages still get visual analysis or the whole file falls back to text only is **unverified**, so don't rely on either |

> **Surface difference, not a contradiction:** the API accepts PDFs of up to **600 pages / 32 MB per
> request** [api] (verified 2026-11-14, claude-api reference). That is a different product with different limits.
> It doesn't overrule the app's 1000 pages. Quote the limit for the surface you're using.

**The five jobs files get used for:**

| Job | Prompt shape | Engineering example |
|---|---|---|
| Extraction | "List every X with its page number" | Every SLA, penalty and notice period from an MSA |
| Summarisation | "Summarise for <reader>, ≤N bullets, cite pages" | A 60-page SOW for the delivery lead |
| Comparison | "Compare v1 and v2; table of changes with page refs in both" | Redline review without a redline |
| Question answering | "Answer only from the document; quote first" | "Can the client terminate for convenience?" |
| Multi-file synthesis | Tag each file and cite by tag | RFP + our capability deck + past proposal → gap list |

For multi-file work, name each file in the prompt and ask for citations **by file and page**. Without that,
Claude blends sources and you can't tell where a claim came from.

### 2. Image and visual understanding

**What it handles [app] GA:** screenshots (error dialogs, dashboards, UI states), whiteboard photos,
architecture diagrams, UI mock-ups, charts and scanned forms.

**Limits [app]:** JPEG, PNG, GIF and WebP, up to **8000 × 8000 px**.

> **Accepted is not the same as seen.** 8000 × 8000 is the largest image you can *upload*. On the API, current
> models process images at up to **2576 px on the long edge** and downscale anything larger [api] (verified
> 2026-11-28, `claude-api` skill, model-migration guide). The app's internal processing resolution is
> **unverified**; assume a similar downscale. A 6000-px photo of a whole whiteboard is therefore seen at well
> under half its pixel density, which is why cropping a region helps (see "Under the hood").

**What vision gets wrong**, and why each one matters:

| Weak spot | Typical failure | Mitigation |
|---|---|---|
| Small text | A version string `4.12.1` read as `4.12.7`. Fine print skipped entirely | Crop and zoom the region and send it separately. Ask Claude to quote the exact text and mark unreadable characters |
| Dense tables | Values shifted one row or column; merged cells mis-attributed | Get the source data (CSV or XLSX) instead. If you can't, ask for the table transcribed and check 3–5 cells |
| Exact measurements | Pixel distances, chart values read off an axis, dimensions on a drawing | Treat them as estimates. Get the underlying numbers |
| Handwriting, whiteboards | Arrows mis-connected, boxes merged, abbreviations guessed | Ask for an "uncertain" list. Confirm with the person who drew it |

The rule: **anywhere being approximately right is being wrong**, the image is a lead, not a source. Prices,
part numbers, account numbers, dosages, legal figures and measurements on drawings all need the original.

### 3. Artifacts — the current system

Artifacts are the output panel: content Claude builds next to the chat that you can open, edit and share [app].

> **Syllabus says:** rebuilt in September 2026. Legacy artifacts can no longer be created (DEPR). Types: Docs,
> Slides and Design (GA, all plans); **Dashboards (BETA, Pro and above)**; Motion (BETA, Team and
> Enterprise); plus code, sites and diagrams. **20 MB text storage per artifact.** ·
> **Current (verified 2026-11-28, support.claude.com/en/articles/17153992 and /17454700):** legacy means made
> in a chat before 16 Sep 2026, and none can be created now. Docs, Slides and Design are GA on all plans.
> **Dashboards has been renamed "Claude Data", now GA on Pro and above**, with certified queries and live sharing
> still in beta. Motion is still BETA on Team/Enterprise. **New BETA templates: Sheets and Whiteboards** (Pro and above).
> Storage is **100 MB and 25,000 documents per new artifact**. The 20 MB text-only limit now applies only to legacy artifacts.

What stays stable, and what you need at work:

- **Requires "Create and edit files"** [app]. The toggle is also labelled "Code execution and file creation"
  in the older settings layout. If artifacts, file creation or Skills "don't work", check this first (M1.3).
- **AI-powered artifacts run on the viewer's own account** [app]. An artifact that calls Claude when it's
  opened spends the *viewer's* usage, under the *viewer's* plan and policies. Before you share one with a client
  or a large group, ask whether they have a seat, whether their policy allows it, and whether they expect to pay for it.
- **Storage is per artifact.** An artifact is not a database. Records that matter belong in a system of record.
- **DEPR legacy artifacts:** you can open old ones, but don't build a process on them.

### 4. Claude Docs

**What they are [app] GA:** living documents with **real-time co-editing**, **comments**, and
**`@Claude` inside a comment**, which asks Claude to act on that thread. **Export:** DOCX, PDF, Markdown, Google Docs.

**When a Doc beats a chat reply:** anything someone else will edit or comment on. A chat reply is a draft
for *you*. A Doc is a shared working surface with history and comments. Use one for a design note the team
will mark up, an incident review the client will comment on, or a proposal section passed between three authors.

Sharing differs by plan [app] (link-only on Free, email invites on Pro and above, people, groups or the whole org on
Team/Enterprise; verified 2026-11-28 from a support-article snippet, see fact-status). Check what your plan allows
before you promise a client access.

### 5. File creation

Claude generates **XLSX, DOCX, PPTX and PDF** (plus CSV, Markdown, HTML and PNG charts) in a sandbox, and
hands you a downloadable file [app] GA.

> **Syllabus says:** files are generated "through the Anthropic Skills". · **Current (verified 2026-11-28,
> support.claude.com/en/articles/12111783 and /12512180):** the file-creation page says it "uses common code
> packages". Separately, the Skills page lists Anthropic Skills for Excel, Word, PowerPoint and PDF that Claude
> uses automatically. The mechanism detail is unconfirmed. What you need to know is that both depend on the same
> "Create and edit files" setting.

**Choosing between a downloadable file and an artifact.** Who edits it next decides:

| Next reader does… | Choose | Why |
|---|---|---|
| Comments and edits with you, in Claude | **Claude Doc** / artifact | Co-editing and comments; one live version |
| Edits in their own tool (Excel, PowerPoint, Google), offline or under their template | **Downloadable file** (XLSX/PPTX/DOCX) | They own the next version in their tool |
| Just reads it, possibly on a phone, possibly forwards it | **PDF** export | Fixed rendering, no accidental edits |
| Interacts with it (filters, toggles) | Data/dashboard artifact | Interaction is the point |

### 6. Working inside Office and Google files

> **Syllabus says:** Excel and PowerPoint add-ins (PLAN: Pro and above); **Word add-in (BETA)**. Microsoft 365
> cross-app context (owner-enabled). Google Docs, Sheets and Slides live-editing connectors, with approval
> required on write actions. · **Current (verified 2026-11-14 and 2026-11-28, claude.com/docs/office-agents,
> support.claude.com/en/articles/15183774 and /10166901):** the Excel, PowerPoint **and Word** add-ins are GA on
> Pro/Max/Team/Enterprise. **Cross-app context is a feature of the add-ins themselves** (Excel, PowerPoint, Word and Outlook share
> context). The owner-enabled part is the **Microsoft 365 connector** (owner enable plus Entra admin consent, with write
> tools as a separate enable). Google live editing is confirmed (owner-enabled on Team/Enterprise). The approval rule
> is general: "each action Claude takes on your behalf requires your explicit approval" outside Auto mode. There is
> no separate Docs/Sheets/Slides write rule.

What this changes for you:

- **Working in place beats exporting.** Claude edits the live workbook or deck, so formulas, named ranges and the
  template survive. Copy-paste round trips lose them.
- **Every write is a decision you made.** Approving a write means you've accepted the change. On shared client
  files, read what will change before you approve. Keep a short log of approvals (exercise 4 asks for one). That log
  is your audit trail when someone asks "who changed the forecast formula?".
- **Auto mode removes the per-action check.** Don't turn it on for shared or client-owned files.

### 7. Accuracy and provenance for file work

- **Demand page and cell references:** "Cite page and clause for every term", "Name the sheet and cell range
  behind every figure". An answer without a reference can't be checked cheaply. An answer with one can be checked in seconds.
- **Quote-backed answers:** "Quote the clause verbatim, then interpret it." Then **check that the quote exists** and
  says what's claimed (the technique is M8.2). Fabricated or paraphrased quotes are the main risk.
- **Compare Claude's reading against the source before you act:** spot-check a sample of high-risk rows (money,
  dates, obligations). Check every row when the output goes to a client or into a contract.

## Under the hood

### How a PDF reaches the model

```text
PDF ──► text extraction (every page)  ──────────────► text tokens
   └──► page rendering → page images (visual pages) ──► image tokens
                                                     ▼
                                         one context window
```

- **Text extraction** pulls the text layer. It's cheap per page, which is why the text limit is high (1000 pages [app]).
- **Visual analysis** renders a page as an image so charts, diagrams, stamps and scanned pages can be "seen". Each
  page image costs far more tokens than its text, which is why the visual cap is lower (100 pages [app]).
- **Scanned PDFs have no text layer.** A scanned page that isn't visually analysed contributes *nothing*. If a 300-page
  scanned contract "has no termination clause", check whether the clause sits on a page that was never seen. Split
  the file into parts under the visual cap, or OCR it first so every page has a text layer.
- **Tables in PDFs** are extracted as text runs. Column alignment can be lost, so a figure can attach to the wrong
  header. That's another reason to cite page and cell, and to prefer the source spreadsheet.

### Why vision misreads dense tables and small text

An image is downscaled and split into patches before the model sees it. A 6-point footnote or a 40-row table may
end up only a few pixels high per character in the representation the model reasons over. The model then **predicts**
plausible text. A predicted cell reads as fluently as a real one, so the error doesn't look like an error. That's the
mechanism behind "approximately right": the output is shaped like the source, but the details are partly inferred.
Cropping a region before you upload it raises its effective resolution, which is why the crop-and-zoom move works.

### Why the output container matters more than it looks

A chat reply is ephemeral and one-to-one. A Doc keeps a single shared version and a comment trail. A downloadable
file forks: once it's on someone's laptop there are two versions, and Claude can't see the edits. Choosing the
container is choosing **where the next version lives**. If you get that wrong, you spend the next week merging edits by hand.

### API equivalent (for engineers wiring this into a service) [api]

Quote-backed document Q&A uses document blocks with citations enabled. Each answer span then carries the cited text
and its location, which is checkable by code:

```python
import anthropic

client = anthropic.Anthropic()  # ANTHROPIC_API_KEY from the environment

f = client.files.upload(file=("msa.pdf", open("msa.pdf", "rb"), "application/pdf"))

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    output_config={"effort": "medium"},
    messages=[{
        "role": "user",
        "content": [
            {"type": "document", "source": {"type": "file", "file_id": f.id},
             "citations": {"enabled": True}},
            {"type": "text", "text": "List every notice period in this agreement. "
                                     "Answer only from the document."},
        ],
    }],
)
for block in response.content:
    if block.type == "text":
        print(block.text)
        for c in (block.citations or []):
            # PDF citations are page locations: start_page_number .. end_page_number (exclusive)
            print("   ↳", c.cited_text[:80], "| page", getattr(c, "start_page_number", "?"))
```

Every cited span carries `cited_text`, the exact text it relies on, so your code can check that the quote really
appears in the source before anything downstream uses it. Citations can't be
combined with `output_config.format` (structured outputs) [api]. Pick one per call.

## In production

**1. SOW review before signature**
*Situation:* The client sends v3 of a 60-page SOW the night before signing and asks "what changed?".
*Right move:* Upload v2 and v3. Ask for a change table: `Clause | v2 text (page) | v3 text (page) | Impact`. Have
it quote both versions. Then hand-verify every row that touches money, scope, acceptance or liability.
*Why:* page references and quotes make each row checkable in under a minute.
*Failure mode:* trusting "no material changes" in prose. Claude can miss a changed number inside an unchanged sentence.

**2. Whiteboard photo → specification**
*Situation:* After an architecture session you have two whiteboard photos and a screenshot of an existing form.
*Right move:* Ask for the spec, **plus an "uncertain readings" list** (unclear arrows, abbreviations). Send that list
to the person who ran the session before anyone builds from it.
*Why:* handwriting and arrows are vision's weak spots, and the person who drew them is the only system of record.
*Failure mode:* a box labelled "AuthZ?" becomes a confident "Authorisation Service" in the spec, and someone builds it.

**3. Proposal deck for a pitch next week**
*Situation:* The bid lead wants a deck. Three colleagues will edit it, and the client wants a PDF.
*Right move:* Draft in a Slides artifact while the team iterates. Export **PPTX** when it moves into the house template
in PowerPoint, and **PDF** for the client.
*Why:* each form matches who edits next: the team in Claude, the designers in PowerPoint, the client reads only.
*Failure mode:* emailing a PPTX at hour one, then merging four forked copies at hour 40.

**4. Formula repair in a live forecast**
*Situation:* A shared Excel forecast returns `#REF!` after someone deleted a column.
*Right move:* Use the Excel add-in on the live file. Ask for an explanation of each broken formula and the proposed fix.
Approve each write individually and log it: cell, old formula, new formula, why.
*Why:* each approval is a change you own on a shared file; the log answers "who changed this?" later.
*Failure mode:* approving a batch of writes unread on a client-owned workbook. You now own changes you can't describe.

**5. Sharing an AI-powered artifact with a client**
*Situation:* You built an interactive estimator that calls Claude, and you want the client's PM to use it.
*Right move:* Check that the PM has a seat, that their policy allows it, and that they're fine with it using their usage. If not,
share a static export.
*Why:* the artifact's AI calls run on the viewer's account, plan and policy, not yours.
*Failure mode:* the artifact fails or bills the client unexpectedly, because it runs on the *viewer's* account.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| "Summarise this contract" with no references | Unverifiable; paraphrase drift goes unnoticed | "Cite page and clause; quote before interpreting" |
| Trusting figures read from a screenshot | Vision predicts plausible digits | Get the source data, or crop, zoom and verify |
| Assuming a 400-page scanned PDF was fully read | Visual analysis stops at the cap; scanned pages have no text layer | Split the document, or check which pages were seen |
| Quoting the API PDF limit for the app, or the reverse | Limits differ by surface | Name the surface with every limit |
| Emailing a PPTX for collaborative editing | Forked versions | A Doc or artifact while editing; export at the end |
| "Artifacts don't work" → raising a ticket | Usually the "Create and edit files" setting is off | Check settings first (M1.3) |
| Batch-approving writes on a shared workbook | You've signed off changes you didn't read | Approve per change and log each approval |
| Sharing an AI-powered artifact widely | Runs on each viewer's account and policy | Check seats and policy, or share a static export |

## Hands-on exercises

1. **Version compare.** Compare two versions of a 60-page document and produce a change table with page references
   in both versions.
   **Done when:** you've verified ten rows by hand against both PDFs and recorded how many were exactly right,
   partly right (wrong page, paraphrased) and wrong.
2. **Photo to spec.** Convert a whiteboard photo and a form screenshot into a structured specification.
   **Done when:** the spec has an "uncertain readings" list, and every item on it has been confirmed or corrected by
   the person who owns the source.
3. **Same deliverable, three forms.** Produce one deliverable as a Claude Doc, a Slides artifact and a downloadable
   PPTX.
   **Done when:** for each one you can name who edits it next, where the next version lives, and why the other two
   forms would be worse for that reader.
4. **Workbook repair.** Fix a formula-heavy workbook with the Excel add-in or the Sheets connector.
   **Done when:** an approval log lists every write you approved (cell, before, after, reason), and a colleague can
   reproduce each fix from the log alone.
