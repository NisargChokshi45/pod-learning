# M5.3 — Debugging, refactoring and optimisation

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| ELECTIVE | Clusters A, C, D; architects in E (cluster letters are **undefined in source**) | 2 | M2.3 (context engineering) |

**Objective:** find, fix and prevent defects, and improve existing code **without breaking it**.

> Claude is a fast, tireless hypothesis generator. It's also fluent enough to make a wrong diagnosis
> sound certain. This module's rule is: **evidence in, ranked hypotheses out, and nothing believed until it is
> measured or reproduced.**

---

## TL;DR

- **Debug with evidence, not descriptions.** Give Claude the stack trace, the logs around it, the reproduction steps,
  the relevant code and what has changed. "It's broken" yields a guess. Evidence yields a diagnosis.
- **Ask for hypotheses ranked by likelihood**, each with the evidence for and against it and the cheapest
  test that would confirm or kill it. Then add **targeted instrumentation**. Don't rewrite on a hunch.
- **Root cause, not symptom.** Rebuild the timeline from logs. Concurrency and environment-specific bugs
  need evidence from *the environment where they happen*.
- **Refactoring preserves behaviour.** Work in small steps and run tests between them. If there are no tests,
  write characterisation tests first. A refactor and a behaviour change never share a commit.
- **Technical debt needs a register** (impact, effort, risk), prioritised and explained to a manager in
  *business* terms: incidents, lead time, cost.
- **Profile first, always.** N+1 queries, leaks, hot loops, bundle size and cold starts are all found by
  measurement. **Never trust a claimed speed-up.** Measure before and after, the same way, on the same data.
- **Large codebases in chat:** paste deliberately (file summaries, symbol maps). Once the task needs the
  repo, the tests or a debugger, **chat is the wrong tool and Claude Code is the right one** (M6.2).

## Concepts

### 1. Debugging with evidence

**Supply stack traces, logs, reproduction steps and the relevant code.** The evidence pack:

| Evidence | Why Claude needs it | Hygiene (M8.1) |
|---|---|---|
| **Full stack trace**, untrimmed, including "caused by" | The root frame is often at the bottom | Strip tokens and customer IDs from the message strings |
| **Logs**: ±2 minutes around the failure, with timestamps | Ordering and correlation between services | Redact PII, IPs and `Authorization` headers |
| **Reproduction steps**: exact input, environment, frequency | Separates deterministic bugs from intermittent ones | Synthetic or anonymised inputs |
| **The relevant code**: the frames in the trace plus their callers | Without it, Claude debugs imagined code | Only the files involved, not the repo |
| **What changed**: deploy, config, dependency bump, traffic | Most regressions follow a change | Diff or release notes |

**Hypothesis lists ranked by likelihood.** Ask for a ranked list, with reasons, instead of "the answer":

```text
<stack_trace>…</stack_trace>
<logs>…</logs>
<code file="PaymentRetryWorker.java">…</code>
<changes>Deployed v4.12 at 14:02 UTC: bumped resilience4j 1.7 → 2.1; raised worker pool 8 → 32.</changes>

Failure: since 14:05, ~2% of payment retries throw DuplicateKeyException on payment_attempts.

Give me up to 5 hypotheses, ranked by likelihood. For each:
- the evidence above that supports it and anything that contradicts it
- the cheapest observation or test that would confirm or rule it out
Don't propose a fix yet. If the evidence is insufficient, say what you need.
```

Why this shape works: it forces Claude to tie each hypothesis to *your* evidence, it shows you the
alternatives (your own first guess may be number three), and "cheapest test" turns debugging into a
sequence of quick experiments, not one big rewrite.

**Targeted instrumentation.** When the evidence can't tell the hypotheses apart, add logging that *can*:
one log line at the suspected race, with a thread ID and correlation ID, that distinguishes hypothesis 1 from
hypothesis 2. Ask Claude for "the minimum logging to tell H1 from H2", not "more logging".

### 2. Root-cause analysis

**Symptom versus cause.** "Disk full" is a symptom, and "log rotation disabled by a config change" is a cause. A fix
aimed at the symptom (delete logs) recurs. The *5 whys* still works, and Claude is a good partner for it as
long as each "why" is answered from evidence, not plausibility.

**Timeline reconstruction from logs.** Give Claude logs from several services and ask for a merged,
UTC-normalised timeline of the events that matter, with **gaps flagged** and **clock-skew warnings** where the
ordering depends on timestamps from different hosts. Then check three entries against the raw logs yourself.
Merging is where fabricated or reordered events creep in.

**Concurrency and environment-specific bugs** are the hardest class, and the easiest to "explain"
wrongly:

| Class | Signal | What to give Claude | What Claude can't do from chat |
|---|---|---|---|
| Race / ordering | Intermittent, load-dependent, vanishes under the debugger | Thread dumps, correlation IDs, the shared-state code | Observe the interleaving. You must instrument or stress-test |
| Deadlock | Hangs, threads `BLOCKED` | Thread dump with lock owners | |
| Environment | "Works on my machine", fails in prod | Config diff, dependency lockfile diff, OS/runtime versions, env vars (redacted) | See your prod environment |
| Time / locale | Fails at midnight, month-end or in one region | Timezone settings, locale, sample timestamps | |

A plausible race-condition story isn't a diagnosis. A reproduction under a stress test is.

### 3. Refactoring

**Behaviour-preserving changes.** By definition a refactor changes structure, not behaviour. Tell Claude
so explicitly: *"This is a refactor: identical observable behaviour, including error messages and logging.
If any step would change behaviour, stop and tell me."*

**Small steps with tests between.** The loop:

```text
0. Tests green? If coverage of this function is thin, write characterisation tests first.
1. One named refactoring (Extract Method, Rename, Introduce Parameter Object, …).
2. Run the tests. Green → commit. Red → revert, don't debug forward.
3. Repeat.
```

Ask Claude for a *plan of named steps* before any code, for example "five steps, each a standard
refactoring, each independently committable", then take them one at a time.

**Extracting modules; naming; removing duplication.**
- *Extract* when a function does several things, or a module has two reasons to change.
- *Naming* is the cheapest, highest-value refactor. Claude proposes names well. You check that they match
  the domain language your team actually uses.
- *Duplication:* remove it only when the copies change for the same reason. Two blocks that look alike but
  serve different domains should stay separate. Merging them couples two things that will diverge later.

### 4. Technical-debt analysis

**Code smell inventories.** Claude can scan provided code for long functions, deep nesting, god
classes, feature envy, primitive obsession, missing tests, outdated dependencies and copy-paste blocks.
Treat the output as a *candidate* list and confirm each item.

**A debt register with impact and effort:**

| ID | Item | Where | Impact (what it costs today) | Effort | Risk if left | Priority |
|---|---|---|---|---|---|---|
| TD-01 | No tests on invoice rounding | `billing/rounding.py` | 2 incidents in Q3; every change needs manual QA (~1 day) | M | High: money | 1 |
| TD-02 | ORM N+1 on order list | `OrdersController#index` | p95 2.8 s on large accounts; support tickets | S | Medium | 2 |
| TD-03 | Deprecated auth library | `auth/` | Security patch window closing; blocks runtime upgrade | L | High | 3 |
| TD-04 | 1,200-line `ReportBuilder` | `reports/` | Slows every report change; one dev understands it | L | Medium | 4 |

**Prioritisation:** high impact with low effort first. *Risk* (security, money, compliance) can override that
order. Ask Claude to propose a priority with reasoning, then argue with it.

**Presenting debt to a manager in business terms.** "The `ReportBuilder` has high cyclomatic complexity" doesn't
get funded. "Every reporting change takes ~3 extra days and only one engineer can do it safely; a
two-sprint cleanup removes that risk" does. Ask Claude to rewrite the register's top five for a non-engineer,
in cost, risk and lead time, and check every number it uses against your data. Never let it invent one.

### 5. Performance optimisation

**Profile first, always.** Intuition about where time goes is wrong more often than it's right, and
Claude's intuition is no better. Give Claude the *profile* (flame graph summary, slow-query log, APM trace),
not just the code.

**The usual suspects:**

| Problem | How you find it | Typical fix |
|---|---|---|
| **N+1 queries** | Query count per request; ORM SQL logging | Eager loading / batched fetch / a join |
| **Memory leaks** | Heap growth over time; heap snapshot diff | Remove unbounded caches, listeners never removed, closures holding large objects |
| **Hot loops** | CPU profiler / flame graph | Hoist invariant work; a better data structure (set lookup in place of list scan) |
| **Bundle size** | Bundle analyser | Code splitting, tree-shakeable imports, dropping heavy dependencies |
| **Cold starts** | Init-time traces (serverless, JVM, mobile) | Lazy initialisation, smaller deployment packages, provisioned concurrency |

**Measuring before and after.** An N+1 example in Django:

```python
# Before: 1 query for orders + 1 per order for customer → N+1
orders = Order.objects.filter(status="open")[:200]
rows = [(o.id, o.customer.name) for o in orders]

# After: one JOIN
orders = Order.objects.filter(status="open").select_related("customer")[:200]
rows = [(o.id, o.customer.name) for o in orders]
```

Prove it. Don't assert it:

```python
from django.db import connection
from django.test.utils import CaptureQueriesContext

with CaptureQueriesContext(connection) as ctx:
    rows = [(o.id, o.customer.name) for o in Order.objects.filter(status="open")[:200]]
print(len(ctx.captured_queries))   # before: 201   after (select_related): 1
```

Record both numbers, plus wall-clock latency over several runs on the same dataset (median and p95), in
the PR. For one-to-many relations use `prefetch_related` (2 queries, not 1). The equivalents are
`include` in Entity Framework / Prisma, `JOIN FETCH` / `@EntityGraph` in JPA, and `includes` in Rails.

**Never trust a claimed speed-up.** "This should be ~40% faster" is a prediction, and Claude can't measure
anything in chat. Benchmarks also lie easily: warm vs cold cache, a tiny dataset, JIT warm-up, measuring a
different code path. Run the same harness and the same data, take several runs and compare medians.

### 6. Working with large codebases in chat

**Choosing what to paste.** Paste the frames in the stack trace, their direct callers, the interfaces they
implement and the config they read. Leave out everything else. More code dilutes attention and spends the window
(M2.3).

**File summaries and symbol maps.** For a wide question ("where could this state be mutated?"), paste a
*map* instead of code. A map is the list of files with one-line purposes, plus the relevant symbols and
signatures (`ctags`, an IDE outline, `grep -rn "pendingCount"`). Claude reasons over the map and tells you
which three files to paste next.

**Recognising when chat is the wrong tool and Claude Code is right:**
- you're pasting more than a handful of files, or pasting the same files again every turn;
- the next step is "run the tests", "run the profiler" or "try the fix";
- the bug spans a call graph you can't easily map by hand;
- you're refactoring across many files.

Claude Code [code] reads the repository itself, runs tests and commands inside the loop, and makes
multi-file edits you review as a diff. The workflow is M6.2, and multi-file changes and Git are M6.3.

## Under the hood

### Why ranked hypotheses beat "what's the bug?"

Asked for "the bug", a model produces the single most plausible story, and plausibility comes from
patterns in training data, not from your system. If you ask for *several* hypotheses, *ranked*, each tied to
evidence with a falsification test, three things change. The model has to look at the evidence for each one. You
see the alternatives the confident single answer hid. And the next action becomes an experiment, not a
fix. This is the debugging form of M2.2's generate-then-select and "list what you're unsure about".

### Why fluent diagnoses are dangerous

A wrong root-cause story with the right vocabulary ("a classic TOCTOU race between the cache check and the
insert") reads exactly like a right one. Tone carries no information about correctness (M8.2). The
defence is procedural: every diagnosis has a reproduction or a measurement behind it before anyone
acts on it.

### Characterisation tests: making refactoring safe on untested code

Legacy code often has no tests, so "refactor with tests between steps" needs tests that don't exist yet.
**Characterisation tests** (Michael Feathers' term) record what the code *does now*, not what it should do:

```python
def test_rounding_characterisation():
    # Pinned from current behaviour on 2026-11-20. Includes half-even (banker's) rounding on .005,
    # which callers may depend on. Do not "fix" during refactor.
    assert round_invoice(Decimal("10.005")) == Decimal("10.00")
    assert round_invoice(Decimal("10.015")) == Decimal("10.02")
```

Claude is good at generating these. Give it the function and ask for inputs that cover each branch and
boundary, then *run the code to capture the outputs*. Don't let Claude predict them. A predicted expected
value is a guess, and a captured one is a fact.

### The measurement loop

```text
baseline (N runs, same data) → change ONE thing → measure (N runs) → compare medians/p95 → keep or revert
```

Change one thing at a time, or you can't tell which change helped. Keep the harness in the repo so the
next engineer can re-measure. Claude helps write the harness, and the numbers come from running it.

## In production

**1. SEV2 at 02:00: duplicate payments after a deploy**
*Situation:* Errors spike five minutes after a release that bumped a resilience library and quadrupled a worker pool.
*Right move:* Build the evidence pack (redacted trace, logs, change list) and ask for ranked hypotheses with
cheapest tests. The top two (a retry semantics change in the library, and a race exposed by the higher concurrency) are
told apart by one log line with thread and attempt IDs. Mitigate first (roll back the pool size), then
diagnose.
*Failure mode:* accepting the first confident story and hot-patching a lock around the wrong code path.

**2. Sprint bug-fix rotation**
*Situation:* Ten small bugs in a week.
*Right move:* Write a reproduction test for each bug first (red), then fix (green), then record the root cause in
the ticket. Claude drafts the test from the repro steps, and you confirm it fails for the right reason.
*Failure mode:* fixing from the description alone. Half the "fixes" don't fix the reported case.

**3. Pre-release performance pass**
*Situation:* The order list page p95 is 2.8 s for large accounts.
*Right move:* APM trace → 201 queries per request → N+1 on customer. Fix with eager loading, then measure:
1 query and p95 0.4 s on the same dataset. Both numbers go in the PR.
*Failure mode:* adding a cache because Claude said "this is probably slow". Now it's stale data *and* still
201 queries on a cache miss.

**4. Modernisation planning**
*Situation:* Leadership asks "how bad is the legacy billing service?"
*Right move:* Build a smell inventory and debt register with Claude, have the team confirm it, then write the top five in
business terms with real incident and lead-time numbers. A manager can fund that.
*Failure mode:* a 40-item smell list nobody prioritises, written in jargon.

**5. The 300-line function**
*Situation:* `calculateShipping()` grew to 300 lines with a flag argument.
*Right move:* Characterisation tests first. Then Claude proposes five named refactoring steps. Do each step, run
the tests, commit, and stop at any red.
*Failure mode:* "Refactor this function" in one shot returns a beautiful rewrite that silently changes rounding
on one branch.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| "My code throws an error, help" | No evidence means a plausible guess | Send the trace, logs, repro, code and what changed |
| Accepting the first diagnosis | Fluent and wrong reads like fluent and right | Ranked hypotheses + cheapest test for each |
| Fixing the symptom | It recurs | Timeline → 5 whys from evidence → cause |
| "Explaining" a race without reproducing it | A story isn't a diagnosis | Instrument, stress-test, reproduce |
| One-shot "refactor this" | Behaviour changes hidden in a big rewrite | Named small steps, tests between, commit each |
| Refactor and behaviour change in one commit | You can't bisect or review either | Separate commits; refactor first |
| Letting Claude predict expected values in characterisation tests | Pins a guess, not current behaviour | Run the code to capture outputs |
| Optimising without a profile | Effort spent where time isn't | Profile → biggest cost → fix → measure |
| Believing "this is ~40% faster" | Claude can't measure in chat; benchmarks mislead | Same harness, same data, several runs, compare medians |
| Debt list in engineering jargon | Never funded | Business terms: incidents, lead time, risk, cost |
| Pasting half the repo into chat | Dilutes attention; spends the window | Symbol map → targeted files, or switch to Claude Code |

## Hands-on exercises

1. **Three seeded bugs.** Debug three seeded bugs using only the provided logs and traces. For each, ask
   for ranked hypotheses before you look at the code in detail.
   **Done when:** all three are fixed with a test that failed before the fix and passes after, and you have
   recorded, for each bug, your initial hypotheses and which (if any) were right, including where Claude's
   top-ranked hypothesis was wrong.
2. **Test-guarded refactor.** Refactor a 300-line function in five steps, with tests run between each.
   **Done when:** there are five commits, each a named refactoring with tests green, the characterisation
   tests are unchanged and passing, and `git diff` shows no change in observable behaviour (same outputs,
   errors and logs).
3. **Debt register for a non-engineer.** Build a technical-debt register for a provided repository, then
   present the top five items to a non-engineer.
   **Done when:** every register row has impact, effort, risk and priority, every number in the
   business-terms version can be traced to a source, and the non-engineer can restate why item 1 comes first.
4. **N+1, proven.** Fix an N+1 query in an ORM of your choice and prove the improvement with measurements.
   **Done when:** you have query counts before and after (for example 201 → 1 or 201 → 2), plus median and p95
   latency over at least 5 runs on the same dataset, recorded with the harness committed next to the fix.
