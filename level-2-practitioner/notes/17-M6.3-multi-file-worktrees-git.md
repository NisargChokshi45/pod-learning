# M6.3 — Multi-file changes, worktrees, testing, debugging and Git

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| ELECTIVE | Clusters A, C, D (cluster letters are **undefined in source**) | 2 | M6.2, and M5.4 (**forward reference**: M5.4 *Review and secure coding* is an Advanced-level module. The minimum you need is given inline below) |

**Objective:** deliver reviewed, tested, multi-file changes through Git, and run more than one piece of work
at once without the pieces colliding.

> **Minimum M5.4 concepts for this module** (until you take M5.4 at Advanced): (1) a reviewer checks
> correctness, tests, security (input validation, secrets, injection, authz) and dependencies, *not*
> style alone; (2) every change is reviewed by a human who didn't write it, and "Claude wrote it" doesn't
> count as an author who reviewed it; (3) a test that can't fail proves nothing (see M5.5).

---

## TL;DR

- **Multi-file changes:** scope first, let Claude explore before it edits, write tests first, and make
  **small commits you can bisect**.
- **Parallel work needs worktrees, not just branches.** Two sessions in one checkout share files, the
  index and `HEAD`, and they'll overwrite each other. Use one worktree per task, each with its own session.
- **Background and watch:** `Ctrl+B`, `/tasks`, `/background`, `claude agents` [code]. Desktop runs
  parallel sessions with an optional worktree per session.
- **Merge back deliberately:** smallest and most independent change first, rebase or merge the rest onto
  it, resolve conflicts by intent, and re-run tests after every merge.
- **Parallelism stops paying** when tasks share a schema change, overlap in a refactor, or need one
  coherent decision.
- **Debug and verify inside the loop:** feed real errors and logs, run a reproduction script, then the suites
  and lint on every edit. Bundled skills: `/verify` (build, run and observe the app), `/code-review` (review
  the diff). `/debug` troubleshoots **Claude Code itself** from its session log, not your application.
- **Git hard rules:** commit messages explain *why*. **No force push. No destructive operation without
  explicit human approval.** Enforce with deny rules *and* server-side branch protection; a pattern rule alone
  isn't a security boundary.
- **CI:** `anthropics/claude-code-action@v1` and `/install-github-app` [code]. Mention `@claude` in an
  issue or PR. GitLab CI integration is BETA.

## Concepts

### 1. Multi-file changes

- **Scoping the change:** state the boundary before Claude starts. *"Change the `Invoice` total
  calculation to include tax lines. In scope: `billing/`, its tests, the API serializer. Out of scope: the
  PDF renderer, migrations."* An unscoped request invites a helpful-looking sweep across the repo.
- **Letting Claude explore before it edits:** ask it to list the files it expects to touch, and why,
  *before* any edit (plan mode, M6.2). An unexpected file in that list is your first review finding.
- **Test-first prompts:** *"First write failing tests for the three tax cases in `tests/billing/`. Run
  them and show they fail. Then implement until they pass. Don't modify the tests after they're
  agreed."* This pins the target, and the last sentence closes the edit-the-test-to-pass loophole.
- **Incremental commits you can bisect later:** one logical step per commit, each compiling and passing
  tests. `git bisect` can then find the exact step that broke production. A single 40-file "implement
  feature" commit can't be bisected.

### 2. Parallel work with worktrees

- **Why worktrees, not branches alone.** A branch is a pointer. Your checkout has one working directory
  and one index. Two Claude sessions in the same checkout edit the same files on disk, and `git checkout
  other-branch` in one session changes the files under the other. **They'll fight.** A `git worktree` gives
  each task its own directory and index on its own branch, while sharing one object store.

```bash
# one worktree per task, each on its own branch
git worktree add ../payments-api-ticket-123 -b ticket-123
git worktree add ../payments-api-ticket-124 -b ticket-124
cd ../payments-api-ticket-123 && claude      # session 1
# (new terminal) cd ../payments-api-ticket-124 && claude   # session 2
git worktree list
git worktree remove ../payments-api-ticket-123   # after merge
```

  Claude Code can create worktrees for you [code] GA: `claude --worktree <name>` (or `-w`) creates
  `.claude/worktrees/<name>/` on a branch `worktree-<name>`.
- **`/branch` and `/fork`** [code] GA. These branch the **conversation**, not the repository. `/branch [name]`
  branches the conversation and switches you into it. `/fork [prompt]` copies it into a new background
  session. Pair them with a worktree when the forked work will also edit files.
- **One worktree per task, each with its own Claude Code session.** That gives you separate context,
  checkpoints and diffs.
- **Backgrounding work:** `Ctrl+B` sends a running command or agent to the background. `/tasks` lists
  background work in the current session. `/background [prompt]` (alias `/bg`) detaches the **current
  session** to run as a background agent and frees the terminal. `/fork` copies the conversation into a new
  background session and tells the copy to create its own worktree before editing code. `claude agents`
  opens the agent view of detached sessions.

> **Syllabus says:** "`claude agents` to view detached sessions". · **Current (verified 2026-11-28,
> code.claude.com/docs/en/agent-view):** confirmed. Agent view is labelled a **research preview**. Treat it
> as BETA-like: demonstrate it, but don't build a team process on it yet.

- **Parallel sessions in the desktop app:** "+ New" opens parallel sessions, each with an optional
  **Worktree** toggle. The toggle is **off by default**, so turn it on for any session that edits files.
- **Merging back: order of operations.** (1) Merge the smallest, most independent branch first. (2) Rebase
  or merge the next branch onto the updated main. (3) Resolve conflicts by **intent**: read both
  sides' plans and commit messages, not only the conflict markers. (4) Re-run the full suite after **each**
  merge. Two green branches can be red together. (5) Remove merged worktrees.
- **Resolving conflicts between two agents' work:** give a third session (or yourself) both branches'
  plans and the conflict. Ask for a resolution that satisfies both intents, *with a test that proves both
  behaviours*. Never accept "ours" or "theirs" wholesale without reading the other side.
- **When parallelism stops paying:** shared schema or migration changes (they serialise anyway);
  overlapping refactors of the same module (you get a conflict on every hunk); anything that needs **one coherent
  decision** (naming, an API shape, an error model). Do those sequentially, or decide first and then parallelise.

### 3. Debugging in session

- **Feed errors and logs:** paste the *full* stack trace, the failing command and its output, and the
  relevant log window. Better still, let Claude run the failing command itself so it sees the real output.
- **Reproduction scripts:** *"Write the smallest script that reproduces this failure. Run it. Don't fix
  anything until it fails reliably."* A reproduction turns a guess into a test, and it becomes the regression
  test after the fix.
- **Running commands and tests inside the loop:** Claude can run the suite, a single test, the app or a curl
  against it. Permission rules decide which of these need your approval.
- **The bundled debug skill** [code] GA: `/debug [description]` turns on debug logging for the **Claude
  Code session** and diagnoses problems by reading that log (a hook that doesn't fire, an MCP server that
  won't connect, a permission rule that doesn't match). It isn't a debugger for your application code.

> **Syllabus says:** "the bundled debug Skill" under *Debugging in session*. · **Current (verified 2026-11-28,
> code.claude.com/docs/en/commands):** `/debug` troubleshoots Claude Code itself from its session debug log.
> Debugging *your* code is the discipline above (evidence, reproduction, hypotheses; M5.3), driven by your
> prompts, not by a bundled skill.

### 4. Testing and verification

- **Running suites:** the full suite before you push, and the targeted tests while you iterate. Put the exact commands
  in CLAUDE.md (M6.2).
- **The bundled verify and code-review skills** [code] GA. `/verify` confirms a change does what it
  should by **building and running the app and observing the result**, rather than relying on tests or type
  checks alone. `/code-review` reviews the current diff (or a PR, branch or path) for correctness at a chosen
  effort level, and can `--fix` or `--comment`.
- **Coverage targets:** useful as a floor ("new code ≥ 80% lines"), useless as a goal. Coverage measures
  what ran, not what was checked (M5.5).
- **Lint and format on every edit:** say so in CLAUDE.md now. Making it automatic with hooks is M6.4.

### 5. Git workflows

- **Commits that explain why:** the diff shows *what*. The message must say *why*. *"Include tax lines
  in invoice total. Totals excluded VAT lines added after the 2025 schema change, under-billing EU
  customers. Refs BILL-412."* Ask Claude to draft it from the plan, then edit it.
- **Pull requests via the GitHub CLI:** `gh pr create --title … --body-file pr.md`. Have Claude generate
  the description from the plan and the diff: what changed, why, how it was tested, the risks, and anything left
  out on purpose.
- **`/review`; Code Review (PLAN: Team and Enterprise):**

> **Syllabus says:** "`/review`; Code Review (PLAN: Team and Enterprise)". · **Current (verified 2026-11-28,
> code.claude.com/docs/en/commands, …/code-review):** `/review` is now an **alias of the bundled `/code-review`
> skill**, which works locally on any plan. The managed **Code Review** service, which posts a check run on PRs
> and is triggered by an `@claude review` comment, is Team and Enterprise only, and unavailable under ZDR,
> HIPAA or CMEK configurations.

- **Hard rules:** **no force push** (it rewrites shared history and can silently delete a teammate's
  commits). **No destructive operation without explicit approval:** `reset --hard`, `clean -fd`, branch
  deletion, history rewriting, dropping tables, deleting files outside the task. Enforce this with
  `permissions.deny` rules in the committed `.claude/settings.json`, not only by asking nicely. Deny rules
  are covered in depth in M6.4.

```json
{
  "permissions": {
    "ask":  ["Bash(git push *)", "Bash(git branch -D *)", "Bash(git rebase *)"],
    "deny": ["Bash(git push *--force*)", "Bash(git reset --hard*)", "Bash(git clean *)"]
  }
}
```

  **Know the limits** [code] GA (code.claude.com/docs/en/permissions): Bash rules match the command *text*;
  everything before the first `*` must match as written. So `Bash(git push --force *)` would **miss**
  `git push origin main --force`, which is why the flag sits between wildcards above. Deny beats ask beats
  allow, and an explicit ask rule prompts in every mode. Compound commands (`a && b`) are checked per
  subcommand. But the same program in another form (`git push -f`, `git push origin +main`, `git -C . push`,
  `sh -c "…"`) isn't matched by the deny rule, which is why every push also sits under `ask`. The docs say
  such a rule "isn't a security boundary around the program". So the deny rule is the first layer. The real controls
  are **branch protection on the remote** (no force push, required reviews on shared branches) and, for
  shell-level enforcement, the sandbox. Never "fix" a blocked command by switching to bypass permissions.

### 6. GitHub Actions and GitLab

- **`anthropics/claude-code-action@v1`** [code] GA: Claude runs in your CI on GitHub events. **`/install-github-app`**
  installs the Claude GitHub App, stores the secret and opens a PR with the workflow. It needs repo admin
  rights, the `gh` CLI, and a github.com remote.
- **Mentioning Claude in an issue or PR:** a comment containing `@claude` (the default trigger phrase)
  starts a run that can answer, review or open a PR. By default the action only runs for a triggering user
  with **write access** to the repo and rejects bot actors (no bot loops), so a stranger on a public repo
  can't drive it.

```yaml
# .github/workflows/claude.yml — minimal
name: Claude
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')   # don't start runners for every comment
    runs-on: ubuntu-latest
    permissions:            # job-scoped; drop to read for a review-only workflow
      contents: write
      pull-requests: write
      issues: write
      id-token: write       # required for the action's default GitHub App authentication
      actions: read         # lets Claude read CI results on PRs
    steps:
      - uses: actions/checkout@v6
        with: { fetch-depth: 1 }
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
```

- **Authentication options:** an `ANTHROPIC_API_KEY` secret; a Claude subscription OAuth token
  (`claude_code_oauth_token`, from `claude setup-token`, tied to one person's subscription, so use an API key
  for an org-wide secret); workload identity federation (the workflow's GitHub OIDC token exchanged for Claude
  API access, no stored secret); or OIDC to Amazon Bedrock, Google Cloud's Agent Platform or Microsoft
  Foundry. Prefer the OIDC routes, because they avoid long-lived keys. Grant the workflow only the permissions
  it needs (a review-only workflow needs read on contents, PRs and issues, plus `id-token: write`).
- **GitLab CI integration** [code] BETA, maintained by GitLab. Explain and demonstrate it, but it isn't assessed.

### 7. Stack labs

The loop is the same in every stack. The *verify* commands are what change. Put them in CLAUDE.md:

| Stack | Test | Lint/format | Watch out for |
|---|---|---|---|
| NestJS / Next.js | `npm test` / `vitest run` | `eslint`, `prettier --check` | Server vs client components; async error paths |

## Under the hood

### Why two sessions in one checkout collide

```
one checkout:   working dir ── index ── HEAD(branch)   ← both sessions read/write here
                     ▲                    ▲
session A edits ─────┘   session B runs `git checkout`, `git stash`, formatter → A's view changes underneath it
```

Each session also has its own **checkpoints**, which only know about its own edits. Session A's rewind can
restore a file to a state that wipes out session B's work. Worktrees remove the shared mutable state, so each
session owns one directory, one index and one `HEAD`, while the object store stays shared, so creating a
worktree is cheap.

### Why small commits matter more with an agent

An agent produces coherent changes quickly. That's exactly why a regression can hide in a large diff. Small
commits give you three things: reviewable units, `git bisect` granularity, and cheap partial reverts
(`git revert <one-step>` instead of unpicking a mega-commit).

### What the GitHub Action actually does

On a matching event the runner checks out the repo, starts Claude Code headless with the event context
(issue or PR body, comments, diff), and lets it act through the GitHub API with the **workflow's token
permissions**. Its reach is exactly what you granted in `permissions:` plus the tools its config allows.
That is why least privilege in the workflow file is a security control, not boilerplate.

## In production

**1. Three tickets before a release**
*Situation:* release freeze on Friday; three independent tickets (a copy fix, a new endpoint, a flaky test).
*Right move:* three worktrees, three sessions, each in plan mode first. Merge the copy fix first, then the
endpoint, then the test fix, running the full suite after each merge.
*Why:* independent files, no shared decisions, so parallelism pays.
*Failure mode:* three sessions in one checkout. The flaky-test session's `git stash` swallows the endpoint
work.

**2. Two tickets that both touch the schema**
*Situation:* ticket A adds `invoice.tax_total`, ticket B renames `invoice.total` → `gross_total`.
*Right move:* sequence them. Decide the schema once, then let either ticket proceed.
*Why:* a schema is one coherent decision; two sessions designing it independently produce two answers.
*Failure mode:* parallel migrations with conflicting heads. It's caught in staging, if you're lucky.

**3. CI red, log only**
*Situation:* a PR fails CI and you have only the log.
*Right move:* give Claude the full failing log section → ask for ranked hypotheses → write a local
reproduction → fix → add the reproduction as a test → push a new commit (not a force-pushed amend on a shared branch).
*Why:* the reproduction turns a guess into evidence and becomes the regression test.
*Failure mode:* "probably a flaky timeout", a retry added, and the real race ships.

**4. Vendor team PR hygiene**
*Situation:* a vendor team's PRs arrive with one-line descriptions.
*Right move:* a committed PR template, Claude-drafted descriptions from plan + diff, `/code-review` on
every PR, and the Code Review service where the plan allows it. A human approver remains mandatory.
*Why:* AI review raises the floor cheaply; accountability still needs a named human (M8.3).
*Failure mode:* treating the AI review as the approval. It's an input to a human reviewer.

**5. "Just clean up the branches"**
*Situation:* you ask Claude to tidy old branches, and it proposes `git push origin --delete` for 40 of them.
*Right move:* refuse in bulk. Review the list and approve explicitly. Deny rules and remote branch
protection prevent the same thing happening unattended.
*Why:* remote deletion can't be rewound by checkpoints; it's outside the working tree.
*Failure mode:* "Yes, and don't ask again" on `git push origin --delete`, which turns one approval into a
standing permission for that command in this repo.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| Two sessions, one checkout | Shared files, index and HEAD. Silent overwrites | One worktree per task |
| "Implement the feature" with no scope | Sprawling diff that touches unrelated modules | Name what's in and out of scope; ask for the file list first |
| One giant commit | Can't bisect, can't partially revert, can't review | One logical, green step per commit |
| Letting Claude edit tests to go green | The suite proves nothing | Agree tests first; forbid changing them; read test diffs |
| Parallelising a shared schema change | Conflicting migrations and decisions | Decide once, then serialise |
| `git push --force` "to clean up" | Rewrites shared history; loses commits | New commits; `--force-with-lease` only on your own unshared branch, with approval |
| AI review treated as approval | No accountable human (M8.3) | AI review feeds a named human reviewer |
| Broad `permissions:` in the Action | Agent reach = token reach | Least privilege; OIDC over long-lived keys |
| Trusting a Bash deny rule as the only guard | Matches command text; another form slips past | Deny rule + remote branch protection (+ sandbox) |
| Using `/debug` to debug the app | It reads Claude Code's own session log | Reproduction script, logs, ranked hypotheses |

## Hands-on exercises

1. **Ticket to PR:** implement a change across five files with tests, commit in steps, and open a PR with a
   generated description.
   **Done when:** the PR has ≥3 commits that each pass tests on their own, with messages that say why. The
   description lists what changed, why, how it was tested, and the risks. You've read every hunk.
2. **Debug a seeded failure from the CI log alone.**
   **Done when:** you have a ranked hypothesis list, a local reproduction script that fails before the fix and
   passes after, and the reproduction is committed as a regression test.
3. **Run two independent tickets in parallel worktrees, then merge both and resolve the conflict.**
   **Done when:** `git worktree list` shows both during the work, the conflict resolution keeps both
   intents with a test for each, the full suite passes after the second merge, and the worktrees are removed.
4. **Set up the GitHub Action on a sandbox repository and have Claude respond to an issue.**
   **Done when:** an `@claude` issue comment produces a response or PR. The workflow's `permissions:` block is
   minimal, and the key is stored as a secret, never in the YAML.
