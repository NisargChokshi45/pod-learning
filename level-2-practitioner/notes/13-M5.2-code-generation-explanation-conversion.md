# M5.2 — Code generation, explanation and conversion

| Status | Audience | Hours | Prerequisite |
|---|---|---|---|
| ELECTIVE | Clusters A, B, C, D; architects in E (cluster letters are **undefined in source**) | 2 | M2.3 (context engineering) |

**Objective:** generate, understand and translate code across stacks **while keeping ownership of
correctness**.

> Claude writes code faster than you can read it. The skill this module teaches isn't getting code
> out of Claude. It's getting code out that *fits your codebase*, that you understand, and that you'd
> defend in review as your own. If you can't explain a generated line, you haven't finished.

---

## TL;DR

- **Generated code matches whatever context you give it.** Supply conventions, an existing pattern, the
  lint rules and **one sample file**. Without them you get generic tutorial code that fails review on
  style before anyone checks logic.
- **Plan before code.** Ask for the file list, signatures and approach first, review it, then ask for
  the implementation. Decide whether you want **scaffolding** (structure you'll fill in) or a **full
  implementation** (which you then own).
- **Explanation is a first-class use:** walking a module, describing a call graph in prose, unpacking a regex, SQL or
  build file. "Explain this as if I'm new to this stack" is a legitimate prompt, not a crutch.
- **Legacy code:** Claude infers intent, spots dead code and hidden coupling, and drafts the missing
  docs. **Inferred intent is a hypothesis.** Confirm it against callers, tests and history.
- **Conversion is idiomatic translation, not transliteration.** Java→Kotlin, .NET Framework→.NET 8,
  Angular→React, Python 2→3 and SQL dialect moves each have a **checklist**, plus a named list of
  what *can't* be converted mechanically.
- **Boilerplate (DTOs, mappers, validators, CRUD, config, CI) is where Claude saves the most time**, and
  where drift from your template does the most quiet damage. Generate from the template, then diff
  against it.
- **Every stack has a known trap** that generated code falls into: Node async, C# nullability, Python
  typing, Java generics, Swift/Kotlin platform APIs, Flutter and React Native platform channels. Review for that trap specifically.
- **Run the existing tests against generated or converted code.** Without that step, "it compiles" is all you know.

## Concepts

### 1. Generation that fits the codebase

**Supply conventions, patterns, lint rules and a sample file.** Claude's default style is the average
of public code it has seen. Your codebase isn't average. It has a layering rule, an error-handling idiom,
a logger, a naming scheme and a test layout. The cheapest way to transfer all of that is to show it:

| Supply | Why it matters | Example |
|---|---|---|
| **Conventions** (written) | Rules that aren't visible in one file | "Services never call repositories of another aggregate; use the domain event bus" |
| **An existing pattern** | Shows the idiom in use, not just described | `OrderService.ts`, the closest sibling to what you're building |
| **Lint and format rules** | Prevents a review cycle spent on style | `.eslintrc`, `ruff.toml`, `.editorconfig`, `detekt.yml` |
| **One sample file** | The strongest single signal (in-context learning, as in M2.1) | The test file for the sibling service |

Pick the sample deliberately. Claude copies the sample's quirks as faithfully as its virtues. If the
closest sibling has a known wart (a swallowed exception, an old logging call), say "follow the structure of
`OrderService.ts` but use the new `Result` error pattern, not its try/catch".

**Scaffolding versus full implementation.**

| Ask for | When | What you own afterwards |
|---|---|---|
| **Scaffolding**: files, signatures, TODO bodies, test stubs | Unfamiliar domain, or logic you must write yourself (pricing, auth, money) | The logic, which you write |
| **Full implementation** | Well-specified, low-novelty work with tests you trust | *Every line*. You review it as if a new hire wrote it |

**Ask for the plan before the code.** A prompt like *"List the files you'd create or change, the public
signatures, and the approach for error handling. Don't write the code yet."* costs one turn and catches
the expensive mistake: the wrong architecture, the wrong layer or a missed existing utility. It's far cheaper
to say "use the existing `RetryPolicy` instead" to a ten-line plan than to a 400-line diff. Reasoning
and decomposition were covered in M2.2. This is the same plan-then-execute idea applied to code.

### 2. Explaining unfamiliar code

**Walking a module.** Ask for a guided read, not a summary: *"Walk through `billing/reconcile.py` in
execution order. For each function: what it's for, what it reads, what it mutates, and what can fail."*

**Call graphs in prose.** *"Starting from `POST /invoices`, trace the call path to the database write.
Name each function and file, and say where it crosses a process or network boundary."* Prose call graphs
show the parts a static tool misses: why a call is there and which branch matters.

**Regular expressions, SQL and build files** are dense and easy to misread, and Claude explains them well:

```text
^(?=.*\d)(?=.*[A-Z])[\w!@#$%^&*]{12,64}$
```

The explanation you want is: "at least one digit, at least one capital, 12–64 characters drawn only from
word characters and those symbols, anchored at both ends". Also ask for **test strings that should match
and should fail**. Then *run them*. An explanation of a regex is a claim, and the regex engine is the
check.

The same goes for SQL ("explain the join order and why this `LEFT JOIN` doesn't behave like an inner join
after the `WHERE` clause"), and for build files (Gradle task graphs, MSBuild targets, webpack/Vite configs,
Bazel rules).

**"Explain this as if I'm new to this stack."** This prompt matters for polyglot teams. A Java developer reading Kotlin
coroutines, or a backend engineer reading a React hook, needs the *stack's concepts* explained, not just the
code. Name your home stack so Claude can map the ideas: *"I know Java well; explain this Kotlin in terms
of what I'd write in Java."*

### 3. Legacy code understanding

**Reading undocumented code and inferring intent.** Claude is good at proposing what code is *for*. Keep that
separate from what it *does*. Ask for both, labelled:

```text
For each function in <module>, give:
- DOES: what the code literally does (verifiable by reading it)
- PROBABLY FOR: the intent you infer, with the evidence (names, callers, comments)
- CONFIDENCE: high / medium / low
```

Check the "probably for" column against callers, tests, commit messages and the ticket history before
you write it down as fact. That check is verification as covered in M8.2.

**Spotting dead code and hidden coupling.**
- *Dead code:* functions with no callers. But check reflection, DI containers, scheduled jobs,
  serialisation hooks, feature flags and external callers (other services, SQL triggers) before you delete.
  Claude only sees what you show it. Treat "no callers" from a chat as "no callers *in the pasted files*".
- *Hidden coupling:* shared mutable globals, singletons, implicit ordering ("must run after
  `init_cache()`"), magic strings that match across services, and database columns two services both write.

**Generating the documentation that was never written.** These outputs are useful: a module README
(purpose, entry points, dependencies, gotchas), docstrings, a sequence diagram (as covered in M5.1), and a
"how to change this safely" section. Have a second person who knows the code check it. In this
module's exercise that person is the validator.

### 4. Cross-language and cross-framework conversion

**Idiomatic translation, not transliteration.** Transliteration keeps the source language's idioms in the
target's syntax: Java getters/setters in Kotlin, callbacks in an `async` world, class components in modern
React. It compiles and nobody wants to maintain it.

```java
// Java (source)
public String displayName(User u) {
    if (u != null && u.getProfile() != null && u.getProfile().getNickname() != null) {
        return u.getProfile().getNickname();
    }
    return "anonymous";
}
```

```kotlin
// Transliterated Kotlin: compiles, but isn't how anyone writes Kotlin
fun displayName(u: User?): String {
    if (u != null && u.getProfile() != null && u.getProfile()!!.getNickname() != null) {
        return u.getProfile()!!.getNickname()!!
    }
    return "anonymous"
}

// Idiomatic Kotlin: properties, safe calls, elvis
fun displayName(u: User?): String = u?.profile?.nickname ?: "anonymous"
```

**Common conversions and their checklists:**

| Conversion | Mechanical part | Needs a human decision |
|---|---|---|
| **Java → Kotlin** | Syntax, properties, data classes, null-safe calls | Platform types from Java interop (`String!`), where `!!` hides a real null, coroutines vs existing thread pools |
| **.NET Framework → .NET 8** | Project file to SDK style, `packages.config` to `PackageReference`, many APIs | `System.Web` / WebForms / WCF server (no direct port), `AppDomain`, Windows-only APIs, `web.config` → `appsettings.json` + DI |
| **Angular → React** | Templates to JSX, components to function components | DI services → hooks/context, RxJS streams → state + effects, routing guards, module boundaries |
| **Python 2 → 3** | `print`, `except … as`, `dict.iteritems()` | **`str`/`bytes` boundaries**, integer division (`/` vs `//`), dict ordering assumptions, `sorted` with mixed types |
| **SQL dialect migration** (e.g. SQL Server → PostgreSQL) | `TOP n` → `LIMIT n`, `ISNULL` → `COALESCE`, `GETDATE()` → `now()` | Collation/case sensitivity, `''` vs `NULL` (Oracle), identity/sequence semantics, transaction isolation defaults, procedural code (T-SQL → PL/pgSQL) |

**Name what can't be converted automatically.** Ask for it explicitly: *"After converting, list
every construct you could not translate one-to-one, what you did instead, and what behaviour might differ."*
That list becomes the review checklist and the test plan. A conversion with no such list hasn't been
thought through, because real conversions always have one.

### 5. Boilerplate and glue

DTOs, mappers, validators, CRUD endpoints, configuration and CI files are high volume, low novelty and
tedious to type. Claude handles them well, which makes **consistency** the real risk:

- **Generate from your template**, not from Claude's idea of a DTO. Paste the template or a sibling.
- **Diff the output against the template.** Check field ordering, annotation set, nullability, naming case
  (`created_at` vs `createdAt`), validation messages and serialisation attributes.
- **Mappers are where bugs hide in plain sight.** A mapper that silently drops a field, or maps `firstName` →
  `lastName`, passes a compile and a casual read. Generate a round-trip test with it.
- **CI files:** generated YAML often pins nothing, caches nothing, or uses a deprecated action version.
  Compare against your org's CI template, and never accept new secrets usage you didn't ask for.

If you generate the same kind of boilerplate weekly, that's a Skill candidate (M4.2), or a code generator
you own. A generator is deterministic and Claude isn't.

### 6. Stack notes

The trap each stack sets for generated code, and what to check in review:

| Stack | The trap | What it looks like | Review check |
|---|---|---|---|
| **Node / TypeScript** | Async patterns | `array.forEach(async x => …)` doesn't await; a missing `await` returns a pending Promise; an unhandled rejection crashes | Grep for `forEach(async`; require `for…of` + `await` or `Promise.all`; make sure errors propagate |
| **C#** | Nullability | `!` (null-forgiving) sprinkled to silence warnings; `#nullable disable` added | Reject every `!` that lacks a proven invariant; keep NRT warnings as errors |
| **Python** | Typing | `Any` everywhere, `Optional` missing, `List` vs `list` drift across versions | Run `mypy`/`pyright` in strict mode on the generated file |
| **Java** | Generics | Raw types, unchecked casts, `List<Object>`, wildcard misuse (`? extends` vs `? super`) | Compile with `-Xlint:unchecked`; treat warnings as errors on new code |
| **Swift / Kotlin (mobile)** | Platform APIs | APIs deprecated or behaviour-changed in recent OS versions; permissions; main-thread rules | Check the minimum OS version you target; verify every platform API against current docs |
| **Flutter / React Native** | Platform channels / native modules | Method channel names that don't match the native side, wrong threading, invented native APIs | Both sides of the channel reviewed together; run on a real device or simulator |

Node, a classic:

```javascript
// Generated: looks fine, finishes before any email is sent
users.forEach(async (u) => { await sendEmail(u); });
console.log("done");

// Fixed: sequential (or Promise.all for concurrent, with a concurrency limit)
for (const u of users) { await sendEmail(u); }
console.log("done");
```

C#, the null-forgiving trap:

```csharp
// Generated to silence CS8602; crashes at runtime when Customer is null
var city = order.Customer!.Address!.City;

// Honest version: handle the null case the domain actually has
var city = order.Customer?.Address?.City ?? throw new InvalidOperationException("Order has no customer address");
```

## Under the hood

### Why a sample file beats a page of conventions

This is in-context learning again (M2.1). A written rule ("use our `Result<T>` type") is abstract. A file
that uses `Result<T>` in twelve places sets the pattern for the whole output. The model predicts the most
likely continuation *of your codebase* when your codebase is in the context. It predicts the average
of the internet when it isn't. Use the sample to show the pattern and the written rule to state the exceptions.

### Why generated code drifts towards the popular, not the current

Training data overweights older, widely copied code. Common failures:

- **Deprecated APIs** that were idiomatic three versions ago (old React lifecycle methods, `moment.js`, `request`
  in Node, `HttpClient` misuse in .NET).
- **Invented APIs**: a method that *should* exist given the library's naming but doesn't. The name is
  plausible, which is why it's dangerous.
- **Version mixing**: syntax from one major version, imports from another.

What to do: name your versions in the prompt ("React 19, TypeScript 5.x, Node 22"). Compile and run against
the actual lockfile. For any unfamiliar API call, open its docs or jump to its definition before you trust it.
Dependency and supply-chain checks for generated code are covered in M5.4 (Advanced). M8.3 covers licences.

### Why conversion needs tests, and why compiling proves little

A conversion has an exact correctness criterion that most generation doesn't: *same behaviour as before*.
That makes the **existing test suite the oracle**. The workflow:

```text
1. Make sure the source module has tests that pass, and add characterisation tests if it doesn't.
2. Convert.
3. Port the tests idiomatically too (or run the originals through an interop boundary).
4. Run them. Each failure is either a conversion bug or a documented behaviour change.
5. Review the "could not convert one-to-one" list against the failures.
```

Characterisation tests pin *current* behaviour, bugs included, so a conversion can't silently fix (or
break) something a caller depends on.

### Where to do it: chat versus Claude Code

| Task | Chat [app] | Claude Code [code] |
|---|---|---|
| Explain one file, regex or query | ✅ Paste it | ✅ |
| Generate a class from a pasted sample | ✅ | ✅ |
| Generate across many files with real imports | ✗ You'd paste half the repo | ✅ It reads the repo itself |
| Convert a module and run its tests | ✗ Claude can't run your suite | ✅ Run tests inside the loop |

Chat is fine for understanding code and producing single-file output. Once the job needs the repository,
the compiler or the tests, move to Claude Code. M6.2 covers the agentic loop.

## In production

**1. Service layer for a new aggregate**
*Situation:* A Spring Boot service needs a `Subscription` service layer alongside the existing `Order` one.
*Right move:* Supply `OrderService.java`, its test, the package conventions and checkstyle rules. Ask for the
plan (classes, signatures, transaction boundaries) first, review it, then implement. Diff the result against
`OrderService` for divergence: exception types, logging, `@Transactional` placement.
*Why:* the plan catches layering mistakes cheaply, and the sibling file fixes the style.
*Failure mode:* "write a subscription service" with no sample returns a generic service with field
injection and `RuntimeException`, so review spends an hour on style before reaching any logic.

**2. Inherited codebase on a new client engagement**
*Situation:* Day 3 on a client's undocumented .NET Framework monolith.
*Right move:* Walk the entry points with DOES / PROBABLY FOR / CONFIDENCE tables. Produce a module map and a
coupling list, then check every inference with a developer who knows the code before it goes into the handover
doc.
*Failure mode:* publishing Claude's inferred intent as documentation. Six months later someone "fixes"
behaviour that was deliberate.

**3. Modernisation: .NET Framework 4.8 → .NET 8**
*Situation:* A WCF-heavy service has to move.
*Right move:* Convert the project files and library code mechanically. Ask Claude for a "cannot convert
one-to-one" list, which will include the WCF server, `System.Web` and `web.config` transforms. Each item becomes a design
decision with an owner (gRPC, CoreWCF or REST). Run the integration tests at each stage.
*Failure mode:* accepting a converted WCF host that compiles against a shim and fails at runtime on the
first message binding.

**4. Polyglot review: Kotlin from a Java team**
*Situation:* A Java-heavy team inherits an Android module in Kotlin.
*Right move:* "Explain this as if I know Java" walk-throughs, plus a review checklist for Kotlin's specific
traps: `!!`, platform types and coroutine scope leaks.
*Failure mode:* reviewers approve code they can't read, because it "looks fine".

**5. Client demo prototype**
*Situation:* A Next.js prototype is needed in two days for a pre-sales demo.
*Right move:* Ask for full generation, explicitly labelled *prototype*: no production credentials, no real
client data, and a README stating what's stubbed. Track the prototype's code apart from the product repo.
*Failure mode:* the demo code gets merged into the product "because it works". Untested, unreviewed code is now production.

## Pitfalls

| Anti-pattern | Why it bites | Do instead |
|---|---|---|
| "Write a service for X" with no sample | Generic style; fails review on conventions | Supply conventions, lint rules and one sibling file |
| Accepting a 600-line diff without a plan | Architecture mistakes found last, at the highest cost | Plan → review → implement |
| Trusting an unfamiliar API call because the name looks right | Invented or deprecated APIs look plausible | Check the docs or the definition; compile against the real lockfile |
| Documenting inferred intent as fact | Future engineers "fix" deliberate behaviour | Label DOES vs PROBABLY FOR; confirm before publishing |
| Deleting "dead" code because chat found no callers | Reflection, DI, jobs and external callers aren't in the pasted files | Search the whole repo and runtime config; delete behind a flag first |
| Transliterating (Java idioms in Kotlin, callbacks in async) | Compiles; unmaintainable; hides null and concurrency bugs | Ask for idiomatic code *and* a list of what couldn't map one-to-one |
| Converting without running the tests | "Compiles" isn't "behaves the same" | Characterisation tests first, then run the suite on the result |
| `forEach(async …)`, sprinkled `!`, `Any`, raw types | Each stack's known trap ships silently | Run a per-stack review check and strict compiler/linter settings |
| Generated mappers merged unreviewed | Swapped or dropped fields pass compile | Round-trip tests for every mapper |
| Merging demo-prototype code into the product | Unreviewed code reaches production | Keep prototypes in a separate repo or branch, marked as prototypes |

## Hands-on exercises

1. **Service layer vs reference.** Generate a service layer for a given data model in your stack, giving
   Claude your conventions and one sample file. Compare against the hand-written reference implementation.
   **Done when:** you have a table listing *every* divergence from convention (naming, errors, logging,
   transactions, tests), each marked "fixed", "accepted with reason" or "convention updated", and the final
   code passes your linter with zero new warnings.
2. **Legacy module documentation.** Have Claude explain a ~400-line legacy module and produce a
   documentation page (purpose, entry points, DOES/PROBABLY FOR table, coupling, safe-change notes).
   **Done when:** a second learner has checked every statement against the code and marked it correct,
   wrong or unverifiable, and you've fixed or removed every "wrong" and labelled every "unverifiable".
3. **Cross-stack conversion with tests.** Convert a small module between stacks (for example Java→Kotlin,
   Python 2→3, or Angular→React), and port its tests.
   **Done when:** the existing test suite passes against the converted module, and you have a "could not
   convert one-to-one" list in which each item explains how behaviour differs or why it doesn't.
4. **Mobile: Kotlin ↔ Swift feature.** Convert a platform-specific feature (for example biometric login, file
   picker or background refresh) from Kotlin to Swift or the reverse.
   **Done when:** the feature runs on a simulator or device, and you've documented every part that needed manual
   work (platform API differences, permissions, threading) with the reason Claude's first version was wrong
   or incomplete.
